## 一、成因（今天现读出来的，不是推断）

**卡片成品图从来没离开过这台手机。** 两处：

- 账：`wx.setStorageSync('cardLog')`，形状 `{ noteId: [{ p, tpl, at, noQr }] }`（`utils/cardLog.js:20`、`:53`）。
- 图：`${wx.env.USER_DATA_PATH}/cards/{noteId}-{tplId}-{时间戳}.jpg`（`:21`、`:42`）。

服务器侧零存放：全后端与卡片图有关的列只有 `shares.cover_asset_id`（`backend/app/models/share.py:38`），那是扫码落地页封面，不是卡片成品图。

于是**"图被清、账还在"是常态**：`cardLog.js:79-82` 那段注释记着 10-03 模拟器实测到的态——`src` 递到了、232×330 尺寸有、`accessSync` 说文件不在。那时候的处理是"图不在就不列"（今天叫 `aliveFor`，`:87-94`），**症状就是站长看到的"我生成的卡片不见了"**：那一格退回"从没生成过"，不报错、不留痕。

要说清的一条：**不是这次更新删的**。1.9.29 的首页里同一句 `fm.accessSync(p)` 就写着（`git show master:miniprogram/pages/index/index.js` 第 318-326 行 `_cardsOf`），`git diff master...release/2.0 -- miniprogram/utils/cardLog.js` 只有 +21 行（把那段搬进函数），存储键、目录、文件名、那两次一次性归一的开关位全没改。2.0 只是让三处共用了这个谓词，并**新增**了详情页右上那一格（`pages/detail/detail.js:120`）——所以更新后他盯的是"两处都空了"，实际是同一个老问题被多看见一次。

## 二、关键事实：卡片不是照片，是**按数据确定性渲染出来的**，所以丢了的能重新画出来

`pages/share/share.js:139-154` 那一条链：

```
poster.posterProfile()            // 名字、一句话、四槽形象图、当前模板
  + 这篇笔记（标题/摘要/要点/标签/分类/来源链接）
  + 模板 id + showQr(= !noQr) + 语言
  → poster.planPoster(ctx, note, tplId, profile, lang, { showQr })
```

**这条就是 §五 全部三档成立的地基**：只要这三样输入拿得回来，重渲一张就是同一张。**输入里唯一"本机专有"的是四槽形象图那几张文件**——这是 §六 要单独处理的那一态。

而且**服务器手上就有第二份输入**：`shares` 那一行存的是建分享那刻的**快照**——`title / summary / tags / key_points / key_links / source_url / author_name`（`backend/app/models/share.py:26-35`）。笔记后来被人改过也不影响：按快照重渲出来的才是**当年那张**。这条决定了重渲档与补传档能画出"当年那张"，不是"现在这张"。

## 四、日常链路（防再发生）

1. **生成即上传**：`cardLog.record(...)` 那一刻除了落本机，还走 10-07 已上线的直传链（`utils/cloudUpload.js` + 新增 `POST /api/notes/{id}/card`）。上传失败不阻断分享（与 B 链同纪律），失败的那一份进待补队列——**照待补绑那条写**：4xx 不再重试、上限、去重（`utils/assetQueue.js` 同一套形状，别另起一套判据）。
2. **三处读判据改吃服务端**：首页列表（`index.js:306`）、详情页右上（`detail.js:120`）、笔记卡片页"一篇只留一张"那道闸（`share.js:74`）。本机文件降级成缓存：有就读缓存（快），没有就从云取。**改这三处会作废一批现有尺子的口径**——红了先问前提还在不在，改判据，不改代码去迁就旧尺子。
3. **删除连带**：删那篇、注销 → `note_cards` 行一起处理，对象走已上线的待删队列（`utils/assetPurge.js`）。对象只有客户端删得动这条不变（后端没有云开发凭据），所以删除回体要多带一个 `card_file_ids`。
4. **配额**：卡片对象计入全站那个池子，单独一项 SUM，不与笔记配图混成同一个数（「我的」页那行脚注现在说的是配图，口径不许悄悄扩）。

## 五、修复这一档：已经丢的那批怎么找回来（**站长要求写进方案的那一节**）

**一趟"补卡"走查**，入口在「我的 → 笔记卡片」页顶部一行「把丢了的卡片找回来」（一次一个入口，不复制到详情页）。它按这篇手上还有什么，分三档，**三档都要覆盖，缺一档就是没解决**。

> **档位命名只认这一份**：`补传档`（图还在）／`重渲档`（账在图没了）／`待确认档`（连账都没了）。`docs/需求清单-下一版-2.0.1.md` 的 P0-5 原来用甲/乙/丙排的是**另一个顺序**（甲=补传、乙=重渲、丙=无账），两份对着读会把"甲档"读成两件相反的事——10-08 已把那份改成同一套名字。**以后这条线不许再用甲乙丙，只用这三个名字。**

### 待确认档 · 台账整条没了（站长 10-08 点名要补的那一档）

现场：`cardLog` 里这篇一条都不剩（连 `tpl`/`noQr` 都没了）——删小程序重装、换手机、微信清缓存把 storage 一起清掉，都是这档。

判据来源：`shares` 那行。服务端知道"这篇建过分享"（活动与撤掉的都算，撤掉的那些当年也确实出过一张卡）。

处理：**不自己重画**。因为没有任何地方记得当年用的是哪套模板、带不带码——猜一套就是把一张他没见过的图塞进他的库，那是另一种"卡片不对"。所以这一档是**发现 + 提示 + 一键补**：

- 那一格不画空白，画一句**「这篇公开过，卡片不在这台手机上了」**（`origin` 待定，未补之前 `note_cards` 里没有行）。
- 点下去 → 走现有生成流程（默认落他当前那套模板，模板名与"带不带二维码"他当场能看到、能改）→ 出图即上传，`origin='from-share-snapshot'`，正文按 `shares` 那份快照渲（§二 说的那条），所以重出来的那张**内容还是当年那张**。
- 界面上那一句必须与重渲档区分开：重渲档是"我们按你当年选的模板自动补好了"，待确认档是"当年用的哪套已经不记得了，请你确认一下"。

**这一档允许一键，但不允许全自动**——批量猜 12 篇的模板，出错时用户分不清是我们丢了还是我们改了。这条是我的判断，标注在此：**站长没拍过这一条**。要放开自动，请明确说。

### 重渲档 · 账在图没了（站长今天撞到的就是这一态）

现场：`cardLog` 里这篇那一条还在（有 `tpl`、有 `noQr`、有 `at`），只有 jpg 文件被系统清掉了——**这正是 10-03 就实测到过、也是站长今天撞到的那一态**。

处理：**自动重渲**，不需要用户点。输入齐了：`tpl`/`noQr` 从台账、正文从 `shares` 快照（没有分享记录的就从笔记当前内容）、形象从 `posterProfile()`。渲完上传、`origin='re-rendered'`，台账那条指向新对象。

界面上仍要留痕：那一格补回来之后，详情窗里那行小字写「这张是按你当年选的模板重新出的」。**不写这句就是悄悄换了他的东西**。

### 补传档 · 图还在、只是从没上过云

现场：这台手机一切正常，纯粹是老版本没上传过（2.0.1 之前生成的全部卡片都属于这档）。

处理：自动补传，`origin='backfilled'`。**一篇只留一张**这条硬规则不变：台账里同一篇多条时只传 `at` 最大的那条，其余按现有 `migrateOnePerNote` 的做法归掉。

### 三档跑完必须出一份数

`补传 甲?／重渲 乙?／按快照待确认 丙?／跳过 若干`——分开报，不许报一句"已修复"。跳过的每一篇要能列出是为什么跳过：私密笔记没解锁、形象四槽缺图、这篇的笔记正文已删而 shares 也撤了。**这份数是 §七 验收 1 的核对物**。

### 形象缺图那一态（三档共同的例外）

四槽形象图本身也是本机文件（`poster.js:59` 的 `poster_avatar_files`）。如果被清的正好是这几张，重渲出来的卡片上那一格是空的——**这不是"同一张"**。处理：渲之前先 `accessSync` 那几张，缺图的那篇**不做重渲**，归到"待确认"里，界面写「形象图不在这台手机上了，重新挑一张就能补回这张卡片」。**不做的是**：拿品牌占位（`poster.js` 那套没人勾「卡片」时画「麦」字的规则）替上去——那等于把一张他没见过的封面当成原图。

## 七、验收标准

**验收 1 · 丢掉的能找回来**（这条是站长要的那条，**不看"以后不丢"，只看这一条**）

1.1 在这台设备上跑到有历史卡片的状态（现网读数：库里 `shares` 20 行、15 行活动，其中 `user_id=3` 名下 13 行、活动 12 行——这就是天然的样本）。
1.2 造三种现场各至少一例（见上面那把真跑尺子）：整条台账没了 / 只剩账图没了 / 账和图都在。**关键：只删 `/cards/` 里那个 jpg、不动 storage**，就是这个产品最难查的那一态，也是最贴近他实际撞到的那一态。
1.3 跑一趟补卡，断言三件：① 三种现场都不再是"空白格"——分别变成"待确认那句"／"重渲回来的那一张"／"补传上来的那一张"；② 那一张的**内容对得上**（`shares` 那份快照的标题/摘要/要点/标签/来源链接逐项一致，且 `origin` 与档位一致）；③ 报出来的数与实际处理**条数相等**（跳过的要逐条有理由，一条都不许静默）。
1.4 云存储里那个 fileID **真能读回来**：退出去再进同一篇，缩略图还在（这条 2.0 的存图链就是这么验收的，同一个姿势）。
1.5 反向：撤掉重渲那一步必须红——证明这条断言真的在盯着"找回来"，而不是盯着格子有东西。

**验收 2 · 不再丢**（防再发生，只作辅助）
清微信缓存／换设备再进那篇，那一格还有同一张。

**验收 3 · 没伤到别的**：删一篇 → `note_cards` 那行跟着走、云对象被待删队列补删；注销 → 一并（这是唯一一次机会那一路）；撤掉分享不删卡（那是两件事）；配额那行数字真实增加。

**验收 4 · 隐私与合规跟上**：后台指引"相册（读取）"那格扩到"卡片成品图也存云"；`shares` 的公开字段白名单里不能因为这张表就多露东西（`LIVE_PUBLIC_FIELDS` 那条豁免是图片从来没送检，**不扩到卡片**）。

**验收 5 · 出包前**：`cli` 出预览码 → **他真机扫一次**，看的是他自己那批"更新后不见了"的格子，那才是这条的最终判定。他没扫过，这条状态只能算"实现完成"，不能算"真机验过"（待删队列那条就是这么留着的）。

## 九、负面清单

1. 不猜模板（待确认档不自动出图，只发现+提示+一键）。理由见 §五 待确认档那条标注。
2. 不把 `note_cards` 塞进 `assets`：`assets` 那张表带着"9 张/篇"、公开页露图与 `not_failed()` 那套配额语义，卡片混进去迟早串味。
3. 不给卡片做自动送检（个人主体拿不到 `imgSecCheck`，那条豁免只在图片那条链上，不扩）。
4. 不做多设备实时同步/冲突合并：这一步只把"留档"搬到服务端，跨端整体仍是 2.1 那条（而 2.1 那条的密码地基今晚查实有硬伤——无盐 sha256 不能当凭据也不能派生密钥）。
5. 不改"一篇一张"这条硬规则（10-03 站长拍的，要改存量先删旧的）。
6. 不拿品牌占位「麦」字替掉缺图的形象（§五 最后一段）。
7. 不在这一版里顺手做第 11 套模板（要站长看图挑，与这条线无关）。
