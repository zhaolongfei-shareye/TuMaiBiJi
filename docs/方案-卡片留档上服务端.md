## 一、成因（今天现读出来的，不是推断）

**卡片成品图从来没离开过这台手机。** 两处：

- 账：`wx.setStorageSync('cardLog')`，形状 `{ noteId: [{ p, tpl, at, noQr }] }`（`utils/cardLog.js:20`、`:53`）。
- 图：`${wx.env.USER_DATA_PATH}/cards/{noteId}-{tplId}-{时间戳}.jpg`（`:21`、`:42`）。

服务器侧零存放：全后端与卡片图有关的列只有 `shares.cover_asset_id`（`backend/app/models/share.py:38`），那是扫码落地页封面，不是卡片成品图。

于是**"图被清、账还在"是常态**：`cardLog.js:79-82` 那段注释记着 10-03 模拟器实测到的态——`src` 递到了、232×330 尺寸有、`accessSync` 说文件不在。那时候的处理是"图不在就不列"（今天叫 `aliveFor`，`:87-94`），**症状就是站长看到的"我生成的卡片不见了"**：那一格退回"从没生成过"，不报错、不留痕。

要说清的一条：**不是这次更新删的**。1.9.29 的首页里同一句 `fm.accessSync(p)` 就写着（`git show master:miniprogram/pages/index/index.js` 第 318-326 行 `_cardsOf`），`git diff master...release/2.0 -- miniprogram/utils/cardLog.js` 只有 +21 行（把那段搬进函数），存储键、目录、文件名、那两次一次性归一的开关位全没改。2.0 只是让三处共用了这个谓词，并**新增**了详情页右上那一格（`pages/detail/detail.js:120`）——所以更新后他盯的是"两处都空了"，实际是同一个老问题被多看见一次。

## 二、关键事实：卡片不是照片，是**按数据确定性渲染出来的**，所以丢了的能重新画出来

`pages/share/share.js:139-154` 那一条链：

```
poster.posterProfile()            // 名字、一句话、四槽形象图、当前模板
  + 这篇笔记（标题/摘要/要点/标签/分类/来源链接）
  + 模板 id + showQr(= !noQr) + 语言
  → poster.planPoster(ctx, note, tplId, profile, lang, { showQr })
```

**这条就是 §五 全部三档成立的地基**：只要这三样输入拿得回来，重渲一张就是同一张。**输入里唯一"本机专有"的是四槽形象图那几张文件**——这是 §六 要单独处理的那一态。

而且**服务器手上就有第二份输入**：`shares` 那一行存的是建分享那刻的**快照**——`title / summary / tags / key_points / key_links / source_url / author_name`（`backend/app/models/share.py:26-35`）。笔记后来被人改过也不影响：按快照重渲出来的才是**当年那张**。这条决定了重渲档与补传档能画出"当年那张"，不是"现在这张"。

## 四、日常链路（防再发生）

1. **生成即上传**（S2 已落地）：`cardLog.record(...)` 那一刻除了落本机，还走 10-07 已上线的直传链。**收在 `cardLog.copyIn` 的 success 块里一个出处**（`_archive(noteId, entry)`），不在首页与卡片页那两个调用点各写一遍——那两处"人真留下这张"吃的本来就是同一个 `record`。新模块 `utils/cardCloud.js`（送 + 读 + 撤）与 `utils/cardQueue.js`（待补登记），后端口 `POST /api/notes/{id}/card`。
   - 上传失败不阻断分享（与 B 链同纪律）：`cardCloud.archive` 全程不抛，任何一步不成只回 `{skipped:true}`；登记那一步失败才落待补队列。
   - 队列与 `assetQueue` 同套纪律（4xx 不再重试、上限 50、超了丢最旧的并留日志），**但有一处必须相反**：那一份是一篇多条 items 并进去，这一份是**一篇一条、新的顶掉旧的**——服务端"一篇只有一张当前"是唯一索引钉着的，队列里留两条旧 fileID 挨个补，最后赢的那条取决于这台手机上一个数组的顺序。
   - 对象放 `cards/{userId}/{日期}/{随机}.jpg` 这一层。⚠ **换前缀必须先拿探针量过**：桶权限完全可能按前缀给，而这条链按设计不报错，写不进的症状是"每张卡片都静默没上云"。10-08 现读：`APREFIX=cards zsh docs/工具/跑尺子.sh 9431 探-云存储可写` → uploadFile 回出 fileID、deleteFile 那条 `status: 0`，所以这一层可用（`cardCloud.CARD_KIND`）。第一次跑那把是 `timeout waiting for automator response`，**那是 IDE 刚起来的传输红，重跑一次就绿**——别把环境红读成"这一层写不进"。
2. **三处读判据改吃服务端**（S2 已落地）：首页那一格（`index.js:_cardsOf`）、详情页右上那一格（`detail.js:loadNote` + 新增 `loadCard`）、笔记卡片页"一篇只留一张"那道闸（`share.js:onLoad`）——三处现在都问 `cardCloud.cellFor(noteId)` / `cardCloud.hasCard(noteId)`：**本机那张还在就画它（快、不花钱），不在了用服务器上那一行顶上**（`cloud://` 直接进 `<image src>`，与配图那一路同一个用法）。页面里再出现 `accessSync`／`cardLog.aliveFor`／`forNote` 就是退回"更新之后卡片不见了"那个根，`验-卡片那一格两页同源.js` 与 `验-一篇一张-真跑.js` 各钉了一条。
   - 名单从 `/api/user/cards` 一次读全（首页整表重载时读，翻页不重复打）；详情页与那道闸读单篇 `/api/notes/{id}/card`。**"没读过"和"读过、是空"必须分开**：`cardCloud.isLoaded()` 就是为这个留的，界面对没读回来的那一批不许说"没有卡片"。
   - 改这三处确实作废了一批现有尺子的口径（10-08 实际红过四把：`验-列表D2`、`验-卡片那一格两页同源`、`验-删卡片二次确认`、`验-一篇一张-真跑`），**全部按"改判据不改代码迁就旧尺子"处理**，其中「删除那一枚零网络写」那条是前提真变了（见本节第 5 条）。
3. **删除连带**：删那篇、注销 → `note_cards` 行一起处理，对象走已上线的待删队列（`utils/assetPurge.js`）。对象只有客户端删得动这条不变（后端没有云开发凭据），所以删除回体把卡片地址**并进同一个 `file_ids` 键**——⚠ 这一条本方案原来写的是"多带一个 `card_file_ids`"，**S1 实现时改定了**：客户端 `cloudUpload.dropFromDeleteRes` 只读 `file_ids` 那一个键，另起一个键等于那一份永远读不到，云上就留下一堆没人记得的对象。测试钉了 `"card_file_ids" not in body`。
4. **配额**：卡片对象计入全站那个池子，单独一项 SUM，不与笔记配图混成同一个数（「我的」页那行脚注现在说的是配图，口径不许悄悄扩）。
   - **入账口径（站长 10-08 定）：一张卡片按 ≤200KB 的上界估，不是实测**，别用 5MB。今天没有实测数（探针跑到第三趟让站长叫停："别为它停 S1"、"量不到就明说量不到"），那就宁可往上算——报少了的症状是"明明快满了，界面还说有余量"，那正是这个产品最难查的那类假话；估多了只是提前一格提示。
   - ⚠ **这一栏只用于配额估算，不是写口的拒收线**：挡人的那道线是云开发单文件上限 20MB（`routes/cards.py` 的 `MAX_CARD_UPLOAD_BYTES`）。拿一个没量过的数当闸门，症状会是"真用户的卡片存不上"——正好是这条线要修的问题本身。
   - **实测的数从 S2 上线后每条登记的 `file_size` 自己进来**（ssh 只读查一次 `MAX(file_size)`、`AVG(file_size)` 就是数），量到再校，**不需要再跑第四趟探针**。
   - 四处同批改，少一处就是下一个人改错的地方：`models/note_card.py` 的 `CARD_ACCOUNT_BYTES`、`tests/test_note_cards.py`、本节、PRD §8.149。`验-卡片留档S1.js` 钉的就是这四处相等。
5. **「删除」那一枚必须两半都撤**（S2 补的后端口，方案原来漏了这一条）：界面上那枚「删除」说的本来就是"这篇不该再有卡片"。判据挪到服务器那一行之后，只清本机 = **那一格删不掉**（本机账清了，下一次进详情页又从云上读回来画上去）。所以补了 `DELETE /api/notes/{id}/card`：当前行与历史行一起删，回体把那些 fileID 放进**同一个 `file_ids` 键**（与删笔记、注销同一条路，客户端 `dropFromDeleteRes` 只读那一个）。
   - 顺序是硬的：**先撤服务器 → 撤成了才清本机 → 再收窗**。反过来做会留孤儿：云上那个对象再没人记得要去删，而对象只有客户端删得动。撤不成（离线）就当这一格没删，屏上照原样留着 + 一句实话（`cardDropOffline`：「这会儿连不上服务器，那张卡片还留着」）。
   - 这一枚**一次都不碰 shares 那张活码**——「已分享的依旧有效」到今天仍是真话，`验-删卡片二次确认.js` ④钉的就是"整条路只有 `DELETE /api/notes/{id}/card` 这一个口"。

## 五、修复这一档：已经丢的那批怎么找回来（**站长要求写进方案的那一节**）

> **⚠ 2026-10-08 站长判定：这一整节作废，代码已全部撤掉（见 PRD §8.152）。**
> 两个理由：① 这一节里的入口与"自动重出"不是他提的需求，是我从这份方案里自己长出来的；
> ② 重出来的版式不是他当年选的那套、原图确实丢了，所以"找回"是个做不到的承诺——
> 画空框让他逐篇点是错的，替他猜一套版式自动出也是错的。**已经丢的那批找不回来，这句实话不许再包装成"找回"。**
> 下面原文留着，只当"当初为什么会做成那样"的记录，不当规格。

**一趟"补卡"走查**，入口在「我的 → 笔记卡片」页顶部一行「把丢了的卡片找回来」（一次一个入口，不复制到详情页）。它按这篇手上还有什么，分三档，**三档都要覆盖，缺一档就是没解决**。

> **档位命名只认这一份**：`补传档`（图还在）／`重渲档`（账在图没了）／`待确认档`（连账都没了）。`docs/需求清单-下一版-2.0.1.md` 的 P0-5 原来用甲/乙/丙排的是**另一个顺序**（甲=补传、乙=重渲、丙=无账），两份对着读会把"甲档"读成两件相反的事——10-08 已把那份改成同一套名字。**以后这条线不许再用甲乙丙，只用这三个名字。**

### 落定时的三处改法（10-08 S3 开工当天现读现改，都写在这里，别让下一个人去代码里猜）

1. **入口不在「我的」，在首页那一枚「笔记卡片」tab 的顶上**。本节原文写的是「我的 → 笔记卡片」页——
   现网没有这一条路径：「我的」里那一行叫「卡片模板」（`pages/profile`），而「笔记卡片」是首页第二枚 tab
   （`navShare`），也正是空白格出现的那一屏。一行可点的文字，不是实心按钮。
   ⚠ 「一次一个入口、不复制到详情页」那条照旧成立。
2. **`/api/user/cards` 多回一栏 `snapshots`**（`backend/app/api/routes/cards.py`）。重渲必须按
   `shares` 那份快照的正文渲（§二），而客户端没有第二个地方拿得到它——撤过分享的那张在公开口回 404。
   一篇取**最新那一行**分享；没有分享记录的篇不给，客户端回退读笔记当前内容（不许替它编一份）。
3. **待确认那一档还有第二种理由：形象图缺了**。上面「缺图那一态」那条落地成 `reason='avatar'`，
   那一格说的话与"不记得模板"那档**不是同一句**（叫他去做一件补不回来的事就是假话）。
4. **撤过分享、而当年那张要印码的，不自动补**：要印就得新建一张公开码，那是替他决定"这篇又公开了"。
   归进跳过、理由逐条报（`noToken`）。这条方案里原来没写，是实现时发现的——**站长没拍过，标在此**。

### 待确认档 · 台账整条没了（站长 10-08 点名要补的那一档）

现场：`cardLog` 里这篇一条都不剩（连 `tpl`/`noQr` 都没了）——删小程序重装、换手机、微信清缓存把 storage 一起清掉，都是这档。

判据来源：`shares` 那行。服务端知道"这篇建过分享"（活动与撤掉的都算，撤掉的那些当年也确实出过一张卡）。

处理：**不自己重画**。因为没有任何地方记得当年用的是哪套模板、带不带码——猜一套就是把一张他没见过的图塞进他的库，那是另一种"卡片不对"。所以这一档是**发现 + 提示 + 一键补**：

- 那一格不画空白，画一句**「这篇公开过，卡片不在这台手机上了」**（`origin` 待定，未补之前 `note_cards` 里没有行）。
- 点下去 → 走现有生成流程（默认落他当前那套模板，模板名与"带不带二维码"他当场能看到、能改）→ 出图即上传，`origin='from-share-snapshot'`，正文按 `shares` 那份快照渲（§二 说的那条），所以重出来的那张**内容还是当年那张**。
- 界面上那一句必须与重渲档区分开：重渲档是"我们按你当年选的模板自动补好了"，待确认档是"当年用的哪套已经不记得了，请你确认一下"。

**这一档允许一键，但不允许全自动**——批量猜 12 篇的模板，出错时用户分不清是我们丢了还是我们改了。这条是我的判断，标注在此：**站长没拍过这一条**。要放开自动，请明确说。

### 重渲档 · 账在图没了（站长今天撞到的就是这一态）

现场：`cardLog` 里这篇那一条还在（有 `tpl`、有 `noQr`、有 `at`），只有 jpg 文件被系统清掉了——**这正是 10-03 就实测到过、也是站长今天撞到的那一态**。

处理：**自动重渲**，不需要用户点。输入齐了：`tpl`/`noQr` 从台账、正文从 `shares` 快照（没有分享记录的就从笔记当前内容）、形象从 `posterProfile()`。渲完上传、`origin='re-rendered'`，台账那条指向新对象。

界面上仍要留痕：那一格补回来之后，详情窗里那行小字写「这张是按你当年选的模板重新出的」。**不写这句就是悄悄换了他的东西**。

### 补传档 · 图还在、只是从没上过云

现场：这台手机一切正常，纯粹是老版本没上传过（2.0.1 之前生成的全部卡片都属于这档）。

处理：自动补传，`origin='backfilled'`。**一篇只留一张**这条硬规则不变：台账里同一篇多条时只传 `at` 最大的那条，其余按现有 `migrateOnePerNote` 的做法归掉。

### 三档跑完必须出一份数

`补传 甲?／重渲 乙?／按快照待确认 丙?／跳过 若干`——分开报，不许报一句"已修复"。跳过的每一篇要能列出是为什么跳过：私密笔记没解锁、形象四槽缺图、这篇的笔记正文已删而 shares 也撤了。**这份数是 §七 验收 1 的核对物**。

### 补卡那一趟只认 `cards/` 前缀（S0 现读出来的脏数据，不写死就会跟着重渲）

10-08 S0 在那台模拟器上现读到台账长这样（`storage 键名` 里 `cardLogKeepOnly` 与 `cardLogOnePerNote` **都在**——顺带把"那两次一次性归一是不是机关"这条彻底排除了，两个 flag 早就立过）：

```
台账 2 篇，两条的图都是"没了"：
  note 20 → http://usr/cards/20-quote-1791289950038.jpg        （真卡片，jpg 被清）
  note 26 → http://usr/ruler-detail-cell.jpg                    （尺子的自证截图，不是卡片）
cards 目录：文件数 0
poster_avatar_files：0 张（这台设备没存过形象图）
storage：已用 62KB／上限 10240KB（storage 不是瓶颈，瓶颈在私有目录那些文件）
```

第二条是**尺子自己造的**：某把真跑尺子往 `cardLog` 写过一条指向自证截图的条目。它和真卡片在同一份台账里，`tpl` 还写着 `classic`，看起来完全合法。所以：

- **补卡那一趟判定"这是一张卡片"的唯一依据是路径在 `${USER_DATA_PATH}/cards/` 底下**（`cardLog.js:21` 那个 `DIR` 常量，不许自己拼字符串），前缀不对的一条都不补、不重渲、不计进那份数。
- 顺带要清：这类条目留在台账里会让详情页那一格去指一张调试图。清理口径与"待确认档"一致——**不动别的东西**，只把明显不属于 `cards/` 的那几条摘掉，并留一条尺子钉住"台账里不许出现 `cards/` 外的路径"。
- **这条是 S0 读数直接换来的规则**，不是预想：没跑那一把我就不知道该写这一条。

### 形象缺图那一态（三档共同的例外）

四槽形象图本身也是本机文件（`poster.js:59` 的 `poster_avatar_files`）。如果被清的正好是这几张，重渲出来的卡片上那一格是空的——**这不是"同一张"**。处理：渲之前先 `accessSync` 那几张，缺图的那篇**不做重渲**，归到"待确认"里，界面写「形象图不在这台手机上了，重新挑一张就能补回这张卡片」。**不做的是**：拿品牌占位（`poster.js` 那套没人勾「卡片」时画「麦」字的规则）替上去——那等于把一张他没见过的封面当成原图。

## 七、验收标准

**验收 1 · 丢掉的能找回来**（这条是站长要的那条，**不看"以后不丢"，只看这一条**）

1.1 在这台设备上跑到有历史卡片的状态（现网读数：库里 `shares` 20 行、15 行活动，其中 `user_id=3` 名下 13 行、活动 12 行——这就是天然的样本）。
1.2 造三种现场各至少一例（见上面那把真跑尺子）：整条台账没了 / 只剩账图没了 / 账和图都在。**关键：只删 `/cards/` 里那个 jpg、不动 storage**，就是这个产品最难查的那一态，也是最贴近他实际撞到的那一态。
1.3 跑一趟补卡，断言三件：① 三种现场都不再是"空白格"——分别变成"待确认那句"／"重渲回来的那一张"／"补传上来的那一张"；② 那一张的**内容对得上**（`shares` 那份快照的标题/摘要/要点/标签/来源链接逐项一致，且 `origin` 与档位一致）；③ 报出来的数与实际处理**条数相等**（跳过的要逐条有理由，一条都不许静默）。
1.4 云存储里那个 fileID **真能读回来**：退出去再进同一篇，缩略图还在（这条 2.0 的存图链就是这么验收的，同一个姿势）。
1.5 反向：撤掉重渲那一步必须红——证明这条断言真的在盯着"找回来"，而不是盯着格子有东西。

**验收 2 · 不再丢**（防再发生，只作辅助）
清微信缓存／换设备再进那篇，那一格还有同一张。

**验收 3 · 没伤到别的**：删一篇 → `note_cards` 那行跟着走、云对象被待删队列补删；注销 → 一并（这是唯一一次机会那一路）；撤掉分享不删卡（那是两件事）；配额那行数字真实增加。

**验收 4 · 隐私与合规跟上**：后台指引"相册（读取）"那格扩到"卡片成品图也存云"；`shares` 的公开字段白名单里不能因为这张表就多露东西（`LIVE_PUBLIC_FIELDS` 那条豁免是图片从来没送检，**不扩到卡片**）。

**验收 5 · 出包前**：`cli` 出预览码 → **他真机扫一次**，看的是他自己那批"更新后不见了"的格子，那才是这条的最终判定。他没扫过，这条状态只能算"实现完成"，不能算"真机验过"（待删队列那条就是这么留着的）。
