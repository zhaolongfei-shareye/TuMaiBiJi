## 1. Summary（60 秒版）

图麦笔记是一个装在微信里的**个人闪记库**：用户在微信里读到一篇公众号文章、截了一张图、或临时冒出一段想法，粘贴/上传后系统自动把内容采集下来并存进自己的笔记库，可选地用大模型提炼成"标题 + 摘要 + 要点 + 标签"，最终能一键生成带小程序码的分享图回流到微信群。给谁用：**日常在微信内完成阅读与记录、但被"收藏夹存了就死"困扰的重度信息摄入者**。

为什么是现在（v2.2 口径）：**这条产品线的运行成本已经可以压到"零按次付费"**——截图认字用我们服务器里的一个开源库（不限次、不按次计费、不申请密钥），提炼用已领取的**混元 10 亿 Token**（2026-09-19 领取，**有效期至 2027-03-19**），服务器与域名主体早已就绪。三件事凑齐的窗口是有期限的：**token 六个月后作废，拖过 2027-03-19 就等于把已领的额度扔掉**。成功长什么样（工程侧可测版本）：**用户从"粘贴一个链接"到"在笔记列表看到这条笔记"的端到端成功率 ≥ 99%，且提炼环节挂掉不影响内容落库**——v2.0 判定"当前实现尚不满足"，v2.1 **已满足并经测试证明**（提炼不可用时降级存原文入库、任务仍 `completed`，见 F6 与附录 A）。

> ⚠️ 但"降级保内容"只在**提炼**这一环成立，采集侧仍有一处硬单点，只是它换了性质：**截图链路的认字完全在我们自己进程里**（开源 OCR 库），不再有"缺 key / 欠费 / 被限流"这回事——代价是**一张 3420×2214px 的图未缩放单独跑，进程峰值 RSS 实测 1,064MB，而服务器只有约 1,992MB 可用**，识别前必须缩放、并且单张串行。**URL 链路的硬单点是目标站点是否可抓**（境内直连站点抽样可用，海外不通）。两条都见 §7.4 R1。

## 2. Background & Problem

### 2.1 问题（用户视角）

用户在微信里产生的"值得记的东西"散落在三个地方：公众号文章、群聊/朋友圈截图、临时冒出来的一句话。今天把它们留住的手段，没有一个能同时做到"留下原文"和"留下结构"。

### 2.2 当前 workaround 与不足

| 现有做法 | 不足 |
|---|---|
| 微信「收藏」 | 只做存储，无摘要、无标签、无要点；收藏多了等同于没有 |
| 微信「浮窗」 | 上限 14 条，是"稍后读"不是"记得住" |
| 转发给「文件传输助手」 | 时间线淹没，不可检索、不可分类 |
| Flomo / Cubox 等外部笔记 | 跳出微信闭环；截图里的文字要手动搬运且搜不到 |

### 2.3 为什么是现在

来自 `sonus-evaluation-report.md` 第 89-105 行的调研结论，加上本轮实测：

- ~~腾讯云 OCR 每月 1000 次免费，个人自用足够（实测端点从服务器可达，HTTP 200）~~ → **v2.2 更新**：截图认字改用**服务器内的开源 RapidOCR**，不按次计费、无次数上限、不申请密钥（本机实测见 §6.1-C）。腾讯云 OCR 从未被真正采用过——它只是"微信自带 OCR 拿不到"的推论，而"自建开源"这条路当时没评估。
- ~~DeepSeek 按 token 计价，单篇提炼成本可忽略~~ → **v2.1 更新**：提炼成本降到 **0 元**——微信「小程序成长计划 2026」向个人主体开放报名，已领取**混元 10 亿 Token + 10 万张生图额度**（2026-09-19 领取，**至 2027-03-19 有效**），前提是开通云开发环境（已于当日开通，见 §7.3）。**v2.2 进一步定案：只用混元这一家，DeepSeek 删除**（用户："避免维护多个大模型"）。
- **额度有保质期，这是本版最硬的时间约束**：混元 Token 领取后 6 个月内有效。提炼迟迟不落地，10 亿 Token 会在 2027-03-19 归零，而"零按次付费"这条卖点会重新变成"要去买 API"。
- 个人小程序**无法使用 `web-view`**（微信规则，报告第 163 行已核对），因此"原生小程序 + 自建后端"不是可选项而是唯一路径
- 服务器、域名、HTTPS、systemd 托管、CI 化的部署脚本均已就绪（本轮已把部署改造为 systemd 托管并修掉假阳性）

### 2.4 本版故意不解决什么

- **不做视频链接解析**（B 站 / 视频号 / 抖音 / 小红书）。报告第 161 行实测结论：视频号 URL 匿名抓取只能拿到空壳页面（无 og:title / description），必须带登录态；这不是产品问题而是合规与对抗成本问题，整体推到 Phase 2 之后。
- **不做语音转笔记**（v2.1 决策：整体下线）。理由不是"做不到"而是"不值"：腾讯云 ASR 需再开一个云产品 + 2 个凭据，且 `SentenceRecognition` 有 60 秒硬上限，长语音要换接口。**代码已完整删除**（`d4ac638`：后端 service/route/task、前端录音 UI、`app.json` 的 `permission.scope.record`、i18n 12 个 key、`config.py` 两个字段），删后零残留。
- **不支持海外站点 URL**（v2.1 决策）。实测服务器出海受限（`en.wikipedia.org` ConnectTimeout，境内站点抽样 4/4 可抓），换地域或加代理属架构级变更，不为 MVP 做。抓取失败必须给可读文案而不是堆栈。
- **不做协作与内容分发**。本产品是个人库，分享图只是回流手段，不做 feed、不做关注、不做公开主页。

## 3. Personas & User Segments ⚠️薄

> ⚠️ 本节**无用户研究支撑**，是从 `pages/create/create.wxml` 的四个真实入口和 README 定位反推出来的工作假设。上线前应用真机访谈校正，不要当成已验证结论。

**Primary persona（工作假设）**

```
姓名：微信重度阅读者
身份：信息摄入多于信息生产的个人用户（产品/研究/媒体/学生均可能）
情境：一天里在公众号、群聊、朋友圈之间连续切换，反复遇到"这个要记下来"
JTBD：当我在微信里读到/看到/听到值得留存的内容，我想在 10 秒内把它变成一条
      可检索、有结构的笔记，从而之后能真正找回并用上，而不是躺在收藏夹里。
当前 workaround：收藏 + 浮窗 + 转发文件传输助手（见 2.2）
```

**这个产品不为谁做**：不为需要多人共享知识库、需要权限管理、或想把笔记当博客公开发布的团队用户做。

### 4.2 Anti-metrics（明确不优化）

- **不优化"笔记总量"**。以条数为 KPI 会诱导把低价值内容自动灌进库里，直接摧毁"知识库"的可检索性——这是本产品自我毁灭型指标。
- **不优化摘要长度或要点数量**。LLM 提示词已限定 3-8 要点 / 3-6 标签，扩大只会增加 token 成本，不增加价值。
- **不做已读/打开率类engagement 指标**。这类指标与"帮用户记住"无因果关系，优化它必然走向通知骚扰。

### 4.3 关键假设（错了就做错产品）

> **"用户愿意为一条内容接受机器提炼的结构，而不是自己写。"**

本轮实测已经**部分证伪了这个假设的必要性**：`pages/detail/detail.wxml` 第 29/35/46 行对摘要、要点、标签三块全部写了 `wx:if`，`pages/write/write.wxml` 第 16/29/40 行则给用户提供了这三个字段的**手动输入框**。也就是说 LLM 在数据模型上不是必需字段的生产者，只是自动填表器。**若假设不成立，产品退化为"微信内剪藏器 + 手动结构化笔记"仍然可用**——这正是第 8 段把 LLM 降级路径列为主路径超集的原因。

## 5. Value Proposition

**对主用户**：

> "微信重度阅读者终于可以**在微信里用 10 秒把一篇公众号文章/一张截图/一段随手写的想法变成一条有标题、能搜到、能分享的笔记**，而不必**手动复制粘贴、跳出微信、或在收藏夹里重新翻找**，因为图麦笔记把采集（网页抓取 / 截图认字）、结构化提炼、和微信原生的分享回流做在了同一个小程序闭环里。"

**竞争差异化**（对照微信收藏 / Flomo / Cubox）：

- 对手的共同空白是**"输入端"和"回流端"分属两个生态**。微信收藏有输入无结构；Flomo/Cubox 有结构但拿不到微信内的相册截图，且分享出去的图不会带小程序码回流。
- 本产品填的是**两端都在微信内**这个空白：入口是微信原生能力（相册选图、分享链接、手写），出口是带小程序码的分享图（已实测可用）。

#### 6.1-C OCR 选型实测（2026-09-19 深夜，本机，可复现）

探针脚本已入库：**`backend/probes/ocr_probe.py`**，复现命令 `.venv/bin/python probes/ocr_probe.py <截图路径> [<截图路径> …]`（macOS 的 `ru_maxrss` 是字节、Linux 是 KB，脚本已自动换算，所以服务器上的读数可直接比较）。输入是当天两张真实截图，两者难度差别很大，必须分开看：**A = 424KB / 2830×1733px，微信后台「AI 能力」页面单层截图（识别出 50 行 / 437 字）**；**B = 1.5MB / 3420×2214px，Safari 全屏截图，页面上叠了微信聊天窗口和 macOS 菜单栏（69 行 / 357 字）**。都是 Retina 桌面截图，**长边 2830~3420px 已高于主流手机截长图的 2532~2796px**，可当作偏严苛的输入。同一顺序**重复跑了多轮**，下表是全部读数而非挑出来的最好那次。

| 指标 | 实测值 | 结论 |
|---|---|---|
| 模型加载 | 0.18 / 0.22 / 0.25 / 0.35 s | 常驻即可，不必担心启动成本 |
| 加载后常驻内存 | 158.6 ~ 165.7 MB | 服务器可用约 2GB，能养 |
| 单张识别耗时 | A 图 3.47 / 4.31 / 4.72 s；B 图 4.17 / 4.80 / 5.42 / 5.71 s | **最慢 5.71s**，异步 worker 里完全可接受；F4 的"≤8s"目标有余量 |
| 识别过程峰值 RSS（进程高水位） | 跑完 A：835 / 838 / 845 MB；A 之后跑完 B：**1,102 / 1,260 / 1,297 / 1,336 MB**；**B 单独跑（进程里没跑过 A）：1,064 MB** | ⚠️ **这是新暴露的硬风险**，必须先缩放。三点读数说明：**①`ru_maxrss` 是整进程的历史最高点，所以"A+B"那几次里已含 A 的用量，别读成"B 单独用掉 1.3GB"；②B 单独跑就有 1,064MB，证明峰值由单张图的像素决定、不是批次累积出来的，所以缩放和串行才是解药；③同一张 B 四次跑出 1,102~1,336MB，本身有约 ±200MB 抖动**。因此 F7 里"缩放后 ≤800MB"是**待验目标值、不是已测结论**——服务器上加缩放后必须重测，别拿这里的数当上限 |
| 模型文件是否联网下载 | **否**：日志显示直接读 `site-packages/rapidocr/models/` 下的 `PP-OCRv6_det_small.onnx` / `PP-OCRv6_rec_small.onnx` / `ch_ppocr_mobile_v2.0_cls_mobile.onnx` | 部署时无需为模型文件准备出网通路 |
| 中文识别 | **A 图（干净后台页）几乎全对**：菜单、开关说明、"评测任务名称备注/评测版本/评测方/状态"等表格文字连贯可读。**B 图（叠加窗口）正文也能认**："第3页，共16页""5058个字""简体中文(中国大陆)"、聊天消息全文（"出鞘007:大批美舰锁定一艘…"、"vivi: 好听"） | 对我们的场景（读文章/聊天记录截图）**够用**。注意这些引用**全部出自 B 图**，A 图另有一整页正确文字 |
| 缺陷 1 | **输出顺序不是视觉阅读顺序**（按检测框返回，跨栏会跳） | 必须自己按框坐标排序（先 y 分行、行内按 x），否则笔记读起来是碎的 |

**这两条缺陷正是"腾讯云 OCR 更准"的实际含义**，但都可以在我们这侧用 20 行代码补掉，代价是一次性调试，而换供应商的代价是永久多一个凭据、一份账单、一个次数上限。

> **顺手回答一个会被反复问到的问题：「已领的混元 token 能不能直接拿来做 OCR，这样连开源库都不用装？」——不能。**
> 成长计划的资源包只有两项：**文本 Token** 和 **图片生成**，没有识别；混元的视觉理解模型（多模态）**已于 2026-06-22 下线并迁到 TokenHub 按量计费**，不在免费包内；CloudBase 的模型清单里也找不到任何视觉模型（出处见附录 A-2）。
> 所以"用 token 换 OCR"这条路在平台层面就是不通的，**不是我们偷懒选了开源库**。想不装东西、又不花钱，是做不到的；两害相权，装一个 30MB 的库换来"零凭据 + 零按次费 + 无次数上限"，同时把**已领的 10 亿 token 全部留给提炼**——这才是那份额度唯一正确的用法。

**In Scope**：分享链接创建、落地页、Canvas 出图、真实小程序码。

#### F6 URL 剪藏 —— P0（**MVP 主力；采集环节零依赖，提炼环节依赖云函数**）

**功能描述**：粘贴公众号/网页链接 → 后台抓取正文 → 入库。

**In Scope（v2.2）**：
- 采集：`scraper.py` 已实现 SSRF 防护（`BLOCKED_NETWORKS`，第 41-42 行）与公众号专用解析（第 116-134 行）。**这一步只依赖 httpx + trafilatura，不依赖任何外部服务或密钥**，是整条链路的主干。
- **提炼：调混元，且只在云函数里调** ⏳ **v2.2 待实现**。现状代码仍写死 DeepSeek（`llm.py:_call_llm`），要改成调用云函数提炼接口，由云函数内 `cloud.ai()` 走混元；已领取的免费 Token 只有从这个来源调用才会被扣减（见 §6.1-A、附录 A-2）。
- **兜底：提炼不可用就存原文** ✅ **已实现并且是 v2.2 的最终方案**（`add7eb0` + `d14e3c0`）。缺凭据 / 云函数超时 / 429 / 5xx / 返回非 JSON，一律退回爬虫 title + 原文入库，任务状态仍为 `completed`，结果里带 `degraded: true`。**这条决定了"提炼"永远是增强项而不是单点**，替换 provider 时不用重写。
  关键细节：`.env` 里遗留的示例值（`sk-your-deepseek-api-key`）**非空但不是真凭据**，若按"非空即已配置"判断，每条任务都会变成 401 重试失败，比缺 key 更难排查。因此 `llm.py:key_usable()` 用正则识别占位符，**同一个函数被 `deploy.sh` 的配置自检复用**，避免两处判断漂移。v2.2 删掉 `DEEPSEEK_API_KEY` 后，这个函数继续留给云函数触发凭据使用，不跟着删。
- **提炼供应商可插拔（v2.2 新增，回应"要预留接口、降低二次开发重构风险"）** ⏳ 随 §8.2 第 3 步一起做
  出发点：小程序生态的 AI 能力现在**不能进正式版**（§8.6），但测试期过后大概率可正式调用，而**同平台产品对接应当是最优选**。所以本轮改造必须做到"将来换供应商 = 换一层实现"，而不是"重做提炼"。四条硬约束，第 3 步写代码时就按它落，不留到"以后再说"：
  1. **契约冻结**：出向提炼的唯一数据形态是那 4 个字段 `{title, summary, key_points[], tags[]}`（降级时多一个 `degraded: true`）。任何供应商的返回都在 `_parse_response` **这一个出口**归一化成该结构，**不许出现第二处"从模型返回里抠字段"**。新增供应商只需产出"那段 JSON"，落库与 UI 一行不改。
  2. **入口唯一**：`extract_knowledge(text, fallback_title)` 保持全项目唯一入口，调用点钉死在 2 个（`ingest_tasks.py:25` URL 链路、`:65` 截图链路）。**换供应商不得新增第三个调用点**；若某个候选方案做不到这点（典型形态：要求前端直连、要求在路由里判分支），说明它与本设计不兼容，直接否掉。
  3. **provider 分层 + 预留枚举位**：`_call_llm` 这一层之上抽出一个配置项 `EXTRACT_PROVIDER`，取值 `hunyuan_cf`（默认）/ `none`（强制降级，供排查与"提审期临时关能力"用）/ **一个为微信 AI 预留的名字**。预留的确切含义是**只占枚举位、本轮不写任何调用代码**（官方明令禁止把相关代码合入正式版）。`deploy.sh` 自检遇到未实现的 provider 要打印"该 provider 未实现，走降级"，不能静默、也不能崩。
  4. **云函数做哑管道**：Node 云函数只承担"文本进 → 4 字段 JSON 出"，**不碰数据库、不认身份、不含业务分支**。它是可整体替换的适配器——将来若换成微信自家 AI，被替换掉的就是"这一个文件 + 后端那一层 provider 实现"，两扇门之外不牵连任何模块。
  > **别把两个方向混成一件事**：以上四条说的是**出向**（我们调用别人的模型）。§8.6 的 `pageMetadata` + 4 个原子接口是**入向**（小微反过来调用我们的功能），两者互不相干，各自的预留不能互相替代。入向侧现在唯一要做的预留是**能力原子化**——"存一条笔记""查我的笔记"保持为不依赖页面、不依赖分享码的服务层函数，路由只做参数校验。这件事在第 2 步的配置收口里顺手就能守住，不单独立项。
- 异步：RQ 队列 + 任务状态轮询（`/api/tasks/{id}`）

**Out of Scope**：视频站点、需登录态站点、正文图片本地化、多页抓取、海外站点。

**验收标准（v2.2：降级三条已由 `TestExtractionDegradation` 覆盖，云函数两条 + 可插拔两条待补）**：
- Given 提炼凭据缺失或仍为占位符，When 提交一个可抓取的 URL，Then 任务最终 `completed`，笔记含标题与原文，摘要/要点/标签为空且 UI 不渲染对应区块 ✅
- Given 云函数返回 HTTP 429，When 重试 3 次（退避 1/2/4 秒）后仍失败，Then **降级入库而不是 `failed`** ✅（重试策略保留，只是换成打云函数 HTTP 触发）
- Given 云函数在超时窗口内没有返回，When 提交，Then 同样降级入库，**不放任任务卡在 `processing`** ⏳ 待补测试；超时阈值必须实测，官方文档在 5s / 15s / 60s / 900s 之间互相矛盾（附录 C）
- Given 抓取的正文送进云函数后返回的不是合法 JSON，When 提交，Then 降级入库 ⏳ 待补测试
- **可插拔两条（v2.2 新增，是上面那四条约束的验收口）**：
  - Given `EXTRACT_PROVIDER=none`，When 提交一个可抓取的 URL，Then **不发起任何出网请求**即降级入库，任务 `completed` ⏳ 待补测试（可并入 `TestExtractionDegradation`）
  - Given `EXTRACT_PROVIDER` 是已声明但未实现的预留值，When 跑 `deploy.sh` 自检，Then 明确打印"该 provider 未实现，走降级"，且服务与 worker 仍能正常启动 ⏳ 待补
- Given 抓取失败或正文为空，When 提交，Then 任务 `failed` 且 error 文案可展示（非堆栈）✅（`未能从 URL 提取到有效内容`）
- Given SSRF 目标为内网地址，When 提交，Then 拒绝 ⚠️ 代码层有 `BLOCKED_NETWORKS`，**未做运行时验证**
- 边缘：正文超 50,000 字截断（现有逻辑）；模型输入超 12,000 字截断（改造时保留，云函数入参体积另受 HTTP 触发限制约束，未实测）

**已决策**：不支持海外站点。`en.wikipedia.org` 实测 `ConnectTimeout`，微信文档 / 36kr / 公众号 / sqlite.org 均可抓；换地域或加代理属架构级变更，MVP 不做，抓取失败给可读文案。

#### F7 截图转笔记 —— **P0（v2.2：认字改自建 RapidOCR，不欠任何密钥；剩 4 项实现要求）**

**功能描述**：相册/聊天选图 → 上传 → OCR 认字 → 提炼 → 入库。

**依赖提炼的价值：高**——OCR 输出是无视觉层级的碎行文本，且**完全没有标题**，没有提炼就是一条无名笔记（降级时只能取正文首行前 30 字当标题）。

**In Scope（v2.2）**：多图批量（**现状常量**：20 张 / 单张 10MB / 批次 TTL 30 分钟，见 `ingest.py`；v2.2 按下方 P1-1 收紧）、两步式 stage→process、**自建 RapidOCR 认字**、提炼（同 F6：混元 → 兜底存原文）。

**Out of Scope**：表格重建、手写识别调优、版面还原。

**改造必须做到的 4 件事（§6.1-C 实测出来的，不是臆想的）**：
1. **识别前缩放**：长边 ≤1600px。§6.1-C 那两张长边 2830 / 3420px 的截图未缩放直接喂，进程高水位就到了 **835~1,336MB**，而服务器只有约 1,992MB 可用——不缩放就是"一张长截图打死机器"。
2. **严格单张串行**：一次只跑一张，跑完释放再跑下一张。并发识别等于峰值相加。
3. **按框坐标重排序**：先按 y 分行、行内按 x。RapidOCR 按检测框顺序输出，跨栏会跳，不排序的笔记读起来是碎的。
4. **过滤噪声行**：单字且置信度低、或整行只有一个拉丁字母/数字的，丢弃。实测把图标认成了"业业业""κ7""曰""AB X"。

**⚠️ P1-1（原为"必须决策项"，v2.2 用实测数值收口）**：为消除 worker 与 API 主机的文件系统耦合，现改为图片 bytes 直接放内存 `_batch_staging` 并 pickle 进单条 Redis job。**结论：不回退落盘，改走 C——收紧批次（张数、单张字节、批次总字节、TTL）**。理由：真正的大头是 **OCR 单张峰值——一张 3420×2214px 的图单独跑就有 1,064MB 高水位（实测，见 §6.1-C）**，落盘并不能降低它，却会把已经解开的耦合重新系上；而 200MB 的 Redis 常驻是可以用收紧上限解决的——**收紧批次治的是 Redis 那份，不是 OCR 那份，两件事别混**。具体数值随代码一并定，并在测试里锁死。

**⚠️ 新增风险**：认字仍然是这条链路的**硬单点**——没有"降级存原文"可言（没认出字就没有内容），但风险性质变了：v2.1 担心的是"缺 key / 欠费 / 被限流"，v2.2 只剩"我们自己写的代码出不出错、内存够不够"。因此失败态必须如实展示（可重试的错误文案），而不是让任务静默卡在 processing。

**验收标准（v2.2，全部待补）**：
- Given 一张长边 2830~3420px 的真实截图（§6.1-C 那两张即为用例输入），When **缩放后**在**服务器**上识别，Then 进程峰值 RSS ≤800MB ⏳ —— 本机未缩放读数是 835~1,336MB 且带 ±200MB 抖动，所以这条只能在服务器上量，跑一次不算数，取三次最高值判定
- Given 一张含噪声图标的截图，When 识别，Then 输出里没有单字噪声行 ⏳
- Given 一张双栏排版的截图，When 识别，Then 输出顺序符合视觉阅读顺序 ⏳
- Given 一批图（张数/字节取 F7 收紧后的上限，现常量仍为 20 张 / 单张 10MB），When 入库，Then 串行处理且批次总字节不超上限 ⏳
- Given OCR 内部异常，When 提交，Then 任务 `failed` 且前端能看到可重试文案，不出现 `processing` 悬挂 ⏳

## 7. Constraints & Risks

### 7.1 技术约束（实测）

| 约束 | 事实 | 影响 |
|---|---|---|
| 单机资源 | 内存 3,719MB，可用约 **1,992MB**；开源 OCR 加载后常驻 159~166MB、**单张 3420×2214px 未缩放识别峰值 RSS 实测 1,064MB** | **识别前必须缩放到长边 ≤1600px，且单张串行**。这条从"理论担心"变成了实测数字（§6.1-C），是 F7 的第一实现约束 |

### 7.2 数据与隐私

- **openid 绝不下发给客户端**（已实现，用 JWT `sub` 承载内部 user id，并有测试断言响应体不含 openid）
- 上传的图片仅用于当次认字，当前为内存传递、进程重启即消失；**不落盘**（P1-3 重构结果，代价见 F7 的 P1-1）。**v2.2 换自建库后这条更重要而不是更松**：图片 bytes 与缩放后的中间图会同时存在于 worker 进程内（这正是峰值的一部分），"不落盘"从"顺手为之"变成**必须保持的设计约束**
- **新增凭据的存放规则**：云函数 HTTP 触发用的 Bearer 凭据与微信 AppSecret 同级——**只进服务器 `.env`，绝不入库、绝不打进日志、验证脚本只打印"已配置/缺失/长度"**。它在后端与云函数之间是唯一一道门，泄露等于任何人可调用我们的混元额度（因此 R10 的计数义务同时是安全义务）
- 密钥治理：`.gitignore` 已覆盖 `.env`、`*.key`、`backend/keys/`；本轮额外修掉 `upload.sh` 会打包 `.env.bak*` 的泄漏面（提交 `7257868`）。**任何验证脚本只打印"已配置/缺失"，禁止输出明文。**
- **合规面因语音下线而缩小**：`app.json` 的 `permission.scope.record` 已删除、录音代码全清，**《隐私保护指引》不再需要申报"麦克风"权限**，只需覆盖相册（截图上传）。这是删除语音的一个附带收益。**v2.2 复核：换自建 OCR 不改变合规面**——图片仍在自己的服务器上处理，不外发第三方，因此不需要新增任何"第三方数据处理"申报条目。

**乙路线：官方文档已回答的部分（2026-09-19 晚间，微信 wxcloud + CloudBase 双侧文档核对）**

- **但有一条极易踩错的边界，它决定架构而非风格**：同一份规则写明"**第三方 API、直接 HTTP 调用等来源……系统将不再从成长计划免费额度中抵扣，改为从套餐额度中扣除**"。而 CloudBase 恰好提供 OpenAI 兼容端点 `https://{env}.api.tcloudbasegateway.com/v1/ai/cloudbase/chat/completions`。**如果我们的 FastAPI 直接打这个端点，10 亿 token 一分都省不到，还会长出账单。** 所以"混元调用必须发生在云函数内部"是额度生效的前提条件。
- **前提②部分解决**：HTTPS 触发云函数有两条路径，且**都不要求备案域名**——① 微信 `POST /tcb/invokecloudfunction`（`access_token` 鉴权，但文档标注**超时 5 秒**）；② CloudBase HTTP API `POST https://{env}.api.tcloudbasegateway.com/v1/functions/{name}` + `Authorization: Bearer <key>`。默认网关域名的说明是"生产环境建议绑定已备案自定义域名"，即默认域名本身可用。

**乙路线：仍未验证的四件事（写业务代码前必须实测，见 R2）**

1. **超时上限到底是 60s 还是 900s**：CloudBase FAQ 写"建议在云控制台调整，上限 60s"，CLI 配置文档写 `timeout` 取值 1–900 秒、默认 5，而 SDK 默认 15 秒且"两者以最短时间为准"。10–30 秒的提炼请求能否落地完全取决于此。
2. **本环境是否开放 HTTP 网关**：微信 wxcloud 文档目录里只有「HTTP 云函数」（且只服务小程序端 `wx.cloud.callHTTPFunction`，timeout 需 <1500ms），**没有「HTTP 网关」章节**；`api.tcloudbasegateway.com` 只出现在 CloudBase 文档。微信侧创建的环境是否支持，未证实。
3. **provider 与模型名**：文本模型二期文档只列 `hy3`，但 SDK 示例仍写 `hy3-preview`，且"需在控制台手动开启 hy3"；模型清单里**无 `hunyuan-large`**，`hunyuan-image` 旧模型已下线。以控制台「生文模型」实际开关为准。
4. **额度耗尽后的行为——已按用户决策定案**：2026-09-19 晚用户明确"**优先用混元，加一个兜底方案，业务量超了愿意付钱**"。因此 provider 取 `cloudbase`（免费额度优先，**耗尽后自动转扣套餐额度**），不取 `hunyuan-v3`（耗尽即报错）。**这条决策同时关闭了 v2.0 遗留的"是否允许静默转扣费"问题：允许。** 但可见性要求随之升级为必做——见 R10。
5. **出网优先级（v2.2 定案，只剩两级）**：**混元（云函数内）→ 失败则降级存原文、任务仍 `completed`**。**DeepSeek 不再是任何一级**——用户要求"只维护一家大模型"，且服务器 `DEEPSEEK_API_KEY` 从来是空的，删它不损失任何现有能力。第二级已实现并有测试（`add7eb0`），第一级待写。

任一实测不成立（尤其是第 1、2 条），**乙路线不会退化成"换一家模型"，而是退化成"提炼先不做"**：内容照常入库、摘要/要点/标签留空、UI 已 `wx:if` 隐藏不破版。这是 v2.2 与 v2.1 的关键区别——**"提炼能不能上"从此不再绑定"产品能不能用"**，所以第 1～3 条的实测是"增强功能何时上线"的前置，不是发布前置。真正卡发布只剩 R8（合法域名）一项。

### 8.6 微信 AI（小微）接入：本轮结论是"暂不动手，留三个便宜钩子"

2026-09-19 应用户要求研究后台「基础功能 → AI能力」页（`wxamp/aiability/index`）与本产品的结合点。取证范围：官方开发者文档全套 + 该页面 DOM 实况。

**能结合的三件事（低成本，但都不该在上线前做）**

| 钩子 | 与本产品的位置 | 成本 |
|---|---|---|
| **自动模式开关**（授权平台提审时读源码，零开发） | 无需改一行代码；开了之后用户在小微里说"把刚才那篇存进图麦笔记"才有机会路由到本小程序 | 点一下开关，但**提审读源码**这一动作对未上线版本意味着什么官方未写清 |
| **知识库上传**（把产品介绍/使用说明喂给小微） | 直接回答"图麦笔记能存哪几种东西"这类问题，省掉客服面 | 纯内容运营，0 代码 |
| **`agent.pageMetadata` + 4 个原子接口**（`saveNote` / `searchNotes` / `getNote` / `listCategories`） | 与 F1/F2/F3 的接口面几乎一一对应，是最自然的能力声明；**账号卡片回流可用场景值 1435/1436/1442/1443 度量**，正好接上 §4 里"分享回流"这条缺基线的指标 | 需 `agent.skills`（SKILL.md + mcp.json + index.js）+ 独立分包 + `lazyCodeLoading`，**是真开发工作量** |

**为什么现在不做（按证据强弱排序）**

1. **开发模式当前未开放提审评测**——官方文档明写"当前暂未开放提审评测"。写出来的 `agent.skills` 没有任何入口可提交，必然返工。
2. **调试要求已上线版本**：能力声明的联调依赖线上/体验版小程序，本项目连首次提审都没做，无版本可测。
3. **官方明确警告不要合入正式版**：`guide.html` 原文"请勿将此模式相关代码合入正式版本提交审核，以免影响正常版本发布"。也就是说，即便只做实验代码，放进主分支就有污染提审的风险。
4. **文档覆盖面本身是个信号**：整套官方文档只写开发模式，**自动模式没有任何开发者文档**，只有后台一句开关说明。无法从文档判断开与关的实际差异。
5. **主体门槛官方未明确**：未写"个人主体不可接入"，真正的门槛是类目与灰度名额；而需要【深度合成】类目的能力，个人主体无法注册该类目。**这条属"未证实不可行"，不是"已证实不可行"**——若将来要碰，先实测再下结论。
6. **"开了 AI 能力就有官方流量扶持"是建议而非硬条件**：成长计划文案把两者绑在一起推荐，但公开文档里没有扶持的资格条件、申请入口或效果承诺。**不要把它计入收益**。

**结论**：第 4 步提审通过、有了可调试的线上版本之后，再回来做两件事——① 打开自动模式（零成本试错，观察小微是否真的路由过来）；② 若观察到有自然请求，才投入 `agent.skills` 的 4 个原子接口。在此之前本节不产生任何代码任务。

**但"本轮不做"不等于"本轮不预留"**（应用户 v2.2 追加要求）：

| 方向 | 是什么 | 预留动作 | 落在哪 |
|---|---|---|---|
| **出向**：微信 AI 当我们的提炼供应商 | 现在写死走云函数混元；将来同平台 AI 若开放正式调用，它应成为首选供应商 | **F6 那四条可插拔约束**：4 字段契约冻结、`extract_knowledge` 唯一入口、`EXTRACT_PROVIDER` 枚举里给它留位（占名不占码）、云函数做哑管道 | 第 3 步改造里一次做完，成本≈零（因为现状本来就只有 1 个入口 1 处归一化） |
| **入向**：小微调用我们的功能 | `pageMetadata` + 4 个原子接口，是"别人来调我们"，与供应商无关 | **能力原子化**：`存一条笔记`/`查我的笔记` 保持为不依赖页面与分享码的服务层函数，路由只校验参数 | 第 2 步配置收口时顺手守住，不单独立项 |

这样做的意义是把"以后再对接"的代价从"重做提炼"降到"换一个适配器文件"。**同时必须说清边界：本轮不写任何微信 AI 的调用代码**（官方警告禁止合入正式版，见本节上文第 3 条），预留只体现为命名与分层，不体现为依赖。
