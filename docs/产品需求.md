## 1. Summary（60 秒版）

图麦笔记是一个装在微信里的**个人闪记库**：用户在微信里读到一篇公众号文章、截了一张图、或临时冒出一段想法，粘贴/上传后系统自动把内容采集下来并存进自己的笔记库，可选地用大模型提炼成"标题 + 摘要 + 要点 + 标签"，最终能一键生成带小程序码的分享图回流到微信群。给谁用：**日常在微信内完成阅读与记录、但被"收藏夹存了就死"困扰的重度信息摄入者**。

为什么是现在（v2.2 口径）：**这条产品线的运行成本已经可以压到"零按次付费"**——截图认字用我们服务器里的一个开源库（不限次、不按次计费、不申请密钥），提炼用已领取的**混元 10 亿 Token**（2026-09-19 领取，**有效期至 2027-03-19**），服务器与域名主体早已就绪。三件事凑齐的窗口是有期限的：**token 六个月后作废，拖过 2027-03-19 就等于把已领的额度扔掉**。成功长什么样（工程侧可测版本）：**用户从"粘贴一个链接"到"在笔记列表看到这条笔记"的端到端成功率 ≥ 99%，且提炼环节挂掉不影响内容落库**——v2.0 判定"当前实现尚不满足"，v2.1 **已满足并经测试证明**（提炼不可用时降级存原文入库、任务仍 `completed`，见 F6 与附录 A）。

> ⚠️ 但"降级保内容"只在**提炼**这一环成立，采集侧仍有一处硬单点，只是它换了性质：**截图链路的认字完全在我们自己进程里**（开源 OCR 库），不再有"缺 key / 欠费 / 被限流"这回事——代价是**一张 3420×2214px 的图未缩放单独跑，进程峰值 RSS 实测 1,064MB，而服务器只有约 1,992MB 可用**，识别前必须缩放、并且单张串行。**URL 链路的硬单点是目标站点是否可抓**（境内直连站点抽样可用，海外不通）。两条都见 §7.4 R1。

## 2. Background & Problem

### 2.1 问题（用户视角）

用户在微信里产生的"值得记的东西"散落在三个地方：公众号文章、群聊/朋友圈截图、临时冒出来的一句话。今天把它们留住的手段，没有一个能同时做到"留下原文"和"留下结构"。

### 2.2 当前 workaround 与不足

| 现有做法 | 不足 |
|---|---|
| 微信「收藏」 | 只做存储，无摘要、无标签、无要点；收藏多了等同于没有 |
| 微信「浮窗」 | 上限 14 条，是"稍后读"不是"记得住" |
| 转发给「文件传输助手」 | 时间线淹没，不可检索、不可分类 |
| Flomo / Cubox 等外部笔记 | 跳出微信闭环；截图里的文字要手动搬运且搜不到 |

### 2.3 为什么是现在

来自 `sonus-evaluation-report.md` 第 89-105 行的调研结论，加上本轮实测：

- ~~腾讯云 OCR 每月 1000 次免费，个人自用足够（实测端点从服务器可达，HTTP 200）~~ → **v2.2 更新**：截图认字改用**服务器内的开源 RapidOCR**，不按次计费、无次数上限、不申请密钥（本机实测见 §6.1-C）。腾讯云 OCR 从未被真正采用过——它只是"微信自带 OCR 拿不到"的推论，而"自建开源"这条路当时没评估。
- ~~DeepSeek 按 token 计价，单篇提炼成本可忽略~~ → **v2.1 更新**：提炼成本降到 **0 元**——微信「小程序成长计划 2026」向个人主体开放报名，已领取**混元 10 亿 Token + 10 万张生图额度**（2026-09-19 领取，**至 2027-03-19 有效**），前提是开通云开发环境（已于当日开通，见 §7.3）。**v2.2 进一步定案：只用混元这一家，DeepSeek 删除**（用户："避免维护多个大模型"）。
- **额度有保质期，这是本版最硬的时间约束**：混元 Token 领取后 6 个月内有效。提炼迟迟不落地，10 亿 Token 会在 2027-03-19 归零，而"零按次付费"这条卖点会重新变成"要去买 API"。
- 个人小程序**无法使用 `web-view`**（微信规则，报告第 163 行已核对），因此"原生小程序 + 自建后端"不是可选项而是唯一路径
- 服务器、域名、HTTPS、systemd 托管、CI 化的部署脚本均已就绪（本轮已把部署改造为 systemd 托管并修掉假阳性）

### 2.4 本版故意不解决什么

- **不做视频链接解析**（B 站 / 视频号 / 抖音 / 小红书）。报告第 161 行实测结论：视频号 URL 匿名抓取只能拿到空壳页面（无 og:title / description），必须带登录态；这不是产品问题而是合规与对抗成本问题，整体推到 Phase 2 之后。
- **不做语音转笔记**（v2.1 决策：整体下线）。理由不是"做不到"而是"不值"：腾讯云 ASR 需再开一个云产品 + 2 个凭据，且 `SentenceRecognition` 有 60 秒硬上限，长语音要换接口。**代码已完整删除**（`d4ac638`：后端 service/route/task、前端录音 UI、`app.json` 的 `permission.scope.record`、i18n 12 个 key、`config.py` 两个字段），删后零残留。
- **不支持海外站点 URL**（v2.1 决策）。实测服务器出海受限（`en.wikipedia.org` ConnectTimeout，境内站点抽样 4/4 可抓），换地域或加代理属架构级变更，不为 MVP 做。抓取失败必须给可读文案而不是堆栈。
- **不支持 HEIC / HEIF 图片格式**（v2.2 同日决策：用户原话"相册不是重点，我们限制文件格式即可"）。iPhone 默认拍出来的就是 HEIC，Pillow 本机 42 种已注册格式里没有它。两条能支持它的路都付得出代价但都不值：① 引 `pillow-heif`——多一个带原生二进制的依赖，和 §6.1-B 那句"对外只有两扇门"直接冲突，而且是 R13（GUI 版 opencv 缺 `libGL.so.1`）的同型坑；② 前端 `chooseMedia` 加 `sizeType:['compressed']` 让微信重编码成 JPEG——不用改后端，但微信会先压一遍，识别率拿质量换兼容（**"HEIC 经 compressed 会转成 JPEG"这条没有真机实测**，是按微信压缩通道的已知行为推断；真要走这条路必须先量出压缩后的分辨率与识别率再决定）。所以改成**进门就拒 + 说清怎么办**（实现见 F7）。用户侧的自助修法：设置 → 相机 → 格式 → 选「兼容性最佳」。
- **不做协作与内容分发**。本产品是个人库，分享图只是回流手段，不做 feed、不做关注、不做公开主页。

## 3. Personas & User Segments ⚠️薄

> ⚠️ 本节**无用户研究支撑**，是从 `pages/create/create.wxml` 的四个真实入口和 README 定位反推出来的工作假设。上线前应用真机访谈校正，不要当成已验证结论。

**Primary persona（工作假设）**

```
姓名：微信重度阅读者
身份：信息摄入多于信息生产的个人用户（产品/研究/媒体/学生均可能）
情境：一天里在公众号、群聊、朋友圈之间连续切换，反复遇到"这个要记下来"
JTBD：当我在微信里读到/看到/听到值得留存的内容，我想在 10 秒内把它变成一条
      可检索、有结构的笔记，从而之后能真正找回并用上，而不是躺在收藏夹里。
当前 workaround：收藏 + 浮窗 + 转发文件传输助手（见 2.2）
痛点：存进去就再也找不到；截图里的文字搜不到；语音完全无法沉淀
```

**这个产品不为谁做**：不为需要多人共享知识库、需要权限管理、或想把笔记当博客公开发布的团队用户做。

### 4.2 Anti-metrics（明确不优化）

- **不优化"笔记总量"**。以条数为 KPI 会诱导把低价值内容自动灌进库里，直接摧毁"知识库"的可检索性——这是本产品自我毁灭型指标。
- **不优化摘要长度或要点数量**。LLM 提示词已限定 3-8 要点 / 3-6 标签，扩大只会增加 token 成本，不增加价值。
- **不做已读/打开率类engagement 指标**。这类指标与"帮用户记住"无因果关系，优化它必然走向通知骚扰。

### 4.3 关键假设（错了就做错产品）

> **"用户愿意为一条内容接受机器提炼的结构，而不是自己写。"**

本轮实测已经**部分证伪了这个假设的必要性**：`pages/detail/detail.wxml` 第 29/35/46 行对摘要、要点、标签三块全部写了 `wx:if`，`pages/write/write.wxml` 第 16/29/40 行则给用户提供了这三个字段的**手动输入框**。也就是说 LLM 在数据模型上不是必需字段的生产者，只是自动填表器。**若假设不成立，产品退化为"微信内剪藏器 + 手动结构化笔记"仍然可用**——这正是第 8 段把 LLM 降级路径列为主路径超集的原因。

## 5. Value Proposition

**对主用户**：

> "微信重度阅读者终于可以**在微信里用 10 秒把一篇公众号文章/一张截图/一段随手写的想法变成一条有标题、能搜到、能分享的笔记**，而不必**手动复制粘贴、跳出微信、或在收藏夹里重新翻找**，因为图麦笔记把采集（网页抓取 / 截图认字）、结构化提炼、和微信原生的分享回流做在了同一个小程序闭环里。"

**竞争差异化**（对照微信收藏 / Flomo / Cubox）：

- 对手的共同空白是**"输入端"和"回流端"分属两个生态**。微信收藏有输入无结构；Flomo/Cubox 有结构但拿不到微信内的相册截图，且分享出去的图不会带小程序码回流。
- 本产品填的是**两端都在微信内**这个空白：入口是微信原生能力（相册选图、分享链接、手写），出口是带小程序码的分享图（已实测可用）。
- 差异化不来自"更好的 UX"这类空话，来自**个人小程序无法用 web-view 这一硬约束下的原生闭环取舍**（报告第 163 行）。

⚠️ 语音输入已于 v2.1 整体下线，**本节此前的"一段语音"表述是过期文案**，v2.2 已改。已复查 `miniprogram/` 全量 `grep`（`语音|录音|转文字|voice`）**零命中**，前端对外文案干净；提审时若微信后台"小程序简介"仍写着语音，那是后台字段而非代码，需一并核对。

| 模型加载 | 0.18 / 0.22 / 0.25 / 0.35 s | 常驻即可，不必担心启动成本 |
| 加载后常驻内存 | 158.6 ~ 165.7 MB | 服务器可用约 2GB，能养 |
| 单张识别耗时 | A 图 3.47 / 4.31 / 4.72 s；B 图 4.17 / 4.80 / 5.42 / 5.71 s | **最慢 5.71s**，异步 worker 里完全可接受；F4 的"≤8s"目标有余量 |
| 识别过程峰值 RSS（进程高水位） | 跑完 A：835 / 838 / 845 MB；A 之后跑完 B：**1,102 / 1,260 / 1,297 / 1,336 MB**；**B 单独跑（进程里没跑过 A）：1,064 MB** | ⚠️ **这是新暴露的硬风险**，必须先缩放。三点读数说明：**①`ru_maxrss` 是整进程的历史最高点，所以"A+B"那几次里已含 A 的用量，别读成"B 单独用掉 1.3GB"；②B 单独跑就有 1,064MB，证明峰值由单张图的像素决定、不是批次累积出来的，所以缩放和串行才是解药；③同一张 B 四次跑出 1,102~1,336MB，本身有约 ±200MB 抖动**。因此 F7 里"缩放后 ≤800MB"是**待验目标值、不是已测结论**——服务器上加缩放后必须重测，别拿这里的数当上限 |

| 缺陷 1 | **输出顺序不是视觉阅读顺序**（按检测框返回，跨栏会跳） | 必须自己按框坐标排序（先 y 分行、行内按 x），否则笔记读起来是碎的 |

**这两条缺陷正是"腾讯云 OCR 更准"的实际含义**，但都可以在我们这侧用 20 行代码补掉，代价是一次性调试，而换供应商的代价是永久多一个凭据、一份账单、一个次数上限。

##### 落地后复测（2026-09-19 晚，同机同图，代码已含缩放/串行/排序/降噪）

缩放这条不能靠推理，所以用**同一张 B 图**只改 `MAX_LONG_EDGE` 跑了一次对照（每次都是新进程，避免高水位互相污染）：

| 识别前缩放 | 耗时 | 进程峰值 RSS | 输出字符数 |
|---|---|---|---|
| 不缩放（长边 3420） | 4.32s | **1,076.6 MB** | 294 |
| **长边 ≤1600（定稿值）** | 3.32s | **666.6 MB** | **301** |
| 长边 ≤1280 | 2.63s | 528.5 MB | 283 |

三点结论：**①缩放确实有效**——峰值降 38%、耗时降 23%，与上面"峰值由单张图像素决定"的判断一致；**②1600 是当前甜点**，字符数不降反升（294→301），说明这一步没牺牲内容；**③1280 开始丢字**（283），不再往下压。

两处必须说清、否则会被误读：
- **绝对值之间不可比**。`deploy.sh` 的 OCR 自检用一张 760×140px 的合成小图，本机峰值反而有 816~826MB——比真图缩放后还高。这说明高水位里有一块与输入像素无关的常驻开销（onnxruntime 线程 arena + 三个模型），所以**只有"同图改缩放"这种对照才有意义**，也说明"≤800MB"这个目标值本机根本判不了，服务器侧仍按"三次取最高"来量。
- 缩放用 `requirements.txt` 里已有的 `Pillow`，**没有为此新增第三个包**；交给模型的输入是 `PIL.Image`（RGB/RGBA）而不是 `ndarray`——RapidOCR 的加载器把 ndarray 直接当 **BGR**，只有走 PIL/bytes 入口才会做 RGB→BGR，喂错颜色顺序是静默降准确率的那种坑。

> **顺手回答一个会被反复问到的问题：「已领的混元 token 能不能直接拿来做 OCR，这样连开源库都不用装？」——不能。**
> 成长计划的资源包只有两项：**文本 Token** 和 **图片生成**，没有识别；混元的视觉理解模型（多模态）**已于 2026-06-22 下线并迁到 TokenHub 按量计费**，不在免费包内；CloudBase 的模型清单里也找不到任何视觉模型（出处见附录 A-2）。
> 所以"用 token 换 OCR"这条路在平台层面就是不通的，**不是我们偷懒选了开源库**。想不装东西、又不花钱，是做不到的；两害相权，装一个占地 ≈273MB（模型只占 30MB）的库换来"零凭据 + 零按次费 + 无次数上限"，同时把**已领的 10 亿 token 全部留给提炼**——这才是那份额度唯一正确的用法。

**大模型的作用面就这么大**：语音下线后全项目只剩 2 个调用点——`app/tasks/ingest_tasks.py` 第 25 行（URL 链路）、第 65 行（截图链路），全部位于"采集完成之后"。没有任何自动归类、语义搜索、问答功能使用大模型。它产出 4 个字段，其中只有 3 个是模型专属：

| Note 字段 | 唯一来源 | 无提炼能力时 |
|---|---|---|
| `original_content` | 爬虫 / OCR | ✅ 不受影响 |
| `title` | URL 链路：爬虫已给（`scraper.py` og:title / h1 / "网页摘录"） | ✅ URL 可用；**截图链路为空**，降级时用正文首行前 30 字兜底（`llm.py:_degraded`） |
| `summary` `key_points` `tags` | 只有大模型 | 空（UI 已 `wx:if` 隐藏，不破版） |

**结论不变且已被代码证实：除"自动提炼"这一个动作之外，MVP 没有任何功能依赖大模型。**

> ✅ **v2.0 列出的那个致命 coupling 已修复**。v2.0 实测 `notes.py:87-88` 的搜索只覆盖 `Note.title` 和 `Note.summary`，而 `summary` 是大模型专属字段——一旦没有大模型，自动入库的笔记就只能按标题找，"界面上不破，检索上会废"。
> v2.1 现状：搜索列已扩到 `title / summary / content / original_content` 四列并保留 `%` `_` 字面量转义（`c7d48d8`），且**有测试锁死**——`TestSearchScope` 用"`summary` 为空但正文含关键词"的样本断言必须命中（`d14e3c0`）。
> 代价照旧：SQLite 对大文本列 `LIKE` 无索引即全表扫描，MVP 量级（数千条）可接受，规模化再上 FTS5。

- **提炼供应商可插拔（v2.2 新增，回应"要预留接口、降低二次开发重构风险"）** ⏳ 随 §8.2 第 3 步一起做
  出发点：小程序生态的 AI 能力现在**不能进正式版**（§8.6），但测试期过后大概率可正式调用，而**同平台产品对接应当是最优选**。所以本轮改造必须做到"将来换供应商 = 换一层实现"，而不是"重做提炼"。四条硬约束，第 3 步写代码时就按它落，不留到"以后再说"：
  1. **契约冻结**：出向提炼的唯一数据形态是那 4 个字段 `{title, summary, key_points[], tags[]}`（降级时多一个 `degraded: true`）。任何供应商的返回都在 `_parse_response` **这一个出口**归一化成该结构，**不许出现第二处"从模型返回里抠字段"**。新增供应商只需产出"那段 JSON"，落库与 UI 一行不改。
  2. **入口唯一**：`extract_knowledge(text, fallback_title)` 保持全项目唯一入口，调用点钉死在 2 个（`ingest_tasks.py:25` URL 链路、`:65` 截图链路）。**换供应商不得新增第三个调用点**；若某个候选方案做不到这点（典型形态：要求前端直连、要求在路由里判分支），说明它与本设计不兼容，直接否掉。
  3. **provider 分层 + 预留枚举位**：`_call_llm` 这一层之上抽出一个配置项 `EXTRACT_PROVIDER`，取值 `hunyuan_cf`（默认）/ `none`（强制降级，供排查与"提审期临时关能力"用）/ **一个为微信 AI 预留的名字**。预留的确切含义是**只占枚举位、本轮不写任何调用代码**（官方明令禁止把相关代码合入正式版）。`deploy.sh` 自检遇到未实现的 provider 要打印"该 provider 未实现，走降级"，不能静默、也不能崩。
  4. **云函数做哑管道**：Node 云函数只承担"文本进 → 4 字段 JSON 出"，**不碰数据库、不认身份、不含业务分支**。它是可整体替换的适配器——将来若换成微信自家 AI，被替换掉的就是"这一个文件 + 后端那一层 provider 实现"，两扇门之外不牵连任何模块。
  > **别把两个方向混成一件事**：以上四条说的是**出向**（我们调用别人的模型）。§8.6 的 `pageMetadata` + 4 个原子接口是**入向**（小微反过来调用我们的功能），两者互不相干，各自的预留不能互相替代。入向侧现在唯一要做的预留是**能力原子化**——"存一条笔记""查我的笔记"保持为不依赖页面、不依赖分享码的服务层函数，路由只做参数校验。这件事在第 2 步的配置收口里顺手就能守住，不单独立项。

**Out of Scope**：视频站点、需登录态站点、正文图片本地化、多页抓取、海外站点。

#### F7 截图转笔记 —— **P0（v2.2：认字改自建 RapidOCR，不欠任何密钥；剩 4 项实现要求）**

**功能描述**：相册/聊天选图 → 上传 → OCR 认字 → 提炼 → 入库。

**依赖提炼的价值：高**——OCR 输出是无视觉层级的碎行文本，且**完全没有标题**，没有提炼就是一条无名笔记（降级时只能取正文首行前 30 字当标题）。

**In Scope（v2.2）**：**进门先过格式白名单**（PNG / JPEG / GIF / BMP / TIFF / WEBP，按文件头判，其余 400）、多图批量（**已收紧为**：10 张 / 单张 10MB / 批次总字节 40MB / **每用户活跃批次 2 个** / **全局暂存 120MB** / TTL 30 分钟，见 `ingest.py`）、两步式 stage→process、**自建 RapidOCR 认字**、提炼（同 F6：混元 → 兜底存原文）。

**Out of Scope**：表格重建、手写识别调优、版面还原、**HEIC/HEIF**（见 §2.4）。

**改造必须做到的 4 件事（§6.1-C 实测出来的，不是臆想的）**——**v2.2 落地状态：4 条全部写进代码并有测试，`backend/app/services/ocr.py` 已从腾讯云 TC3 签名实现整体换成进程内 RapidOCR，对外两个函数签名 `ocr_image(bytes)->str` / `ocr_images(list[bytes])->str` 一字未改（worker 与测试都靠它）**：
1. **识别前缩放**：长边 ≤1600px。§6.1-C 那两张长边 2830 / 3420px 的截图未缩放直接喂，进程高水位就到了 **835~1,336MB**，而服务器只有约 1,992MB 可用——不缩放就是"一张长截图打死机器"。✅ 已实现（`MAX_LONG_EDGE=1600`，Pillow LANCZOS；实测对照见 §6.1-C 落地后复测）。**注**：`PIL.Image` 直接交给引擎而非 ndarray，避免 BGR/RGB 颜色顺序坑。
2. **严格单张串行**：一次只跑一张，跑完释放再跑下一张。并发识别等于峰值相加。✅ 已实现（`_run_lock` 全局串行 + 模型单例双检锁懒加载；`RapidOCR.__call__` 内部会 `update_params` 改自身状态，本就不是线程安全，锁同时解决了这两件事）。测试用假引擎计数验证并发数恒为 1。
3. **按框坐标重排序**：先按 y 分行、行内按 x。RapidOCR 按检测框顺序输出，跨栏会跳，不排序的笔记读起来是碎的。✅ 已实现。**落地时校正了一点**：同一行的多个框用**空格**连接而不是直接粘贴——两个独立框粘在一起会造出"帮我做了太简陋了"这种假词。真图复测菜单栏已正确读作"Safari浏览器 文件 编辑 显示 历史记录 书签 开发 窗口 帮助"。
4. **过滤噪声行**：~~单字且置信度低、或整行只有一个拉丁字母/数字的，丢弃~~ → **落地时收紧为"单字行全丢"**。实测把图标认成了"业业业""κ7""曰""AB X""品""稿""像""区"，其中"品/稿/像/区"是**高置信度的单个中文字**，按原写法（只在低置信时才丢单字）抓不住它们，真图上一屏留下 8 行垃圾。现规则：置信度 <0.5 丢；有效字符 ≤1 个丢；不含中文且有效字符 ≤4 丢；同一字符重复（"业业业"）丢。**代价说清楚**：正文里真正只有一行的单个汉字会被吃掉——对"截图→提炼"这个场景可接受，因为一个字既成不了标题也成不了要点。✅ 已实现并有测试。

**批次上限（P1-1 的"收紧"部分，v2.2 定数值）**：`MAX_IMAGES_PER_BATCH` 20 → **10**（前端单次最多选 9 张，留 1 张余量）、单张 **10MB** 不变、**新增批次总字节上限 40MB**、TTL **1800s** 不变。这六个常量由 `test_ocr_flows.py` 锁死，改动必须同时改文档。**分清治谁**：总字节上限治的是进 Redis job 的那份内存（原来最坏 20×10MB=200MB），OCR 那份峰值靠上面的缩放压，两件事互不替代。

**⚠️ 上面那四条卡的是"单批多大"，没卡"能有几批"（2026-09-19 审查发现的洞，本轮已补）**：`/screenshots/stage` 限流 20 次/分钟、批次 TTL 30 分钟，而**不传 `batch_id` 就是新建批次**——一个客户端在半小时内能堆出几百个各 40MB 的批次，`_batch_staging` 是进程内 dict，等于把 API 主机的内存交给单个用户决定。补的两条：`MAX_BATCHES_PER_USER = 2`（新建批次前淘汰该用户**自己**最旧的那批，不动别人的）、`MAX_STAGING_BYTES = 120MB`（全局预算仍不足时返回 **429**，而不是悄悄丢掉已暂存的内容）。另外把 `_sweep_stale_batches()` 也加进了 `process`：用户传完不点"提交"时，过期批次要等下一次上传才被清，加这一条让内存释放不依赖新的上传动作。

**⚠️ P1-1（原为"必须决策项"，v2.2 用实测数值收口）**：为消除 worker 与 API 主机的文件系统耦合，现改为图片 bytes 直接放内存 `_batch_staging` 并 pickle 进单条 Redis job。**结论：不回退落盘，改走 C——收紧批次（张数、单张字节、批次总字节、TTL）**。理由：真正的大头是 **OCR 单张峰值——一张 3420×2214px 的图单独跑就有 1,064MB 高水位（实测，见 §6.1-C）**，落盘并不能降低它，却会把已经解开的耦合重新系上；而 200MB 的 Redis 常驻是可以用收紧上限解决的——**收紧批次治的是 Redis 那份，不是 OCR 那份，两件事别混**。具体数值已定并锁进测试：**10 张 / 单张 10MB / 批次总字节 40MB / TTL 1800s**（见上一段）。

**坏图也要说人话（2026-09-19 审查补，✅ 已实现）**：`_prepare` 把解码整体包进 try，`Image.open` 认不出的字节（含 **HEIC**——本机 Pillow 10.4.0 `Image.init()` 后注册 42 种格式，其中没有 HEIF/AVIF，已实测确认；**注意不调 `init()` 只数得到 41，插件是懒注册的**）抛中文"图片无法识别，可能格式不受支持"；截断/超大图分别有各自文案（PNG 的截断是**懒解析**，`Image.open` 阶段不报错，所以显式 `img.load()` 把失败点提前到能给出中文消息的地方）。原先那句附带的 iPhone 设置路径（相机 → 格式 → 兼容性最佳）已从 toast 文案里去掉——它超过 30 字会被截断，改由入口卡片小字承载。

**用户可见文案与运维线索分家（同日审查补，✅ 已实现）**：上面这些串会进任务 `failed` 的 `error` 字段并被前端原样塞进 toast，所以"给用户的"和"给运维的"必须显式分开，而不是靠 `str(e)` 一把梭。规则由一个新类型承担：`app/core/errors.py::UserError`（继承 `RuntimeError`，不改既有捕获行为）。**只有 `UserError` 的文本允许出门**，其余异常在 `ingest_tasks.failure_message()` 与 `scraper.scrape_url()` 两处收口成通用中文、原文进 `logger`。据此搬迁的两例：① RapidOCR 导入失败原先抛"…opencv 找不到 libGL.so.1，需 apt install libgl1…"，现在用户只看到"图片识别暂不可用，请稍后重试"，`libGL` 那条完整留在日志（`exc_info`）且测试钉住两边；② URL 抓取原先把 httpx 的英文异常（含完整 URL）直接透出，现按 401/403/404/其他状态码给中文，连接失败与超时统一"读取网页失败，请稍后重试或改用截图"。顺带把 charset 声明错误的页面改成 `errors="replace"` 而不是让整条任务失败。

**AppSecret 不许从异常文本里走出去（同日第三轮补，✅ 已实现并已部署到现网，见 §8.7）**：上一段立的规矩，这一轮用到唯一一处"异常原文里本身带着密钥"的地方。实测（`httpx.MockTransport`，本机）：`resp.raise_for_status()` 抛出的 `HTTPStatusError` 首行是 `Server error '502 Bad Gateway' for url 'https://api.weixin.qq.com/cgi-bin/token?grant_type=client_credential&appid=wx…&secret=SENTINEL-app-secret-7f3d'`——**httpx 会把整条含 query 的 URL 拼进异常文本**，而取 access_token 的 AppSecret 正在 query 里。旧代码这条串沿 `get_access_token → get_qr_code_image → shares.py` 的 `except Exception as e: raise HTTPException(500, detail=f"生成小程序码失败: {e}")` 一路走到响应体，而 `/api/shares/{token}/qrcode` 只需要一个有效 share token、**不要求登录**（`create_share` 才要鉴权）。**这条不是推理，是 A/B 实跑**：把 HEAD 版 `wechat.py`+`shares.py` 与工作区版各装进同一个进程、喂同一份"token 接口返回 502"的桩（一次性脚本，未入库；**可反复跑的等价断言在 `test_note_flows.py::TestCredentialErrorsDoNotLeak`**），旧侧 `HTTPException(500).detail` = `生成小程序码失败: Server error '502 Bad Gateway' for url 'https://api.weixin.qq.com/cgi-bin/token?grant_type=client_credential&appid=wx4416d1283b5de721&secret=SENTINEL-app-secret-7f3d'`（哨兵命中 `True`），新侧 `502` + `微信接口暂不可用，请稍后重试`（命中 `False`，状态码与响应体只出现在日志行）。也就是说：微信 token 接口返回任何 4xx/5xx（网关抖动、限流都会），AppSecret 明文就出现在匿名调用方拿到的 JSON 里。**修复上线前，现网旧版一直带着这条**，与本轮那些未部署的改动无关。修法是把 `raise_for_status()` 换掉：状态码与响应体只 `logger.error`，往外抛不含凭据的 `UserError("微信接口暂不可用，请稍后重试")`；`shares.py` 的兜底分支改成固定文案 + 502（`share.js` 只判 `statusCode === 200`，状态码变更不影响前端），并单独放行 `UserError`；`auth.py` 的 `_wechat_code2session` 同规则处理，顺带补了两个旧缺口——响应非 JSON 时原先在 `resp.json()` 处抛裸异常，`openid` 缺失时原先在下游 `data["openid"]` 处抛 `KeyError`，两条都变成中文；errmsg 只进日志不再拼进 401 detail。**4 条哨兵测试**把 `SENTINEL-app-secret-7f3d` 注进 `settings.WECHAT_APP_SECRET`，分别断言异常文本、`caplog`、HTTP 响应体三处都不含它，并断言那条含凭据的请求确实发出去了（否则测试会因为"根本没调用"而假绿）。附带一处：`llm.py` 的"DeepSeek API Key 未配置或仍为占位符"原先会经 `str(e)` 进 toast（泄露配置项名），现被 `failure_message()` 收口成通用文案。**这套规矩现在覆盖全仓**：`grep` 过 `app/api/` 里所有 `detail=f"…{e}"` 与 `{exc}` 插值，除 `shares.py` 放行 `UserError` 那一处外已无例外。

**像素闸门（同日审查实测补，✅ 已实现）**：单张 ≤10MB 管得住字节管不住像素——实测一张 **0.43MB 的纯色 PNG（12000×12000 / 1.44 亿像素）能过掉格式闸门**，而"先全尺寸解码再缩放长边"的写法把进程峰值 RSS 顶到 **1271MB / 6.86s**（干净进程对照：拦住之后 37MB / 0.015s）。Pillow 自身的阈值挡不住这一档：它在 `open` 里就拒掉 1.79 亿像素以上（`DecompressionBombError`，已被上面的中文分支接住），**8950 万～1.79 亿之间只 warn**。所以 `_prepare` 在 `load()` 之前用文件头给出的宽高判像素数，`MAX_PIXELS = 40_000_000` 以上直接 `UserError("图片像素过大，请换一张或分次截取")`；真机截图 3420×2214 只有 760 万像素，留了约 50 倍余量。这条与批次字节上限是两件事：**字节管的是 Redis 里那份，像素管的是 worker 解码那一下**。

**格式闸门挪到进门处（2026-09-19 决策"限制文件格式即可"，✅ 已实现）**：`ingest.py` 的 `_image_format(data)` 按**文件头**（不是扩展名）判格式，只放行 PNG / JPEG / GIF / BMP / TIFF / WEBP，其余在 `/screenshots/stage` 直接 **400**。为什么不等 worker：HEIC 走到解码才失败，意味着它已经占过 Redis、占掉了一个 40MB 批次额度，最后还给用户一条英文栈。`_prepare` 里那句中文提示因此退成第二道闸——它仍然要留着，因为直接投喂 worker 的路径不经 stage。

**一句提示语为什么只有 23 个字（别再往回写）**：`wx.showToast({icon:'none'})` 的 title 只容两行（约 30 个汉字），超了从后半句开始截断。所以 toast 里只留"怎么办"（改用 JPG 或 PNG），iPhone 的设置路径写在**选择入口的小字**上（`albumDesc: '相册选择 / 拍照（JPG·PNG）'`，卡片小字会换行不截断），测试里用 `len(detail) <= 30` 钉住这条约束。

**⚠️ 后端给了中文还不等于用户看得到（本轮实测到的前端断点）**：`wx.request` 的 `res.data` 是**对象**，而 `wx.uploadFile` 的是**字符串**——页面里 `(err.data && err.data.detail)` 这种取法在上传失败时会拿到 `undefined`，用户只看得到兜底的"处理失败，请重试"，格式白名单等于白做。修法是 `uploadSingleImage` 在非 2xx 时先 `JSON.parse` 再 reject（正文不是 JSON 时原样抛出，不抛异常）。本地已验两条路径：400 + JSON 正文 → 页面拿到中文提示；502 + HTML 正文（网关页）→ 走兜底文案且不抛异常。

**成功提示改中性（同日决策，✅ 已实现）**：`extractSucceeded` 原为"提取成功"，但任务 `completed` 只证明笔记建好了，正文可能是提炼降级后的空壳。改为"已存入笔记"——只陈述一定为真的那部分，内容好坏留给详情页判断。**这条是小程序文案，要重新提审才生效**（与后端那两条不同，后端随部署生效）。

**⚠️ 新增风险**：认字仍然是这条链路的**硬单点**——没有"降级存原文"可言（没认出字就没有内容），但风险性质变了：v2.1 担心的是"缺 key / 欠费 / 被限流"，v2.2 只剩"我们自己写的代码出不出错、内存够不够"。因此失败态必须如实展示（可重试的错误文案），而不是让任务静默卡在 processing。**本轮按这个要求做了两件事**：错误文案按 `UserError` 收口（见上面"用户可见文案与运维线索分家"）；但**"任务不静默卡在 processing"这一条仍然没做到**——worker 被 OOM 干掉或超过 `job_timeout=600` 时被 RQ 强杀，没有 failure callback 去翻状态，`task:{id}` 会停在 `processing` 直到 3600s TTL，而客户端只轮询 300s。这是 R1/R5 之外的独立欠账，未修。

### 7.2 数据与隐私

- **openid 绝不下发给客户端**（已实现，用 JWT `sub` 承载内部 user id，并有测试断言响应体不含 openid）
- 上传的图片仅用于当次认字，当前为内存传递、进程重启即消失；**不落盘**（P1-3 重构结果，代价见 F7 的 P1-1）。**v2.2 换自建库后这条更重要而不是更松**：图片 bytes 与缩放后的中间图会同时存在于 worker 进程内（这正是峰值的一部分），"不落盘"从"顺手为之"变成**必须保持的设计约束**。本轮据此把批次上限收紧为**定值**：单张 ≤10MB、单批 ≤10 张、单批合计 ≤40MB、**每用户活跃批次 ≤2 个**、**全局暂存 ≤120MB**、暂存 1,800 秒过期，且六者都由 `ingest.py` 顶部常量单一来源生成报错文案（不再出现"文案说 20 张、代码卡 10 张"的漂移）。40MB 这条是按"峰值内存 ≈ 输入像素量"实测推出的：长边 ≤1600 的单张实测 666MB，而 10 张未缩放手机长截图在 RQ 队列里就是十份 bytes 常驻。
- **新增凭据的存放规则**：云函数 HTTP 触发用的 Bearer 凭据与微信 AppSecret 同级——**只进服务器 `.env`，绝不入库、绝不打进日志、验证脚本只打印"已配置/缺失/长度"**。它在后端与云函数之间是唯一一道门，泄露等于任何人可调用我们的混元额度（因此 R10 的计数义务同时是安全义务）
- 密钥治理：`.gitignore` 已覆盖 `.env`、`*.key`、`backend/keys/`；本轮额外修掉 `upload.sh` 会打包 `.env.bak*` 的泄漏面（提交 `7257868`）。**任何验证脚本只打印"已配置/缺失"，禁止输出明文。**
- **合规面因语音下线而缩小**：`app.json` 的 `permission.scope.record` 已删除、录音代码全清，**《隐私保护指引》不再需要申报"麦克风"权限**，只需覆盖相册（截图上传）。这是删除语音的一个附带收益。**v2.2 复核：换自建 OCR 不改变合规面**——图片仍在自己的服务器上处理，不外发第三方，因此不需要新增任何"第三方数据处理"申报条目。

**乙路线：官方文档已回答的部分（2026-09-19 晚间，微信 wxcloud + CloudBase 双侧文档核对）**

- **前提①已解决：云函数侧可以用这份免费额度。** 成长计划 AI 资源包的官方适用范围原文是"仅限微信小程序和云开发服务端中使用……云函数、云托管中使用 `wx-server-sdk`、`@cloudbase/node-sdk`"。云函数内调用链：`wx-server-sdk ≥ 4.0.1` → `cloud.init({env: cloud.DYNAMIC_CURRENT_ENV, timeout: 60000})` → `cloud.ai()` → `createModel(...)` → `generateText(...)`。
- **但有一条极易踩错的边界，它决定架构而非风格**：同一份规则写明"**第三方 API、直接 HTTP 调用等来源……系统将不再从成长计划免费额度中抵扣，改为从套餐额度中扣除**"。而 CloudBase 恰好提供 OpenAI 兼容端点 `https://{env}.api.tcloudbasegateway.com/v1/ai/cloudbase/chat/completions`。**如果我们的 FastAPI 直接打这个端点，10 亿 token 一分都省不到，还会长出账单。** 所以"混元调用必须发生在云函数内部"是额度生效的前提条件。
- **前提②部分解决**：HTTPS 触发云函数有两条路径，且**都不要求备案域名**——① 微信 `POST /tcb/invokecloudfunction`（`access_token` 鉴权，但文档标注**超时 5 秒**）；② CloudBase HTTP API `POST https://{env}.api.tcloudbasegateway.com/v1/functions/{name}` + `Authorization: Bearer <key>`。默认网关域名的说明是"生产环境建议绑定已备案自定义域名"，即默认域名本身可用。

**乙路线：仍未验证的四件事（写业务代码前必须实测，见 R2）**

1. **超时上限到底是 60s 还是 900s**：CloudBase FAQ 写"建议在云控制台调整，上限 60s"，CLI 配置文档写 `timeout` 取值 1–900 秒、默认 5，而 SDK 默认 15 秒且"两者以最短时间为准"。10–30 秒的提炼请求能否落地完全取决于此。
2. **本环境是否开放 HTTP 网关**：微信 wxcloud 文档目录里只有「HTTP 云函数」（且只服务小程序端 `wx.cloud.callHTTPFunction`，timeout 需 <1500ms），**没有「HTTP 网关」章节**；`api.tcloudbasegateway.com` 只出现在 CloudBase 文档。微信侧创建的环境是否支持，未证实。
3. **provider 与模型名**：文本模型二期文档只列 `hy3`，但 SDK 示例仍写 `hy3-preview`，且"需在控制台手动开启 hy3"；模型清单里**无 `hunyuan-large`**，`hunyuan-image` 旧模型已下线。以控制台「生文模型」实际开关为准。
4. **额度耗尽后的行为——已按用户决策定案**：2026-09-19 晚用户明确"**优先用混元，加一个兜底方案，业务量超了愿意付钱**"。因此 provider 取 `cloudbase`（免费额度优先，**耗尽后自动转扣套餐额度**），不取 `hunyuan-v3`（耗尽即报错）。**这条决策同时关闭了 v2.0 遗留的"是否允许静默转扣费"问题：允许。** 但可见性要求随之升级为必做——见 R10。
5. **出网优先级（v2.2 定案，只剩两级）**：**混元（云函数内）→ 失败则降级存原文、任务仍 `completed`**。**DeepSeek 不再是任何一级**——用户要求"只维护一家大模型"，且服务器 `DEEPSEEK_API_KEY` 从来是空的，删它不损失任何现有能力。第二级已实现并有测试（`add7eb0`），第一级待写。

任一实测不成立（尤其是第 1、2 条），**乙路线不会退化成"换一家模型"，而是退化成"提炼先不做"**：内容照常入库、摘要/要点/标签留空、UI 已 `wx:if` 隐藏不破版。这是 v2.2 与 v2.1 的关键区别——**"提炼能不能上"从此不再绑定"产品能不能用"**，所以第 1～3 条的实测是"增强功能何时上线"的前置，不是发布前置。真正卡发布只剩 R8（合法域名）一项。

### 8.8 把"读哪个 `.env`"从当前工作目录手里拿回来（2026-09-19 同日第四轮，✅ 本地已修 / ✅ 已随 v2.2 整批上线，见 §8.10）

§8.7 记的那次事故不是"手滑跑错目录"就完事的：跑错目录是引信，**能炸是因为我们的配置装载方式本身把密钥查找交给了 CWD**。这一轮修的是引信本身。

**出事要同时满足两个条件，我们两个都有**：
1. `env_file=".env"` 是相对路径 → pydantic-settings 按**当前工作目录**解析它。从 `/home/ubuntu` 启动的任何进程（临时脚本、以后加的 cron、调试时手敲的 `python -c`）读到的都是**别人的** `.env`。

**外泄面到底有多大（先量再定性）**：这条路径不经过任何 `HTTPException.detail`，小程序端拿不到；`journalctl -u wtsj-api -u wtsj-worker | grep -cE 'WECHAT_PAY|SESSION_SIGNING|extra_forbidden'` 在服务器上是 **0**——journal 里那几条命中是 `sudo` 的 COMMAND 审计行，属于别的项目、日期是 9 月 6/10 日。所以已发生的泄露范围就是**我那次终端输出**（也就是这份会话记录），不是"线上在往外吐"。**对方那个文件一个字节都没动**：`/home/ubuntu/.env` 是 `root:root 644`、1461 字节、9 月 14 日，被同机的 `watermark-image-api` 容器经 `docker-compose.yml` 的 `env_file: .env` 在用，挪走或改名会把**别的项目**搞挂。它 644 全局可读是别人的卫生问题，不在本轮授权范围。

- 断言 `env_file` 是绝对路径、等于 `PROJECT_ROOT/.env`、且 `PROJECT_ROOT/app/main.py` 确实存在（防止 `parents[2]` 数错层数——数错了会安静地指向别处）
