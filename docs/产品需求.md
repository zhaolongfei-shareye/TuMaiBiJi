## 1. Summary（60 秒版）

图麦笔记是一个装在微信里的**个人闪记库**：用户在微信里读到一篇公众号文章、截了一张图、或口述一段想法，粘贴/上传后系统自动把内容采集下来并存进自己的笔记库，可选地用 LLM 提炼成"标题 + 摘要 + 要点 + 标签"，最终能一键生成带小程序码的分享图回流到微信群。给谁用：**日常在微信内完成阅读与记录、但被"收藏夹存了就死"困扰的重度信息摄入者**。为什么是现在：微信 OCR/ASR 云产品有个人可用的免费额度、DeepSeek 类 LLM 的单篇成本已降到可忽略、且服务器与域名主体已就绪，四件事同时成立的时间窗口刚刚打开。成功长什么样（工程侧可测版本）：**用户从"粘贴一个链接"到"在笔记列表看到这条笔记"的端到端成功率 ≥ 99%，且该链路不依赖任何单一外部服务存活**——这一条正是当前实现尚不满足、本 PRD 列为 P0 的核心改造点。

## 2. Background & Problem

### 2.1 问题（用户视角）

用户在微信里产生的"值得记的东西"散落在四个地方：公众号文章、群聊/朋友圈截图、语音消息、临时冒出来的一句话。今天把它们留住的手段，没有一个能同时做到"留下原文"和"留下结构"。

### 2.2 当前 workaround 与不足

| 现有做法 | 不足 |
|---|---|
| 微信「收藏」 | 只做存储，无摘要、无标签、无要点；收藏多了等同于没有 |
| 微信「浮窗」 | 上限 14 条，是"稍后读"不是"记得住" |
| 转发给「文件传输助手」 | 时间线淹没，不可检索、不可分类 |
| Flomo / Cubox 等外部笔记 | 跳出微信闭环；截图与语音要手动二次搬运 |

### 2.3 为什么是现在

来自 `sonus-evaluation-report.md` 第 89-105 行的调研结论，加上本轮实测：

- 腾讯云 OCR 每月 1000 次免费，个人自用足够（实测端点从服务器可达，HTTP 200）
- DeepSeek 按 token 计价，单篇提炼成本可忽略（实测端点可达，HTTP 401，仅缺 key）
- 个人小程序**无法使用 `web-view`**（微信规则，报告第 163 行已核对），因此"原生小程序 + 自建后端"不是可选项而是唯一路径
- 服务器、域名、HTTPS、systemd 托管、CI 化的部署脚本均已就绪（本轮已把部署改造为 systemd 托管并修掉假阳性）

### 2.4 本版故意不解决什么

- **不做视频链接解析**（B 站 / 视频号 / 抖音 / 小红书）。报告第 161 行实测结论：视频号 URL 匿名抓取只能拿到空壳页面（无 og:title / description），必须带登录态；这不是产品问题而是合规与对抗成本问题，整体推到 Phase 2 之后。
- **不做协作与内容分发**。本产品是个人库，分享图只是回流手段，不做 feed、不做关注、不做公开主页。

## 3. Personas & User Segments ⚠️薄

> ⚠️ 本节**无用户研究支撑**，是从 `pages/create/create.wxml` 的四个真实入口和 README 定位反推出来的工作假设。上线前应用真机访谈校正，不要当成已验证结论。

**Primary persona（工作假设）**

```
姓名：微信重度阅读者
身份：信息摄入多于信息生产的个人用户（产品/研究/媒体/学生均可能）
情境：一天里在公众号、群聊、朋友圈之间连续切换，反复遇到"这个要记下来"
JTBD：当我在微信里读到/看到/听到值得留存的内容，我想在 10 秒内把它变成一条
      可检索、有结构的笔记，从而之后能真正找回并用上，而不是躺在收藏夹里。
当前 workaround：收藏 + 浮窗 + 转发文件传输助手（见 2.2）
痛点：存进去就再也找不到；截图里的文字搜不到；语音完全无法沉淀
```

**这个产品不为谁做**：不为需要多人共享知识库、需要权限管理、或想把笔记当博客公开发布的团队用户做。

## 4. Goals & Success Metrics ⚠️薄

> ⚠️ 业务 KPI（留存、日活、人均笔记数）**本轮无数据来源，不编造**。以下只列工程侧此刻就可度量的验收指标，业务指标待产品上线后由用户定义。

**产品目标（一句话，outcome-framed）**：让"在微信里遇到值得记的东西"到"它变成一条找得回来的笔记"之间的时间压到 10 秒以内，且不要求用户离开微信。

### 4.1 工程验收度量（今天就能测）

| 指标 | 度量什么行为 | 目标值 | 时间窗 | 当前实测 |
|---|---|---|---|---|
| 零凭据功能面可用性 | 笔记 CRUD/分类/分享/偏好在无第三方 key 下全通 | 100% | 每次部署 | ✅ 19/19 通过（2026-09-19） |
| 微信登录凭据有效性 | 服务端到微信的凭据握手 | 通过 | 每次部署 | ✅ 40029（凭据被接受） |
| 小程序码生成 | 真实拉取微信 getUnlimited 并出图 | 200 + 有效图片 | 每次部署 | ✅ 55,802 字节真实图 |
| URL 采集成功率 | 粘贴链接→取到正文 | ≥ 95%（国内站点） | 上线后 30 天 | ✅ 抽样 4/4 命中（微信文档/sqlite/36kr/公众号） |
| **单点故障降级能力** | LLM 不可用时链路是否仍交付笔记 | **必须能交付** | — | ❌ **当前不能，本 PRD 的 P0** |
| 服务重启真实性 | MainPID 变化 + 无孤儿进程 | 强制断言 | 每次部署 | ✅ 已改为 systemd 断言 |

### 4.2 Anti-metrics（明确不优化）

- **不优化"笔记总量"**。以条数为 KPI 会诱导把低价值内容自动灌进库里，直接摧毁"知识库"的可检索性——这是本产品自我毁灭型指标。
- **不优化摘要长度或要点数量**。LLM 提示词已限定 3-8 要点 / 3-6 标签，扩大只会增加 token 成本，不增加价值。
- **不做已读/打开率类engagement 指标**。这类指标与"帮用户记住"无因果关系，优化它必然走向通知骚扰。

### 4.3 关键假设（错了就做错产品）

> **"用户愿意为一条内容接受机器提炼的结构，而不是自己写。"**

本轮实测已经**部分证伪了这个假设的必要性**：`pages/detail/detail.wxml` 第 29/35/46 行对摘要、要点、标签三块全部写了 `wx:if`，`pages/write/write.wxml` 第 16/29/40 行则给用户提供了这三个字段的**手动输入框**。也就是说 LLM 在数据模型上不是必需字段的生产者，只是自动填表器。**若假设不成立，产品退化为"微信内剪藏器 + 手动结构化笔记"仍然可用**——这正是第 8 段把 LLM 降级路径列为主路径超集的原因。

## 5. Value Proposition

**对主用户**：

> "微信重度阅读者终于可以**在微信里用 10 秒把一篇公众号文章/一张截图/一段语音变成一条有标题、能搜到、能分享的笔记**，而不必**手动复制粘贴、跳出微信、或在收藏夹里重新翻找**，因为图麦笔记把采集（抓取/OCR/ASR）、结构化提炼、和微信原生的分享回流做在了同一个小程序闭环里。"

**竞争差异化**（对照微信收藏 / Flomo / Cubox）：

- 对手的共同空白是**"输入端"和"回流端"分属两个生态**。微信收藏有输入无结构；Flomo/Cubox 有结构但拿不到微信内的截图与语音，且分享出去的图不会带小程序码回流。
- 本产品填的是**两端都在微信内**这个空白：入口是微信原生能力（相册、录音、分享链接），出口是带小程序码的分享图（已实测可用）。
- 差异化不来自"更好的 UX"这类空话，来自**个人小程序无法用 web-view 这一硬约束下的原生闭环取舍**（报告第 163 行）。

⚠️ 竞品对比未做系统化调研，上述判断来自 `sonus-evaluation-report.md` 的零散核对，Section 5 整体评级 moderate。

### 6.1 依赖矩阵（本 PRD 的决策核心）

**这是全部功能与外部依赖的真实映射，逐条实测于 2026-09-19。**

| 功能 | 依赖 | 缺凭据后果 | 实测状态 |
|---|---|---|---|
| 微信登录、笔记库、分类、分享、小程序码、壁纸、语言 | 仅基础设施 | **无** | ✅ 19/19 通过（服务器 `DEEPSEEK_API_KEY` 当时为空） |
| URL 采集正文 | httpx + trafilatura，无 key | 无 | ✅ sqlite.org 取到 7,406 字正文 |
| 截图 OCR | 腾讯云 OCR（2 字段） | 截图链路不可用 | ⛔ 缺 key（端点可达 200） |
| 语音 ASR | 腾讯云 ASR（2 字段） | 语音链路不可用 | ⛔ 缺 key（端点可达 200） |
| **结构化提炼** | **DeepSeek（1 字段）** | **三条 ingest 全部标 failed** | ⛔ 缺 key（端点可达 401） |
| 资产上传 COS | 腾讯云 COS（4 字段） | **无任何影响** | ⚠️ 死代码，建议删除 |

**DeepSeek 的真实作用面，全项目只有 3 个调用点**：`app/tasks/ingest_tasks.py` 第 26、62、97 行，全部位于"采集完成之后"。没有任何自动归类、语义搜索、问答功能使用 LLM。

它产出 4 个字段，其中只有 3 个是 LLM 专属：

| Note 字段 | 唯一来源 | 无 LLM 时 |
|---|---|---|
| `original_content` | 爬虫 / OCR / ASR | ✅ 不受影响 |
| `title` | URL 链路：爬虫已给（`scraper.py:137-149` og:title / h1 / "网页摘录"） | ✅ URL 可用；截图与语音为空 |
| `summary` `key_points` `tags` | 只有 LLM | 空（UI 已 `wx:if` 隐藏，不破版） |

**结论：除"自动提炼"这一个动作之外，MVP 没有任何功能依赖 DeepSeek。**

> ⚠️ **但有一个例外 coupling，实测于 `app/api/routes/notes.py:87-88`**：搜索条件只覆盖 `Note.title` 和 `Note.summary`，**不搜 `content` / `original_content`**。而 `summary` 是 LLM 专属字段——所以**一旦没有 DeepSeek，自动入库的笔记就只有标题可搜**，"知识库找得回来"这个核心价值直接塌掉。
> 这修正了"无 LLM 只是少几个卡片、不影响功能"的初判：**界面上不破，检索上会废**。
> 修法很便宜（把 `original_content` 纳入搜索列），且不依赖任何凭据，已列入 §8.1 第 1 步。代价是 SQLite 对大文本列做 `LIKE` 无索引即全表扫描——MVP 量级（笔记数千条以内）完全可接受，规模化再上 FTS5。

### 6.2 功能块逐个交付定义

---

#### F1 微信登录与用户隔离 —— P0 ✅ 已验证

**功能描述**：小程序 `wx.login` 拿 code，后端换 openid 并签发 JWT；客户端全程不见 openid。

**In Scope**：code2session、JWT（HS256，7 天，`sub/exp/jti` 强制校验）、`JWT_SECRET_KEY` 缺失时启动即失败。
**Out of Scope**：刷新 token、多设备会话管理、账号注销流程。

**验收标准**：
- Given 有效 code，When 调 `POST /api/auth/wechat`，Then 返回 JWT 且响应体内不含 openid
- Given 无 Authorization，When 调 `GET /api/notes/`，Then 401「缺少认证凭证，请重新登录」（✅ 实测 401）
- Given 垃圾 Bearer token，When 调任意鉴权接口，Then 401（✅ 实测 401）
- Given 用户 A 的 token，When 访问用户 B 的 note_id，Then 404（✅ 实测 404）
- 边缘：`JWT_SECRET_KEY` 为空或为公开占位符 → 服务启动失败，不得静默降级（`config.py:22-30`）

**设计触点**：`miniprogram/app.js:45`（启动即登录）、`backend/app/core/auth.py:42-52`
**证据**：2026-09-19 从服务器调用 `jscode2session` 返回 **40029 invalid code**（而非 40013 invalid appid），证明 AppID+AppSecret 已被微信接受。

#### F2 笔记库：列表 / 搜索 / 置顶 / 删除 —— P0 ✅ 接口已验证 / ⚠️ 检索覆盖有缺陷

**In Scope**：分页列表、关键词搜索、置顶、软删除、分类归属。
**Out of Scope**：语义搜索、批量操作、回收站。
**验收标准**：
- Given 已登录，When `GET /api/notes/`，Then 200 且只含本人笔记（⚠️ 代码层 `notes.py:80` 已按 `user_id` 过滤，但**运行时未真正验证**：库中仅 1 个用户，无法构造真实越权样本；上线前需造第二个测试账号复测）
- **Given 一条 `summary` 为空但正文含关键词的笔记（即 LLM 降级产物），When 用该关键词搜索，Then 必须命中**（当前 ❌ 不满足，`notes.py:87-88` 只搜 title+summary）
- Given 搜索串含 `%` 或 `_`，When 搜索，Then 按字面量匹配不被当通配符（✅ 已有 escape）
- 边缘：空库时列表页需有空状态文案（不得白屏）

**设计触点**：`pages/index/index.wxml:59-61`（摘要与标签块按字段存在性渲染）、`pages/detail/detail.wxml:24-65`
**证据**：`GET/POST/PUT/DELETE /api/notes/` 与 `?q=` 均实测返回 200。**注意 200 只证明接口不报错，不证明检索命中**——命中能力见上条 ⚠️。

#### F3 手写笔记 —— P0 ✅ 已验证

**功能描述**：用户自己填标题、摘要、要点、标签、正文、分类。
**关键设计事实**：这三个"LLM 字段"本来就提供了手动输入框（`pages/write/write.wxml:16 / 29 / 40-43`），因此**它们在数据契约上不是 LLM 专属**，这是 F6 降级方案成立的前提。

#### F4 分享图 + 小程序码 —— P0 ✅ 已验证，含 2 个已知缺陷

**功能描述**：Canvas 绘制笔记卡片图（750×1200），底部嵌小程序码，用户保存到相册后回流微信群。

**In Scope**：分享链接创建、落地页、Canvas 出图、真实小程序码。
**Out of Scope**：自定义模板、多图分享。

**验收标准**：
- Given 有笔记，When `POST /api/shares/`，Then 返回 token（✅）
- Given token，When `GET /api/shares/{token}/qrcode`，Then 200 + 有效图片（✅ 55,802 字节 / 280×280）
- **⚠️ 缺陷 A（本轮新发现，P1）**：`pages/share/share.js` 的卡片三段内容用**绝对坐标**（摘要 `cardY+180`、要点 `cardY+380`、标签 `cardY+620`，第 110/122/137 行），而画布与卡片高度固定（`share.js:60-84`，750×1200 / cardH=1040）。**LLM 字段为空时版面不会收缩，会输出大片空白的分享卡**。这会让"无 DeepSeek 的 MVP"在增长环节上直接可用但观感很差。必须改为按实际内容累加 y。
- **⚠️ 缺陷 B（P3，暂不改）**：接口声明 `content-type: image/png`，实际字节是 **JPEG**（微信 getUnlimited 行为）。渲染靠内容嗅探故显示正常，若未来做格式校验会踩。

**设计触点**：`pages/share/share.js:60-150`、`backend/app/api/routes/shares.py:91-101`、`app/services/wechat.py:16-40`

#### F6 URL 剪藏 —— P0（**MVP 主力，可零凭据交付**）

**功能描述**：粘贴公众号/网页链接 → 后台抓取正文 → 入库。

**In Scope（本版）**：
- 采集：`scraper.py` 已实现 SSRF 防护（`BLOCKED_NETWORKS`，第 41-42 行）与公众号专用解析（第 116-134 行）
- **提炼改为「可选 + 自动降级」**：LLM 可用则填 title/summary/key_points/tags；LLM 不可用（缺 key / 超时 / 429 / 5xx / 返回非 JSON）则**退回爬虫 title + 原文入库，任务状态仍为 `completed`**
- 异步：RQ 队列 + 任务状态轮询（`/api/tasks/{id}`）

**Out of Scope**：视频站点、需登录态站点、正文图片本地化、多页抓取。

**验收标准（本轮改造的核心）**：
- Given 未配置 `DEEPSEEK_API_KEY`，When 提交一个可抓取的 URL，Then 任务最终 `completed`，笔记含标题与原文，摘要/要点/标签为空且 UI 不渲染对应区块
- Given LLM 返回 HTTP 429，When 重试 3 次（退避 1/2/4 秒，`llm.py:12-13`）后仍失败，Then **降级入库而不是 `failed`**
- Given 抓取失败或正文为空，When 提交，Then 任务 `failed` 且 error 文案可展示（非堆栈）
- Given SSRF 目标为内网地址，When 提交，Then 拒绝
- 边缘：正文超 50,000 字截断（现有逻辑），LLM 输入超 12,000 字截断（`llm.py:41-42`）

**待澄清**：国内服务器出海受限——`en.wikipedia.org` 实测 `ConnectTimeout`，而微信文档 / 36kr / 公众号 / sqlite.org 均可抓。**是否需要支持海外站点是一个产品决策，若需要则须换地域或加代理。**

---

#### F7 截图转笔记 —— P1（缺 2 个 key）

**依赖 DeepSeek 的价值：高**——OCR 输出是无视觉层级的碎行文本，且**完全没有标题**，没有 LLM 就是一条无名笔记。
**In Scope**：多图批量（上限 20 张 / 单张 10MB / 批次 TTL 30 分钟，`ingest.py` 常量）、两步式 stage→process、OCR、可选提炼。
**Out of Scope**：表格重建、手写识别调优、版面还原。
**⚠️ 已知风险 P1-1**：为消除"worker 与 API 主机文件系统耦合"，本轮已改为把图片 bytes 直接放内存 `_batch_staging` 并 pickle 进单条 Redis job。**在 3.7GB（可用 1.9GB）单机 + Redis `maxmemory=0` 的前提下，一批最多 200MB 常驻 1800 秒，是把路径耦合换成了 OOM 风险。** 因 COS 已判定为死代码，"传 object_key"这条路被堵，**只剩 A（回退落盘）或 C（收紧张数/TTL/总字节上限）二选一**。若 MVP 采纳 S0/S1（截图入口隐藏），此项风险自动归零。

---

#### F8 语音转笔记 —— P2（缺 2 个 key）

**依赖 DeepSeek 的价值：高**（同 F7，ASR 只给连续文本无标题）。
**⚠️ 未评估项**：`SentenceRecognition` 有 **60 秒**上限，长语音需换录音文件识别接口。当前代码未见分片或时长校验，**上线前必须实测确认**，否则用户录 2 分钟会得到静默截断或失败。
**前端**：录音 UI 已在 `pages/create/create.wxml:24-40`（含 recorder 与取消），无需重做。

#### F9 资产存储 COS —— **建议整块删除（死代码）**

**证据**：后端有完整实现（`app/services/storage.py` 三个函数 + `app/api/routes/assets.py` 两条路由），但 `miniprogram/utils/api.js` 全文**没有任何一处调用 `/api/assets/`**——前端零调用。
**建议**：删除路由 + service + `requirements.txt` 的 `cos-python-sdk-v5`，并从配置里去掉 4 个 `COS_*` 字段。收益：少申请一个云产品、少一份存储与流量费、少 4 个待填字段、F7 的 P1-1 决策空间清晰化（只剩 A/C）。
**保留理由**：若未来做"笔记内插图"，COS 是既定方案。**折中：不进 MVP，代码保留但从配置面移除，避免误导外部审查者以为 COS 是必需依赖。**

## 7. Constraints & Risks

### 7.1 技术约束（实测）

| 约束 | 事实 | 影响 |
|---|---|---|
| 单机资源 | 内存 3,719MB，可用约 1,992MB | 大文件批处理不得常驻内存（F7 P1-1） |
| 出网受限 | 海外站点超时，国内站点全通 | URL 剪藏范围受限，需产品决策 |
| 个人小程序 | 无法使用 `web-view` | 必须原生实现，无 H5 兜底 |
| 小程序不走 CORS | 客户端无同源策略 | `CORS_ORIGINS` 留空即可，不要为"测试方便"开 `*` |
| 数据库实况 | `DATABASE_URL` 指向 **SQLite**，PostgreSQL 迁移从未生效（表内仅 users=1/notes=1/shares=2 测试数据） | MVP 阶段 SQLite 够用；历史"已迁移"记录作废 |
| ASR 接口 | `SentenceRecognition` 60 秒上限 | F8 长语音不可用 |
| 部署 | 服务器无 git，`upload.sh` 打包 → `deploy.sh` systemd 重启 | 禁止回退到 `pkill`+`nohup`（曾导致 5,966 次崩溃重启） |
| 密钥 | 仅 `JWT_SECRET_KEY` 有 fail-fast，其余第三方 key 默认 `""` | **应用可在核心功能全废的状态下"健康启动"** —— 这是本轮假阳性的根因 |

### 7.2 数据与隐私

- **openid 绝不下发给客户端**（已实现，用 JWT `sub` 承载内部 user id）
- 上传的图片/语音仅用于当次 OCR/ASR，当前为内存传递、进程重启即消失；**不落盘**（P1-3 重构结果）
- 密钥治理：`.gitignore` 已覆盖 `.env`、`*.key`、`backend/keys/`；本轮额外修掉 `upload.sh` 会打包 `.env.bak*` 的泄漏面（提交 `7257868`）。**任何验证脚本只打印"已配置/缺失"，禁止输出明文。**
- 合规：需补《隐私保护指引》——涉及相册、麦克风权限，提审必查（当前未确认是否已填）

### 7.3 关键风险

| 风险 | 可能性 | 影响 | 缓解措施 |
|---|---|---|---|
| **DeepSeek 单点：缺 key / 欠费 / 429 → 三条链路全 `failed`，用户连原文都存不下**（`llm.py:37-38` 直接 raise） | High | High | **P0，不依赖凭据，立即可做**：F6 的降级路径 + 把 key 缺失从"运行时抛错"改成"启动时自检并明确告警" |
| **搜索不覆盖正文，只搜 title+summary**（`notes.py:87-88`）→ 无 LLM 时自动入库的笔记实际只能按标题找 | High | **High**（直接削弱"知识库"核心卖点） | 把 `original_content` 纳入搜索列（不依赖凭据）；规模化再上 FTS5 |
| 分享卡在 LLM 字段为空时输出大片空白 | High | Medium（伤增长） | F4 缺陷 A 改为内容驱动布局 |
| F7 内存批处理导致 OOM | Medium | High | 决策 A 或 C；或 MVP 阶段隐藏截图入口使风险归零 |
| 服务器出海受限导致部分 URL 抓不到 | 已发生 | Medium | 明确"仅支持境内可直连站点"，抓取失败给可读文案；或换地域 |

- **上线后头两周监测**：任务 `failed` 率、failed 原因分布（区分"抓取失败"与"提炼失败"，第 1 步后提炼失败不应再产生 failed）、分享图生成次数与回流打开次数
