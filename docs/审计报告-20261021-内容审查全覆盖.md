# 内容审查全覆盖审计（2026-10-21 夜）

站长原话：**「代码全量审计，排查有没有漏的内容审查，任何图文都要」**。
这一份是审计报告，**代码一行没改、现网零写、没出包、没提审**。出网只打了四次微信的接口（§三 的读数），不碰我们自己的库。

## 一、三句结论

1. **文字这一半站得住**：全仓六个送检**调用点**（表1 那七行是把 `notes` 的"写入／编辑／有活码时刷新快照"三刻拆开列的），凡是**会出现在公开页上**的每一栏，都在"写入刻"或"建分享刻"这两个时刻之一被检过——没有"公开面上一栏字没检"这种洞了。
2. **图片这一半是零**：八条图片入站路径（§二 表2）**没有任何一条做过内容检查**，现有的闸全是形状（MIME／magic bytes／字节上限／边长／`cloud://` 前缀）。其中**五条服务端握着字节**（当场就能检），**三条是客户端直传云开发存储**（服务端从不经手字节，要先绕一步才检得到）。
3. **推翻一条抄了十几处的断言**：代码注释和文档到处写着「图片侧的 imgSecCheck 个人主体拿不到」。今晚实测——**两条图片接口都调得通**（§三）。但同时拿到一句更难听的实话：**接口调得通 ≠ 判得出来**，我们把已知违规文字画成图送过去，微信回的是 `pass`（§四）。所以我们唯一**能自证有效**的图片审查路是：**自家 OCR 取字 → 现有的 msgSecCheck 判**（§五 甲档），这一条今晚已经端到端量通。

用的就是我们自己的 `backend/.env` 凭据与现成的取 token 那条链（`wechat.py` 的 `_access_token_sync`，`get_access_token()` 的同步孪生）。

## 四、不许说反的六条（能力边界）

1. **不许说"图片检测接上就能拦违规图"**。今晚只证到"接口调得通、且在解析字节"；唯一一次带已知风险的探针（图上赌博文字）**它没判出来**。要证"判得出"需要一张已知违规的图作对照样本，我们没有、也不该自己造。
2. **不许说"imgSecCheck 个人主体拿不到"**——已被实测推翻。仓里那十几处要逐个更正（§七 名单）。
3. **不许说"客户端直传那三条图也能顺手检"**。服务端不经手字节，要么后端回头把字节捞回来（多一跳、要压到 <1MB 才喂得了同步接口），要么走异步 URL 那条（要配消息推送）。
4. **`/ops` 与帮助文档那几栏不检，是选择不是漏**：写它的人要先过管理口令，不在"坏人"那条链上。但要说清一句实话：这几栏**下发给所有用户**，所以口令一旦泄露，那几栏就是一条不经内容安全的公开路。
5. **`unavailable` 一律放行**这条口径没变（微信侧抖动不该变成"存不了笔记"）。代价照旧：额度打光＝当天检查看作没做。前提已翻正——小程序已上线，口径升到 **4000 次/分钟、2,000,000 次/天**（文字），异步图片那条官方给的是 **2000 次/分钟、200,000 次/天、单文件 <10MB**；`deploy.sh` 那句"用的是 100 次/天额度里的 2 次"字面已过时，本轮**没动**。
6. **卡片成品那张 PNG 是客户端画完直接出去的**，服务端只登记 fileID ⇒ 图上那几栏文字因为来自笔记栏而被检过，**图本身从没被检过**（表2 #2）。
