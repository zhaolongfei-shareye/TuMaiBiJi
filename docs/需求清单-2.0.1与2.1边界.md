# 下一版需求清单（2.0.1）与 2.1 的边界

写于 2026-10-08。**这份只是需求与范围，等站长拍定才开工——目前代码一行没为 2.0.1 动过**（今天已提交的 `934119c` 是"邮箱那一格"与那条隐私口径，两件事都已拍过）。

站长 10-08 的原话定了这条文档的写法：「我还是不清楚你下个版本做什么，清楚列出来，包括怎么处理丢卡片的事，因为如果因为版本更新，影响现网用户使用，这是很严重的问题，必须解决。」

## 一、先把"丢卡片"这件事说准：不是这次更新删掉的，但这次更新让它更容易发生

**证据（都是今天现读的，不是推断）**

- 卡片留档 100% 在本机，两样东西：账在 `wx.setStorageSync('cardLog')`，图在 `${wx.env.USER_DATA_PATH}/cards/{noteId}-{tplId}-{时间戳}.jpg`（`miniprogram/utils/cardLog.js:20-21`、`:42`）。
- 服务端**从来没存过一张成品卡片图**。后端全仓只有一个相关列：`shares.cover_asset_id`（`backend/app/models/share.py:34`），那是扫码落地页的封面，不是卡片成品图。`note_cards` 这样的表在整个仓库零命中。
- 所以：换手机、删过小程序、微信「清理缓存」、系统把私有目录清掉，这一格必然回到"没生成过"。这是 10-03 定本机方案时就写死的代价（`cardLog.js:9-10` 那段注释原话："换设备、清微信缓存、删掉小程序，这一格就空了"）。
- **2.0 没有把判据改严**：那条"图不在就不列"的规则 1.9.29 就在首页（`git show master:miniprogram/pages/index/index.js` 第 318-326 行的 `_cardsOf`），2.0 只是把它搬进 `cardLog.aliveFor` 让三处共用。`git diff master...release/2.0 -- miniprogram/utils/cardLog.js` 只有 **+21 行**，全是那个新函数与注释；存储键名（`cardLog`）、目录（`USER_DATA_PATH/cards`）、文件名格式、那两次一次性归一的开关位（`cardLogKeepOnly` / `cardLogOnePerNote`）**一个都没改**。2.0 的"与旧版隔离"是**分支隔离**（同一个 AppID、同一份本机存储），不是数据隔离。
- 那两次"进页就清账"的一次性归一只在**从 1.9.12 及更早直接跳上来**那一次生效（`cardLog.js:100-127`，靠 flag 挡着）。你手机上 10-03 就在跑 1.9.13+，基本排除这一条。

**这条我还没量，但它最可能解释"为什么偏偏是现在"**：本机私有目录合计上限 10MB（`docs/后台隐私指引-填写文案.md` 里"分享形象头像"那处也写着这个数），而 2.0 这版往本机多写了东西（首页背景、外观那两枚壁纸、模板小样、以及随笔记保存的压缩图副本）。**目录越满，系统越可能先清掉旧的卡片图**——账还留着、图被清走，界面就显示"没生成过"。这个数我今天没量出来，2.0.1 开工第一件事就是量它（见下面 §三第 0 步），量不出来我不许自己写结论。

**没有全丢的那一半**（这条要说给你放心）：服务器知道"哪一篇曾经公开过"。现网库只读查回来的实据：`shares` 共 20 条、其中 15 条活动；你名下（`user_id=3`）13 条、其中 12 条活动。详情页那一行「已公开，扫码能看」是服务端驱动的（`pages/detail/detail.js:194-195` 现调 `api.getShareStatus`）。**已经发出去的码和落地页扫得开**，丢的是那一张成品图与"这篇生成过卡片"那一格。

## 二、2.0.1 的正面清单（我建议就一条真功能 + 四条搭车件）

### 第 1 条（核心，唯一需要设计的新功能）：卡片留档从"本机"改成"服务端 + 云存储"

**问题**：见上面第一节。

**我的建议（四步，都复用已经上线的东西，不新开基础件）**

1. **生成卡片那一刻就上传**：走 10-07 已经上现网的那条图片直传链（`utils/cloudUpload.js` 压缩直传 + `assets` 表 + `POST /api/notes/{id}/assets`，现网探针 41/41）。服务端新增一张 `note_cards`：`note_id / object_key / tpl / no_qr / created_at`。**一篇仍只留一张**（10-03 你定的那条硬规则不变，要改存量必须先删旧的那张）。
2. **三处判据改吃服务端**：列表那一格、详情页右上那一格、笔记卡片页「一篇只留一张」那道闸（`share.js:74`），从"本机文件在不在"改成"服务端有没有那一行"；本机文件降级成缓存——有就直接画（快），没有就从云存储取。这样更新包、清缓存、换手机都不再影响它。
3. **存量补传（一次性）**：第一次进「我的 → 笔记卡片」时，把**本机图还在**的那批一次性补传上去，立个 flag 不再重复跑。图已经没了的那些**界面上明写**："这一篇的卡片图已不在这台手机上，重新生成会出一张新的"——不假装能救回来，也不让它看起来像我们弄丢了数据。
4. **删除连带**：删那篇、或注销账号时，卡片对象一起删。复用今天刚补好的那条待删队列（`utils/assetPurge.js`：失败落账、每次进前台补删、注销故意不清）。

**做了的好处**：这一格从此与"这台手机"无关，跨端那条（2.1 要的数据迁移）自动带上卡片；"卡片不见了"这类问题一次解决到根，而且**服务端有账可查**——再出现类似投诉，我能拿现网读数证明不是我们删的。

**不做的最坏情况**（具体到谁、哪条功能）：每一次微信清缓存 / 删小程序重装 / 换手机，现网用户都会再看到一次"我生成过的卡片没了"；卡片是这产品对外的**成果物**（要发朋友圈、要印出去的那张图），丢了等于让人重做一次工作，而且是**静默地丢**——界面上不报错、不留痕。这一条已经在你自己手机上发生过一次；如果用户遇到同样的事，这是差评、投诉、直接注销的触发点，而我们手上**没有任何服务端证据**能自证清白（因为图本来就没上过服务器）。

**代价（能确定的写在下面；没量的明确标出来）**

- 服务端要加表、加接口、跑迁移、部署（这几步要你点头，我不会自己上现网）。
- **配额这条必须先量后定**：一张卡片成品图实际多少字节我今天没测（`cardLog` 那趟是 `canvasToTempFilePath` 出的 jpg）。云存储那 5GB 是**全站共用的池子**（不是每人 5GB，`pages/me/me.js:10-13` 那条注释写着的就是这个口径），所以"卡片也上云"要先把每张的实际字节量出来，再决定要不要给卡片单设一档更小的尺寸——**这条我没量过，2.0.1 第 0 步就是量它**。
- 界面那三处判据一起改，所以要新增一把真跑尺子（"退出去再进、换一台设备，卡片还在不在"），不能再依赖本机文件当判据。
- 法律文本要跟着改：卡片图也是"用户上传的图片存到云开发对象存储"，已生效那份《用户隐私保护指引》里"相册（读取）"那格的用途说明要覆盖它（10-07 那版只写了笔记配图，没写卡片成品图）。

## 三、2.0.1 的开工顺序（拍定之后才动）

0. **先量两个数，量不出来不写代码**：① 一张卡片成品图的实际字节；② 本机私有目录现在被什么占着、离 10MB 还有多远（`wx.getFileSystemInfo`）。这两个数决定第 1 条要不要给卡片单设一档尺寸。
1. 服务端 `note_cards` + 三个口的改动 + 迁移 + 用例（本机跑，不动现网）。
2. 前端：生成即上传、三处判据改吃服务端、一次性补传、"图不在这台手机上"那一态的文案。
3. 尺子：新增"卡片读得回来不依赖本机文件"的真跑一把；把现有那三处依赖本机的判据改口径（**红了先问前提还在不在**，别拿旧尺子当真相）。
4. 部署（等你点头）→ 现网探针 → 后台指引那一版重交（等你点头）→ 出包提审。

**验收怎么算过**：给一篇笔记生成卡片 → 把小程序从后台划掉、在微信「我 → 小程序」里清一次缓存（或换一台设备登录同一个微信）→ 再进这篇，那一格**还能看到同一张卡片**。这一条过了才叫解决；只看"我这边模拟器画得出来"不算。

## 四、2.1 的边界（这次不展开，等你拍范围）

大版本那三件你 10-08 晚上提过：**新 UI 改造、跨端、数据迁移（想用私密密码那条来实现）**。它与 2.0.1 的关系我先把话放这儿：第 1 条做完之后，"跨端"才有一块可迁移的东西（卡片与笔记都在服务端了）；而"用密码实现迁移"那条有个硬约束我今晚查实了——库里存的是**6 位数字密码的无盐 sha256**（`backend/app/api/routes/user.py` 的 `_hash_pin`：`hashlib.sha256(pin.encode()).hexdigest()`，没盐没迭代），它既不能当账号凭据、也不能拿来派生加密密钥。所以 2.1 那条要单独出一份技术方案，我不会把它和 2.0.1 挤一批。

## 五、需要你拍的三件（每件都写了我建议哪个）

**① 卡片上服务端这条，放 2.0.1 还是等 2.1？**
我建议：**放 2.0.1，而且它是那一版唯一的真功能**。理由：现网用户正在受影响，且这条不是"体验优化"而是"成果物静默丢失"。
好处：一次做到根，跨端那块顺带解决一半。
代价／不做的最坏情况：2.0.1 会比"只把邮箱搭上去"晚几天；拖着不做的最坏情况就是上面第三节那段——下一次微信清缓存再复现一次，而且我们依旧拿不出服务端证据。

**② 存量卡片（升级前生成过的那些）要不要一次性补传？**
我建议：**要**（本机图还在的那些才补得上，一次 flag 不重复跑；图没了的界面明说）。
好处：老用户升级完就能看到自己的历史卡片回来，"必须解决"这句话才算真解决。
不做的最坏情况：只保证"以后不再丢"，但**已经丢的那些永远显示"没生成过"**——在老用户眼里这就是数据丢失，而且他们分不清是系统清的还是我们删的。

**③ 2.0.0 先发，还是压住不发、把这批并进 2.0.1 一次过？**
我建议：**先发**。它已经过审，当天就能被真用户用到；不发这个审白过一遍（1-7 天的排队成本）。
代价：发出去这几天里"卡片不见了"仍会发生。
但要说清这条安全性：**2.0.0 不会让卡片更容易丢**——同一存储键、同一目录、同一判据（§一那四条实据），风险面与 1.9.29 一致。真正的"更容易发生"要等 §一最后那条量出来才敢下结论。
压住不发的最坏情况：2.0 那条主功能（图片存下来）晚上一个批次，而它对现网用户是净收益。

回我一行就行，比如「一放 2.0.1、二要补传、三先发」，我就按拍定的范围出 2.0.1 的技术方案与任务表，然后才动代码。
