## 1. 卡住的：这些要他点头才动

每一条给：现状（引他原话或现读代码）／证据／后果／两条改法／我的建议。

### 1.1 客户端：回体读不懂时那一趟永远挂着〔代码〕

`miniprogram/utils/api.js` **`uploadSingleImage()` 的成功分支**里是 `resolve(JSON.parse(res.data))`，**没包 try**；
同文件非成功分支那一处 `JSON.parse` 是包在 try 里的。全仓 `JSON.parse` 只有这两处（grep 现读）。
（⚠ 我第一版这里写成"`request()` 的成功分支"，归属错了：`request()` 直接 `resolve(res.data)`，本来没有 parse。
 撞得到这一条的是**截图转笔记那一条链**——全仓只有 `/api/ingest/screenshots/stage` 走这个上传口。修完在 6.1。）
后果：服务器（或中间那层代理）回一个 2xx 但body 不是 JSON（空体、HTML 错误页）时，异常吞在 `wx.request` 的回调里，
**Promise 既不 resolve 也不 reject** ⇒ 调用方那枚 `showLoading` 永远收不掉，界面上是"点了没反应"，日志里一行都不留。
这类正是本仓最贵的那一型：静默。
- 甲：成功分支也包 try，读不懂就走 reject 那句"回体读不懂"（多一句用户看得见的错）；
- 乙：只有 `typeof res.data === 'string'` 时才 parse，是对象就直接用（不新增话术）。
我建议乙：它不新增任何一句要翻译的字，也把"永不落地"这一态堵死。

### 1.2 客户端：运营图落账那一行不在 try 里〔代码〕

`miniprogram/utils/mpAssets.js` 的 `pull()` 里，"给旧账补 url" 那一行 `wx.setStorageSync(...)` 写在 `try` **外面**
（`try` 从它的下一行才开始）。而 `app.js` 调 `mpAssets.pull()` 是**故意不 await、也不 catch** 的。
后果：本机存储写满（小程序 10MB 本地缓存上限，图片就落在这个目录下）时，这一行抛出 ⇒ 整趟 pull 变成一个未处理的 Promise 拒绝，
**后面所有 kind 一个都不落账**（含背景图与文案那两条）。这一条不需要用户做错什么，只要机器满了。
改法只有一条值得说：把那一行挪进同一个 try（一行位置），并给 `pull()` 外面补一个 `.catch` 打一行 warn。

### 1.3 客户端：撤账不删本机那个文件，孤儿字节永久留着〔代码〕

同文件里撤账那两处（后台停用／从没登记那一支、以及"账在文件不在"那一支）只 `removeStorageSync`，不 `unlinkSync`；
而正常换图那一支是会删旧文件的（`新文件落盘成功再清旧的`）。
后果：后台撤一次图，本机那份位图就永久躺在 `USER_DATA_PATH` 里（单张实测 294,804 B），谁也读不到它、也没人清它。
改法：撤账那两处一起补 `try { FS.unlinkSync(cached.filePath) } catch(_){}`。这是"删本机文件"，不改任何界面，不需要发版之外的动作。

### 1.4 客户端：官方那一篇的配图每次都白下一份字节〔代码〕

`serverPresetImage()` 回的是 `cached.url`（后端那个匿名口的 https 地址），三个落点（列表右侧那枚封面、详情窗那一排、独立详情页那一格）
和看大图**全部吃这个 URL**；而 `pull()` 顺着图片栏那条通用链把这个 kind 也下载落盘了（源码注释自己写着"屏上不读那个文件"）。
后果：每次换图白下一张（现网那一张 294,804 B）并占本机空间，永远不读。
- 甲：给 `preset_note_image` 开一个"只落账不下字节"的分支（省下载，但那张图的取不到风险全暴露给网络）；
- 乙：照现在这样留着（本机那份当"以后可能要"的余量，实际没人用）。
我建议甲，并连带把 1.3 一起改。⚠ 这条是我自己起的问题，**他没提过**，也可以直接说"不动"。

### 1.5 客户端：三处画配图的 `<image>` 没有 `binderror`〔代码〕

现读：`pages/index/index.wxml` 与 `pages/detail/detail.wxml` 里 `binderror` 命中数为 **0**。
其中这三处画的是**远端地址**（今天这一轮刚接上的）：列表右侧那枚封面（`index.wxml:178`）、详情窗那一排（`index.wxml:236`）、
独立详情页那一排（`detail.wxml:73`）。另外两处（首屏背景 `index.wxml:13`、卡片那一格 `index.wxml:405`）画的是本机路径，取不到的后果不同，先不混在一起说。
后果：远端那个口一旦 404／断网／被撤，那一格**静默空白**——而后台那一栏写着"已发布"。这正是今天他报"我发布了图片，客户端没看到"时最难查的一型；
今天定的是"旧包"那一条根因（见 §8.309 与 §8.310），这一条不是那一次的根因，是**下一次的探测器**。
改法：三处补 `binderror`，落一句本机计数或直接 `console.warn`（不许弹给用户，那是运营侧的事）。

### 1.6 客户端：每次验密码多打一趟全文请求〔代码〕

`pages/index/index.js` 里 `if (this._unlockRenewed) full = await api.getNote(row.id)` 这**同一行连着写了两遍**（现读 :970、:971）。
后果：解锁那一趟多打一次全文 GET，纯浪费，不改变任何显示。删一行即可，是本仓反复警告的"两处同一事实"最低危的一型，但它也在。

### 1.7 后端：「帮助文档不能编辑」那道闸漏了一栏〔代码〕

`backend/app/services/preset_note.py` 里 `CONTENT_FIELDS = ("title","summary","tags","key_points","content","original_content")`（六栏），
而 `routes/notes.py` 的 `NoteUpdate` 有七栏——**多了 `key_links`**。
后果：只 PUT `key_links` 能改掉官方那一篇（改的是"来源链接"那一栏，会进公开分享快照）。
而且 `resync_all()`（他拍的"后台更新后新旧用户全量刷新"）刷的是那六栏，**刷不到 `key_links`**：一旦被改，管理员在后台重发一次也纠不回来。
改法只有一条：把那枚元组补上 `key_links`（一行），并补一条用例钉"七栏逐条 PUT 官方那一篇都要被拒"。
我建议这条现在就补，它不是新需求，是他那句「这一类不许编辑」漏挡的一栏。

### 1.8 后端：配图绑定那一口只查了一张表的归属〔代码〕

`assets.py` 的 `bind_note_assets` 只在 `row` 存在时判 `row.user_id != uid`，查的是 `assets` 这一张表；
而卡片那个口（`cards.py`）与名片那个口（`profiles.py`）都调 `_assert_ours`，它查的是 **assets + note_cards + 名片四格** 三处。
后果形状与 10-09 审计第五条**同一类**（那一条修的正是"别人的对象会被这台客户端删掉"）：
一条已经登记成**别人卡片**的 fileID，可以被绑成我的配图，然后出现在我删笔记的回体 `file_ids` 里交回我的客户端去删。
⚠ 我不下"别人的对象真被删掉了"这句结论：那取决于云开发存储"删"那一档的规则，**今天没有重读那条规则**（10-12 只核过"读"那一档）。
改法：`bind_note_assets` 里改调 `_assert_ours`（它比现在这行查得全）。这是一处"同一个纪律三个口写了两样"的收口，不是新功能。

### 1.9 后端：列表翻页那一栏没有下界也没有上界〔本地实测〕

`routes/notes.py` 的 `list_notes`：`limit` 是 `Query(20, ge=1, le=100)`，`skip` 是裸 `int = 0`（全仓只有这一处用 `skip`，grep 现读）。
本地实测两趟：① 框架层放行超大整数（`skip=1000000000000000000000` → 200 进业务层）；② 驱动层在超过 int64 时抛
`OverflowError: Python int too large to convert to SQLite INTEGER`（sqlite 3.45.3 现测）。负数不报错，等于回到第一页（静默重复同一批）。
**现网端到端我没打**——不想为了拿一个读数在现网日志里留一条 500，所以"现网回 500"这句我不写死。
客户端自己算 `skip = notes.length`，撞不到这一条；只有直接打接口的人撞得到。
改法：`skip: int = Query(0, ge=0, le=100000)`（一个数），要不要设、设多大是他一句话。

### 5.1 这批红里有一条统一根因：一把尺子把这台机的语言带歪了

`验-中英切换-真跑`（批次里第 4 把）**中途崩在恢复之前**，崩因是 `Error: page is not on top of page stack`〔本地实测：日志现读〕。
它崩之前已经把这台机切到英文那一门，而语言存在本机 storage 里，**跑尺子.sh 每把之间只重启不改 storage** ⇒ 后面每一把都在英文界面上量。

这条根因不是猜的，两处独立对上：
