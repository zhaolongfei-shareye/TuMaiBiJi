## 二、它错在哪、我怎么纠的（这一段是这次使用最有价值的部分）

第 1 轮产出的三份文件里，有**六处与仓库实际不符**。其中三处是它没读到值却写了一个"看起来合理"的默认值，而且没按约定标「待核对」：

| 它写的 | 仓库现读 | 出处 |
| --- | --- | --- |
| `DATABASE_URL` 注释为「PostgreSQL 连接串」 | 模板值是 `sqlite:///./tmbj.db`；代码默认空串且空值启动即抛错 | `backend/.env.example`、`backend/app/core/config.py:12`、`:183-185` |
| `JWT_EXPIRE_MINUTES`「通常填 60」 | 代码默认 `60 * 24 * 7` ＝ 10080（7 天） | `backend/app/core/config.py:86` |
| `CORS_ORIGINS` 举例 `http://localhost:5173` | 代码默认 `*` | `backend/app/core/config.py:83` |
| 脚本放仓库根 | 仓库根没有任何 `.sh`，`deploy.sh`／`upload.sh`／`backup.sh` 都在 `backend/` 下 | 目录实测 |
| 入口与端口标「待核对」 | 实例名就是 `app`，端口 8000 在脚本里有实值 | `backend/app/main.py:29`、`backend/deploy.sh:17` |
| README 含「新建 systemd unit」类操作 | 仓库内不含 `.service` 文件，脚本只对已存在的 `wtsj-api`／`wtsj-worker` 做 restart | `deploy.sh` 第 481 行那一段 |

结论：**码道能把活干到"接近能交"，但最后那一层必须由有第一手读数的人逐条核。** 我们这套流程是"人贴真实读数 → 码道成文 → 人 grep 复验 → 带出处打回 → 码道改"，两轮下来六处全部落正。复验方法写在 `codearts_proof/核对记录-01-六处更正.md`，每条都能在改后的文件里 grep 到原句。
