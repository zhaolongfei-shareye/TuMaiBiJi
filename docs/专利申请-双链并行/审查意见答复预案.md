#### CN117528103A —「一种图片压缩方法及装置」

- **申请人**：中国联合网络通信集团有限公司（中国联通）
- **申请日** 2023-11-09，**公开日** 2024-02-06 → 早于我方申请日，构成现有技术
- **核实程度**：**已逐字读取权利要求 1–12 全文**

**它披露了什么**

| 其权项 | 内容 | 对应我方 |
|---|---|---|
| 权 1 | 取得目标源图片；**当其体积超出预设范围时**压缩使之落入该范围；压缩含第 n 次压缩，该次质量比**由第 n−1 次质量比与第 n−1 次压缩后体积共同决定**；n 为正整数 | 我方 S3b 的"按预设压缩策略生成压缩数据" |
| 权 2 | 质量比按 ±1/2ⁿ 依据上次是否超调而调整（收敛式二分） | — |
| **权 3** | **"创建 canvas 画布，将所述目标源图片绘制到 canvas 画布中；将所述第一压缩质量比作为 canvas 画布函数的入参，调用所述 canvas 画布函数"** | **我方"离屏绘图表面重绘＋质量参数导出"——完全命中** |
| 权 5／说明书 | **"预设范围为目标压缩体积的 3/4 至目标压缩体积之间"** | **我方 500KB 预算阈值——命中** |
| 权 11/12＋说明书 | "当指令在终端上运行时"，接收来自其他软件程序的图像 | 我方客户端侧执行——命中 |

**它没有披露什么（我方区别点）**

1. **固定质量阶梯**：其质量比是自适应收敛的（由上一次的结果算出），我方是**预先给定的固定档位** [0.7, 0.5, 0.3]。技术目的不同——我方要让导出次数存在**确定上界（3 次）**，从而在移动端给出确定的时间与内存开销上界；其迭代次数取决于收敛过程，无上界。
2. **长边阈值 ≤1920px**：其说明书提到分辨率影响体积，但**权利要求中无任何尺寸限定**。
3. **串行逐份处理以约束内存峰值**：完全未涉及。其方案不约束多张图像的处理次序，因而不涉及峰值叠加。
4. **两级退路**：压缩不可完成时回退上传原图、字节数不可读时仍输出结果——完全未涉及。
5. **失败输出空值而不抛异常**：完全未涉及。
6. **最关键**：它是**独立的图片压缩方法**，不含笔记、不含字符识别、不含语言模型、不含链的分叉、不含引用绑定、不含孤儿回收。它没有"另一条链"，因而**不可能**产生跨链一致性问题，我方的跨链补偿手段在其架构下**无适用对象**。

**答复口径**

> CN117528103A 解决的技术问题是"如何将图片体积收敛到目标区间"，属于压缩算法本身的改进。本申请解决的技术问题是"在移动端内存配额约束下如何组织多张图像的处理次序，以及在压缩能力不可用时如何保证原件不丢失"，属于处理调度与容错。二者技术问题不同，故本申请的串行逐份处理与两级退路不是该对比文件的常规变体，本领域技术人员在面对本申请的技术问题时无动机从该对比文件出发得到相应手段。此外，该对比文件为单一处理链，不存在本申请权利要求 1 中 S5 所述跨链补偿回滚的适用前提。

**风险提示**：我方**从属权利要求 2 与 3**（阶梯压缩策略与具体数值）被该文献覆盖程度较高。若审查员以其否定权 2／3 的创造性，**建议直接放弃权 3（纯数值限定），保留权 2 但把"固定档位＋导出次数确定上界"写进权 2 的特征部分**，而不是纠缠数值本身。

**已采取的措施**：v2.1 已把发明名称从"双链并行解耦"改为"**语义抽取与原件留存跨链补偿**"，并在背景技术第三类中不点名地准确描述了该架构及其"不汇合"的构思。

## 三、答复策略：三段式

### 第一段：把战场钉在跨链补偿上

主张权利要求 1 的区别技术特征为：

1. 客户端在**同一执行上下文**中分叉两条链，且**留存链句柄在抽取链发起首个网络请求之前建立、抽取链不等待该句柄**（时序关系本身是特征，不只是"并行"这个结果）；
2. 两条链的**失败关键性被刻意设为非对称**：留存链全程不抛异常、抽取链有损可降级且记录仍被持久化；
3. **S5 跨链补偿回滚**：抽取链失败**反向触发**对留存链**已成功提交的完整对象**的删除，且为删除本身的失败定义了二阶处置（待删队列＋与绑定补偿共用生命周期触发）；
4. S4／S5 两队列**共用同一生命周期事件触发时机**，使绑定与删除两类跨链中间状态收敛于同一收敛点。

### 第二段：创造性论证的主道与辅道

**主道＝第四章4.2 组合发明**：「其中组合发明的每个单独的技术特征本身是否完全或者部分已知并不影响对该发明创造性的评价。」据此，审查员即使认定重试队列、幂等绑定、碎片清理各自已知，仍**必须**就"本领域技术人员为何会把它们组合成权利要求 1 的整体、并预期获得消除原件丢失路径的效果"给出理由。只逐条列举各特征已知、不论证组合动机与组合后功能互依的通知书，不符合三步法，应据此反驳。

**辅道＝预料不到的技术效果（第四章6.3；是替代路径，不是要件）**：仅在主道被正面击破时启用，落点为：

- **消除原件永久丢失路径**：由五条规则构成的闭环，任一规则被移除都会打开一条丢失路径——这是各单点特征都不具备的整体效果。
- **将不可恢复故障转化为可重算故障**：推理服务不可用时，结果不是"记录不存在"，而是"记录存在＋语义字段为空＋降级标记"，后者可由留存链已保全的原件重新计算得出。**该转化的前提正是两条链的分叉与非对称失败处置**，在单链架构下无法实现。
- **内存峰值可前置约束**：像素量前置于解码的准入判定（针对实测 0.43MB 文件解码后峰值 1271MB）、识别调用互斥串行化、客户端串行逐份压缩、服务端六维暂存预算——四者共同使峰值存在确定上界。

### 第三段：预防"公知常识"拼装

预先声明：即便重试队列、幂等写入、碎片清理各自属于常规工程实践，**将下游语义处理的失败反向耦合至上游存储已提交的副作用之上**这一构思在检索范围内未见任何文献披露；且现有云厂商碎片清理的对象是**未完成的分片**而非**已完成的完整对象**，其触发条件是**上传会话未完成**而非**另一条链失败**，故不能给出技术启示。
