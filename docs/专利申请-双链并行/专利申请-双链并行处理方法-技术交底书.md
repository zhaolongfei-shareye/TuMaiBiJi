# 权利要求书

1. 一种移动端多源内容处理的双链并行方法，其特征在于，包括以下步骤：

   S1：响应于用户在移动终端上触发的内容提交操作，同时启动相互独立的内容提取链（A链）和资产备份链（B链），两链并行执行且互不阻塞；

   S2：所述A链执行以下步骤：
   - S2a：将用户提交的原始内容数据传输至服务端；
   - S2b：服务端对所述原始内容数据进行智能处理，提取结构化知识信息；
   - S2c：将所述结构化知识信息写入数据库，生成笔记记录，并返回笔记标识；

   S3：所述B链在客户端执行以下步骤，与S2同时并行：
   - S3a：对所述原始内容数据进行压缩处理，生成压缩后的备份数据；
   - S3b：将所述备份数据上传至云存储系统，获得存储标识；

   S4：在A链和B链均完成后，执行资产绑定步骤，将B链获得的存储标识关联至A链生成的笔记记录；

   其中，所述A链和B链各自独立处理失败：A链失败时，清理B链已上传的资产数据；B链失败时，不影响A链的笔记创建。

2. 根据权利要求1所述的方法，其特征在于，所述S2b中的智能处理包括：

   当原始内容数据为图像数据时，先通过光学字符识别（OCR）引擎提取文本内容，再将所述文本内容输入大语言模型（LLM）进行知识提炼，输出包括标题、摘要、要点和标签的结构化知识信息；

   当大语言模型调用失败时，执行降级处理：仅从原始文本中提取标题字段，摘要、要点和标签字段置为空值，并将降级标记写入笔记记录，笔记创建操作仍然成功完成。

3. 根据权利要求1所述的方法，其特征在于，所述S3a中的压缩处理采用阶梯式质量递减方法，包括：

   - 首先按预设长边阈值对图像进行等比缩放；
   - 然后按照预定义的质量参数阶梯从高到低依次尝试导出，每次导出后检测文件大小是否超过预设预算阈值；
   - 当文件大小在预算阈值以内时，立即返回当前结果；
   - 当所有质量档位均超出预算阈值时，返回最低质量档位的导出结果，保证不丢失图像数据。

4. 根据权利要求3所述的方法，其特征在于，所述质量参数阶梯为[0.7, 0.5, 0.3]，所述预设长边阈值为1920像素，所述预设预算阈值为500KB。

5. 根据权利要求1所述的方法，其特征在于，所述S3b中的上传步骤采用客户端直传云存储的方式，上传失败时返回空值而不抛出异常，调用方将空值视为该张图像未备份，不影响后续处理。

6. 根据权利要求1所述的方法，其特征在于，所述B链中的步骤S3a采用串行处理方式，逐张对图像进行压缩和上传，以避免多张大图同时处理导致客户端内存溢出。

7. 根据权利要求1所述的方法，其特征在于，所述S4中的资产绑定步骤还包括失败补偿机制：

   - 当绑定接口调用失败时，将待绑定的资产信息写入客户端本地持久化队列；
   - 在应用程序下次进入前台时，自动从所述队列中读取待绑定项并重试绑定操作；
   - 对于服务端返回明确拒绝（4xx状态码）的绑定请求，从队列中移除对应条目不再重试；
   - 对于服务端返回临时错误（5xx状态码）或网络错误的请求，保留在队列中等待下次重试。

8. 根据权利要求1所述的方法，其特征在于，当A链失败时，所述方法还包括孤儿资产清理步骤：

   - 获取B链已上传至云存储的所有资产存储标识；
   - 调用云存储删除接口清除所述孤儿资产；
   - 删除失败时，将待删除的存储标识写入待删队列，在应用程序下次进入前台时重试。

9. 根据权利要求1所述的方法，其特征在于，所述S2a中服务端接收原始内容数据采用两阶段方式：

   - 暂存阶段（stage）：逐张接收客户端上传的图像数据，存入服务端内存暂存区，返回批次标识；
   - 处理阶段（process）：客户端提交批次标识，服务端将暂存区中的整批数据打包入队至异步任务队列，由工作进程异步执行OCR和LLM处理。

10. 一种移动端多源内容处理的双链并行系统，其特征在于，包括：

    调度模块，位于客户端，用于响应于用户的内容提交操作，同时启动内容提取链和资产备份链，两链并行执行且互不阻塞；

    内容提取模块，位于服务端，用于对客户端提交的原始内容数据进行智能处理，提取结构化知识信息并写入数据库生成笔记记录；

    资产备份模块，位于客户端，用于对原始内容数据进行压缩处理后上传至云存储系统；

    资产绑定模块，用于在A链和B链均完成后，将B链的存储标识关联至A链生成的笔记记录；

    降级补偿模块，用于处理A链或B链的独立失败情况：A链失败时清理B链已上传资产，B链失败时不影响笔记创建，绑定失败时通过本地队列实现异步重试。

# 说明书

## 一种移动端多源内容处理的双链并行方法及系统

### 技术领域

[0001] 本发明涉及移动互联网数据处理技术领域，具体涉及一种在移动端应用中将内容智能提取与原始资产备份解耦为两条独立并行管线的数据处理方法及系统。

### 背景技术

[0002] 随着移动互联网的发展，用户日常产生大量需要保存和管理的数字内容，包括网页链接、屏幕截图、手动文本等。现有的笔记类应用通常采用串行处理方式：先将用户上传的内容进行智能处理（如OCR识别、AI摘要生成），处理完成后再进行原始数据的备份存储。

[0003] 这种串行处理方式存在以下技术问题：

[0004] （1）用户体验差：用户需要等待智能处理（包括OCR识别和大语言模型调用）完成后，原始资产才开始备份，整体耗时较长。当AI服务不可用或响应缓慢时，原始资产的备份也被延迟。

[0005] （2）容错能力弱：智能处理和资产备份耦合在一起，任一环节失败都会导致整个流程中断。例如，当AI服务暂时不可用时，不仅无法生成结构化笔记，原始截图的备份也无法完成，导致用户数据丢失。

[0006] （3）资源利用不合理：在移动端有限的计算和内存资源下，同时进行OCR、LLM调用和图片压缩上传会导致资源竞争，可能引发内存溢出或应用崩溃。

[0007] 因此，需要一种能够将内容智能提取与原始资产备份解耦、并行执行且各自具备独立容错能力的技术方案。

### 发明内容

[0008] 为了解决上述技术问题，本发明提供了一种移动端多源内容处理的双链并行方法及系统，将内容处理解耦为两条独立的并行管线（A链：内容提取链，B链：资产备份链），两链同时启动、互不阻塞、各自独立处理失败。

[0009] 本发明的技术方案如下：

[0010] 一种移动端多源内容处理的双链并行方法，包括以下步骤：

[0011] S1：响应于用户在移动终端上触发的内容提交操作，同时启动相互独立的内容提取链（A链）和资产备份链（B链），两链并行执行且互不阻塞。具体地，在客户端代码中，B链的Promise对象在A链调用之前创建，但B链不通过await等待，使得A链和B链同时进入执行状态。

[0012] S2：所述A链执行以下步骤：

[0013] S2a：将用户提交的原始内容数据传输至服务端。采用两阶段接收方式：暂存阶段（stage）逐张接收图像数据并存入服务端内存暂存区，返回批次标识；处理阶段（process）根据批次标识将整批数据打包入队至异步任务队列。

[0014] S2b：服务端异步任务队列中的工作进程对所述原始内容数据执行智能处理。当原始数据为图像时，先通过OCR引擎（如RapidOCR）提取文本内容，再将文本输入大语言模型（LLM）进行知识提炼，输出包括标题（title）、摘要（summary）、要点（key_points）和标签（tags）四个字段的结构化知识信息。LLM调用采用指数退避重试策略，最多重试3次，退避间隔为1秒、2秒、4秒。

[0015] S2c：将所述结构化知识信息写入数据库，生成笔记记录，并返回笔记标识（note_id）。客户端通过轮询方式（间隔2秒，最长等待300秒）获取任务处理结果。

[0016] S3：所述B链在客户端执行以下步骤，与S2同时并行：

[0017] S3a：对所述原始内容数据采用阶梯式质量递减方法进行压缩处理。具体包括：首先按预设长边阈值（1920像素）对图像进行等比缩放，通过离屏Canvas重绘；然后按照质量参数阶梯[0.7, 0.5, 0.3]从高到低依次尝试导出为JPEG格式，每次导出后检测文件大小是否超过预设预算阈值（500KB）；当文件大小在预算以内时立即返回；当所有档位均超出预算时返回最低质量档位的导出结果。

[0018] S3b：将压缩后的数据通过客户端直传方式上传至云存储系统。上传路径按照"images/{用户标识}/{日期}/{时间戳随机串}.{扩展名}"的格式生成。上传失败时返回空值（null）而不抛出异常。

[0019] S3中B链采用串行处理方式，逐张对图像执行压缩和上传，避免多张大图同时在离屏Canvas上重绘导致客户端内存溢出。

[0020] S4：在A链和B链均完成后，执行资产绑定步骤。具体包括：

[0021] - 当A链成功返回笔记标识时，调用服务端绑定接口将B链获得的存储标识（file_id）关联至该笔记记录。绑定接口采用幂等设计：已存在的资产行更新关联的笔记标识，不存在的资产行新建记录。每篇笔记最多关联9张资产图片。

[0022] - 当绑定接口调用失败时，将待绑定资产信息写入客户端本地持久化队列（assetQueue），在应用程序下次进入前台时自动重试。对于服务端返回4xx明确拒绝的请求从队列移除，对于5xx或网络错误保留等待下次重试。本地队列上限为50条，超出时丢弃最旧条目。

[0023] - 当A链失败（笔记未创建）时，获取B链已上传的所有存储标识，调用云存储删除接口清除孤儿资产。删除失败时写入待删队列（purgeQueue），下次前台时重试。

[0024] 本发明的核心设计原则是：B链全程不抛出异常，所有失败均返回空值或静默处理，确保B链的任何问题都不影响A链的笔记创建。A链的LLM提炼环节具备降级策略：当LLM调用失败时，仅从原始文本提取标题，其余字段置空，笔记仍然成功创建。

[0025] 本发明还提供一种移动端多源内容处理的双链并行系统，包括：调度模块、内容提取模块、资产备份模块、资产绑定模块和降级补偿模块。

[0026] 本发明的有益效果如下：

[0027] （1）用户体验提升：内容提取和资产备份并行执行，用户无需等待AI处理完成即可看到备份进度，整体感知等待时间缩短。

[0028] （2）容错能力增强：两链独立失败处理，AI服务不可用时原始截图仍然可以备份保存；备份失败时笔记创建不受影响。

[0029] （3）资源利用优化：B链在客户端串行处理避免内存溢出，A链在服务端异步队列处理避免阻塞主进程。

[0030] （4）数据一致性保障：通过本地持久化队列实现异步重试机制，确保在网络波动或临时故障场景下最终完成资产绑定。

### 具体实施方式

[0035] 下面结合附图和具体实施例对本发明作进一步详细说明。

[0036] **实施例1：截图导入场景**

[0037] 用户在微信小程序"图麦笔记"中选择1-9张截图并点击"导入"按钮，触发本发明的双链并行方法。

[0038] 调度模块（位于客户端create.js的submitScreenshots方法）执行以下操作：

[0039] 步骤1：创建B链Promise对象。调用_backupShots(batch)方法，该方法返回一个Promise但不通过await等待。B链内部执行：

[0040] - 遍历batch中的每张截图路径；
[0041] - 对每张截图调用compressForBackup()进行阶梯式压缩：先通过wx.getImageInfo获取原始尺寸，计算缩放比例使长边不超过1920像素，通过wx.createOffscreenCanvas创建离屏画布重绘，然后按质量阶梯[0.7, 0.5, 0.3]依次调用canvas.toTempFilePath导出，每次导出后通过wx.getFileSystemManager().stat检查文件大小，不超过500KB即返回，否则继续下一档；
[0042] - 对压缩后的图片调用wx.cloud.uploadFile直传云存储，路径格式为"images/{userId}/{YYYYMMDD}/{timestamp36}.{ext}"；
[0043] - 收集所有成功上传的file_id，返回{items: [{file_id, size, width, height}]}。

[0044] 步骤2：启动A链。调用api.ingestScreenshots(batch)方法，该方法内部执行：

[0045] - 逐张调用POST /api/ingest/screenshots/stage接口，将图片二进制数据上传至服务端内存暂存区（_batch_staging字典），第一张不带batch_id，服务端返回生成的batch_id，后续图片携带该batch_id；
[0046] - 所有图片暂存完成后，调用POST /api/ingest/screenshots/process接口提交batch_id，服务端将该批次数据打包入队至Redis+RQ异步任务队列，返回task_id。

[0047] 步骤3：客户端轮询A链结果。调用api.pollTask(task_id)方法，每2秒调用一次GET /api/tasks/{task_id}接口检查任务状态，最长等待300秒。

[0048] 步骤4：服务端RQ Worker异步执行A链任务。process_screenshots_task函数执行：

[0049] - 调用ocr_images()对暂存区中的图片逐张执行OCR：先通过_prepare()函数进行预处理（EXIF方向校正、长边缩放至1600像素以内、像素总量检查不超过4000万），然后通过RapidOCR引擎（PP-OCR模型，ONNXRuntime推理）识别文字，过滤置信度低于0.5的噪声行，最终拼接为带页码标记的全文；
[0050] - 调用extract_knowledge()将OCR文本输入混元大语言模型（通过微信云函数cloud.ai()调用，模型ID hy3-preview，温度0.3），系统提示词要求模型输出JSON格式的{title, summary, key_points, tags}四个字段；
[0051] - LLM调用采用3次指数退避重试（间隔1s/2s/4s），仅对429/5xx/超时错误重试；
[0052] - 若LLM调用最终失败，执行降级策略：调用_degraded()函数，从OCR文本首行截取不超过30字符作为标题，summary/key_points/tags置空，返回{degraded: True}；
[0053] - 将结构化知识信息写入SQLite数据库的Note表，返回note_id。

[0054] 步骤5：A链完成后执行资产绑定。调用_settleBackup(note_id, backup)方法：

[0055] - 等待B链Promise完成（await backupPromise）；
[0056] - 若A链成功（note_id不为空）：调用POST /api/notes/{note_id}/assets接口绑定资产，服务端执行幂等写入（已存在的object_key更新note_id，不存在的插入新行），检查总绑定数不超过9张；
[0057] - 若绑定接口失败：调用assetQueue.push(note_id, items)将待绑定项写入本地Storage（键名pendingNoteAssets），同一篇笔记的多次追加合并为一条，队列上限50条；
[0058] - 若A链失败（note_id为空）：调用cloudUpload.deleteFiles(fileIDs)删除B链已上传的孤儿资产；删除失败时写入待删队列（pendingCloudPurge），下次前台重试。

[0059] 步骤6：应用前台恢复时自动补偿。app.js的onShow生命周期中：

[0060] - 调用assetQueue.flush(api)：逐条读取pendingNoteAssets队列，尝试绑定，成功则从队列移除，4xx错误也移除（重试无意义），5xx/网络错误保留；
[0061] - 调用cloudUpload.flushPurge()：逐条读取pendingCloudPurge队列，尝试删除，成功则移除。

[0062] **实施例2：URL导入场景**

[0063] 用户粘贴一个网页URL，A链执行：服务端通过SSRF安全抓取（DNS验证防止内网访问，最大5MB响应，最多5次重定向）获取网页内容，使用trafilatura提取正文，然后送入LLM提炼结构化知识。B链在此场景下不启动（URL无原始图像需要备份）。

[0064] **实施例3：手动文本输入场景**

[0065] 用户手动输入文本内容，A链执行：文本先经过内容安全审核（微信msgSecCheck API，分块2000字符，最多8块），审核通过后送入LLM提炼。B链在此场景下不启动。

# 说明书摘要

[0067] 本发明公开了一种移动端多源内容处理的双链并行方法及系统。该方法响应于用户的内容提交操作，同时启动内容提取链（A链）和资产备份链（B链），两链并行执行且互不阻塞。A链将原始内容传输至服务端，经OCR识别和大语言模型提炼后生成结构化笔记；B链在客户端对原始内容进行阶梯式质量压缩后直传云存储。两链完成后执行资产绑定，将云存储标识关联至笔记记录。A链和B链各自独立处理失败：A链失败时清理B链已上传的孤儿资产；B链失败时不影响笔记创建；绑定失败时通过本地持久化队列实现异步重试。本发明解决了现有笔记应用串行处理导致的等待时间长、容错能力弱、资源竞争等问题，提升了用户体验和数据可靠性。
