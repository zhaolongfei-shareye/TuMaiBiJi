## 七、要他判断的，其实只有三句话（其余是读数）

1. **装不装渲染**：收益＝微博那一族从 0 张变 5～6 张原图；代价＝给 4 核／可用 1.8G 的机器装浏览器＋浏览器版 SSRF 必须先做出口拦截。
2. **要不要"Referer 重试一次"这一小块**：它单独不成立（微博地址还得靠渲染才拿到），但**渲染做完就必须做它**，否则微博那 5 张全 403。
3. **要不要重看乙**（换住宅出口）：技术上 0/5→4/5 是真的，但它同时把"承诺级"三个字撑不住（本机 1/5 仍落登录壳、裸笔记页 10/10 过不去），且要把用户链接交第三方。

**这三句之外我不再列新待拍**：cookie、签名对抗、开放平台、`web-view` 四条是"做不到／不做"，
黑名单那一格（今天就会自然拦掉小红书短链）只有一句"要不要预先手工拦"。

## 九、「微信用户能直接打开小红书」的机制，与"拿用户登录凭证"那三枚凭证（10-19 16:0x 新量，两台读数一致）

### ① 那条链接在微信里到底走了什么（跳链原样抄下来）

用**微信内置浏览器 UA**（`MicroMessenger/8.0.50`）与**小程序 webview UA**（`MiniProgramEnv`）各打一遍，
本机与现网**四发读数完全一致**：

```
https://xhslink.cn/o/9F1fAXNBL1I
  → 302  https://www.xiaohongshu.com/discovery/item/6ad40f01…?app_platform=android&…
              &xsec_source=app_share&xsec_token=CBUezgT0…（分享令牌）
  → 302  https://open.weixin.qq.com/connect/oauth2/authorize?appid=wx24d4366d90ac53a8
              &redirect_uri=https%3A%2F%2Fwww.xiaohongshu.com%2Fdiscovery%2Fitem%2F…
  → 301  同上
  → 200  1,033 B，title「抱歉，出错了」，可见词 40
```

⇒ **"微信用户可以直接打开小红书"靠的是小红书自己接了微信开放平台的网页授权**：
那枚 `appid=wx24d4366d90ac53a8` 是**小红书的微信应用**，用户在微信里点「允许」，小红书换到用户身份后才渲染笔记。
⇒ 脚本复制不了这一条：脱离真实微信 webview，微信那一头回的就是 1,033 B 的错误页（**两台四发都是这个读数**）。

### ② 今天才发现的一枚被所有旧轮次忽略的东西：`xsec_token`（分享令牌）

| 这一发怎么打 | 本机（移动出口） | 现网（腾讯云出口） |
|---|---|---|
| **带 `xsec_token`** 的完整分享址（生产头） | ✅ 200／68,997 B → **正文 42 字／图 5 张／作者有** | ❌ 36,212 B 登录壳 |
| `explore/<id>?xsec_token=…`（生产头） | ✅ 200／69,040 B → 同上，**通** | ❌ 36,211 B 登录壳 |
| **不带 token** 的裸址 `discovery/item/<id>` | ❌ 96,397 B、正文 0 字 0 图 | ❌ 96,398 B 同形 |
| 短链（生产头，跟完跳转） | ✅ 4/5 真笔记（§8.346） | ❌ 登录壳 |

⇒ **两个条件缺一不可：出口身份 ＋ 分享令牌。**
好消息是**令牌这一头我们已经有了**——`_fetch_and_parse` 跟跳时原样带着 `location` 里的全部 query 参数，
所以粘短链的用户，我们替他把 `xsec_token` 一起送到了。
⇒ **今天这枚读数把"换出口到底能不能解决小红书"这一格收紧了：令牌不是障碍，卡的只剩出口那一项。**
（另：移动浏览器 UA 打带 token 的址回 73,969 B 的 **SPA 空壳**——`fe-static.xhscdn.com` 那串加载器、`noteDetailMap` 命中 0
⇒ 又一处"必须执行 JS 才有内容"的实证，但对现网没用，出口照样拦。）

⚠ 顺带记一条我自己判据的坑：那 96,397 B 的拒绝页里**也有 `noteDetailMap` 这个键**（SPA 把 store 骨架一并发了），
所以"命中 `noteDetailMap`"**不等于拿到笔记**，判据必须看 `note` 里那四格有没有实际内容。
临时脚本那一把我就把它错标成"真笔记 0 字 0 图"；已提交的尺子先判 `sec`／`login` 再判这个键，顺序是对的。

### ③ 「用户通过我们小程序登录了，拿他的凭证能不能读小红书」——三枚凭证分开答

| 这枚"凭证" | 能不能打开小红书 | 为什么 |
|---|---|---|
| **我们小程序的登录态**（我们的 JWT；用户在本服的账号） | ❌ **结构上无关** | 我们的票只在自己 API 里有效；`openid`／`unionid` 只在**我们这个 AppID** 体系内有意义。小红书不认它，也不会因为它放行 |
| **用户在微信里授权给小红书的那枚 code／token** | ❌ **拿不到，也不该拿** | 微信网页授权只把 code 发给 `redirect_uri` 所属的那个 appid（这里是小红书自己的 `wx24d4366d90ac53a8`）。**授权对象是小红书，不是我们**；反过来我们 `wx.login` 拿到的 code 也只能换"用户在我们这里"的身份 |
| **用户自己小红书账号的登录态 cookie** | ⚠ **唯一技术上说得通的形状，但我没测、也不会拿你或用户的账号去试** | 代价清单：① 等于让用户交出**密码级凭据**（会话 cookie 丢了就是账号被人用）；② 我们要长期**存第三方账号凭据**，与这台机器"凭据不落盘、不进对话"那条纪律正面冲突；③ 隐私政策要改写＋微信后台要报备（处理敏感个人信息的委托/共享）；④ **被封的是用户本人的账号**，不是我们的服务器；⑤ 小红书用户协议明确禁止自动化访问 |

⇒ 这一格我**不写成"已排除"**（它不是被读数推翻的），也不写成"建议做"（它不由我建议）。
它现在的准确状态是：**技术形状存在，代价由你承担判断**。要往前走需要你说清两件事：
用谁的账号（你自己的？还是每个用户自己的？）、以及凭据存在哪儿、多久失效。

### ④ 而今天这条读数把第三条路的成本重算了一遍

原话「换出口」我列在"他拍乙"那一档。今天新读数把它的**收益不确定性去掉了一半**：
令牌已经有了，卡点只剩"服务器那个 IP 被判定为机房风险"。
⇒ 如果哪天要重看乙，**要买的东西现在很明确**：一个国内家宽／移动出口（不是签名、不是 cookie、不是浏览器），
就这一项。至于它撑不撑得起承诺，还是那两条老读数在：本机 5 趟里 1 趟落登录壳、裸址那一档两台都 10/10 拒。
