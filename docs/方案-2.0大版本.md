# 2.0 大版本方案（与旧版隔离 · 模板不走发版 · 拍照与截图 · 每篇最多 3 张图）

写于 2026-10-06，基于当天仓库与现网实据（每条事实后面都标了出处，动手前可复核）。
**这份是路线，不是施工单**：§5 那三条待拍回完，才谈得上按 §3 开工。

## 0. 锚点

一句话：**把"卡片模板能不走发版就更新"做成一条真能跑、真有人管的通道，同时把图片这一件事按你要的口径定下来，全程不许把线上 1.x 那条线弄坏。**

大版本的主功能不是"新画法"，是**换交付方式**——模板从"跟着小程序发版走"变成"服务端下发配方"。这件事的代码已经写完了（见 §1.1），所以 2.0 的重心在后端上线、流程、和隔离契约上，不在前端画法上。

## 1. 三条不查就会踩的事实（今天的样子）

### 1.1 模板那套：代码 100% 在，现网 0% 部署

- 客户端配方解释器、包内兜底十套、拉取与合并、回退，全在：`miniprogram/utils/posterRecipe.js`、`poster.js` 的 `planFromRecipe` / `applyRemoteTemplates` / `recipeSource`、`posterTemplates.js`、`posterRecipes.js`。
- 后端那一套也全在：迁移 `backend/alembic/versions/a7d2e5b8c310_poster_templates.py`（只建表 + 3 条索引，不灌数据）、路由 `backend/app/api/routes/poster_templates.py`（要登录、只回 live、**故意没有写接口**）、服务与测试、种子 `backend/seed/poster_templates.json`（十套 × 9 字段）。
- **但现网 10-06 实测：`GET /wtsj/api/poster/templates` 回 404**，`openapi.json` 里 29 条路径含 poster 的 0 条（对照 `/api/notes/` 回 401、`/docs` 回 200，不是整站坏了）。
- 结论：这条主功能的剩余工作是**部署 + 开闸门 + 建上线流程 + 加新模板**，不是写解释器。省下来的力气应该花在"怎么让加一套模板这件事不再依赖我改代码"。
- 边界要记住（官方 2022-07-06 明令禁止下发可执行代码）：能热更的只有**配方 JSON**；绘制 op（10 种）与排版原语（30 条）是封闭清单，**动这两层＝必须发版**。规范全文在 `docs/产品需求.md` §11（11.2 十条硬规矩、11.4 五步上线、11.5 负面清单）。

### 1.2 图片：今天一篇笔记的图**根本不落库**

- `backend/app/models/note.py` 里没有任何图片列；没有 `note_images` 这类表。
- 截图/拍照进来的字节只活在 `ingest.py` 的进程内存 staging（TTL 30 分钟），`ingest_tasks.py:111 process_screenshots_task` 做完 OCR 把文字写进 `original_content` 就**丢弃原图**。
- 有一张 `assets` 表（`object_key`/`file_size`/`width`/`height`），但**全仓零写入**——只有注销时那句 `Asset...delete()` 和两个从没被赋过值的 `cover_asset_id` 外键在引用它。
- 张数上限今天是这么写的：前端 `create.js` 选图 `count: 9` 且合并后 `.slice(0, 9)`；后端 `ingest.py:119 MAX_IMAGES_PER_BATCH = 10`（注释写明"前端 9 留 1 余量"，管的是**一批**，不是**一篇**）。另外单张 10MB、单批 40MB、每用户 2 批。
- 所以"每篇笔记最多关联 3 张图片"有两种读法，工作量差一个数量级——这是 §5 待拍第①条，我不替你选。
- 云开发那套方案（`docs/图片云备份方案.md` 方案 A：前端直传、压缩 ≤500KB、详情页缩略图 + `wx.previewImage`、分享带图，COS 已否）**代码零实现**：全仓搜不到 `wx.cloud` / `fileID` / `cloudPath`，方案里规划的两个 utils 文件不存在。云开发环境本身是活的（混元走的就是它），所以走这条路不用新开通什么。

### 1.3 那个挂着的 `feature-2.0` 分支不能当底座

- 冲突区七个文件，最险的是 `pages/share/share.js`（两边各自动了一百多行）与 `backend/app/api/routes/notes.py`、`services/quota.py`、`i18n.js`、`deploy.sh`。
- 分支上**没有任何隔离设计痕迹**：`utils/appInfo.js` 那时还不存在（版本号写死在 about 页 = 1.1.15）、没有 `/api/v2` 前缀、没有灰度开关，只有一个 `XPAY_ENABLED` 支付总开关。

## 2. "与旧版隔离"怎么隔（先讲一件平台事实）

**微信小程序线上只有一个版本。** 不存在"1.x 用户和 2.0 用户同时在线各用各的"这种状态（除体验版/开发版那条灰度通道）。所以"隔离"只能发生在三个地方，不能发生在"两个线上版本并行"上：

- **甲 同 AppID + 分支隔离 + 数据向后兼容（建议）**
  拉 `release/2.0` 分支，master 冻结成"只修 P0 故障"；2.0 期间线上继续发 1.9.x 的补丁。
  兼容契约三条：① 接口字段**只增不改不删**，老包读新数据不许炸；② 配方带 `schema_version`，客户端读不懂的版本就回退包内那十套（这条今天已经是这个行为）；③ 数据库迁移只加表加列，2.0 期间不许改老列语义。
  代价：2.0 上线那一刻，所有用户一次性跳到 2.0，没有"想留在旧版"的出口。
  好处：一份 i18n、一套判据、一个域名配置、一次审核。你一个人维护，这条最省。

- **乙 另开 AppID，做一个全新的 2.0 小程序（真隔离）**
  代价：新 AppID 要重新配 request/uploadFile/downloadFile 合法域名、重新提审（1–7 天）、后端要按 AppID 分流用户与数据（现在 openid 是唯一键，等于要建"同一自然人两个身份"的映射）、老用户不主动迁移就看不到新版、i18n 与判据两套各自维护、云开发配额与混元 token 也要按两个主体算。
  适合的场景只有一个：你想让 2.0 换名字/换定位重新起盘。这次四条需求里没有这个意思。

- **丙 同一个包里做新旧双皮肤/开关**
  代码不隔离，两套 UI 长期共存，每条判据都要跑两遍。**不建议**，这是三种里最贵的，而且和"与旧版隔离"这句正好相反。

## 3. 排期（每阶段都有出口判据，判据不过不进下一阶段）

**阶段 0 · 先把 1.x 收口（10-06 ~ 10-08）**
1.9.30 提审 → 过审发布；然后才开后端闸门部署模板那套（`POSTER_TEMPLATES=1`），跑 `backend/probes/poster_templates_live_probe.py` 现网探针。
**顺序不能倒**：现在线上那个 1.9.26 的包里连 `getPosterTemplates()` 这条调用都没有，先部署只会得到"表里有十套、线上没人读"的错位。
出口：后台读到线上版本 = 1.9.30；现网 GET 回 200 + 十套 live；探针全过。

**阶段 1 · 隔离与契约（10-09 ~ 10-13）**
定 §2 甲/乙（待拍②）；拉 `release/2.0`；版本号常量走 2.0.x；把"接口字段只增不改"和"配方 schema_version 读不懂就回退"各钉一条判据；**新建一把守张数的尺子**（今天没有任何尺子守张数，改 9→3 会同时打红两处常量却没人告诉你漏了哪一处）。
出口：新尺子跑通；master 上 1.9.x 的回归尺子（色板/四套莫兰迪/列表/详情窗/录入条）在 2.0 分支上全绿。

**阶段 2 · 模板不走发版闭环（10-14 ~ 10-24）**
这是主功能。三件事：
① 把"下发真生效"证明到端到端——`验-模板配方下发-注入-真跑.js` 那把（唯一能证"改服务端数据 → 用户手机上换了一套卡片"的尺子）要在**现网**跑通，不再靠注入替身。
② 加 2~3 套新模板验证"不发版"——P1 那两套试验品（`docs/design/新模板候选/` 的 band / halo）按 §11.2 十条规矩正式收编，再新写一套做对照。
③ 把上线流程落成文档 + 脚本：写配方 → 两道关（静态等价 + 注入真跑）→ 肉眼看图 → 种子 → 闸门 → 探针。目标是**加一套模板不用碰 miniprogram 一行代码**。
出口：现网改一行配方 JSON、小程序不发版，真机上卡片跟着变；回退路径也演一遍（把那条翻成 archived）。

**阶段 3 · 图片这一条（取决于待拍①）**
- 若读法甲（只是**选图上限**改成 3）：改 `create.js` 两处常量 + 后端注释与校验对齐 + 新建那把张数尺子 + 面板缩略图那一排在 3 张下的高度复量。**1~2 天**。
- 若读法乙（**图要留在笔记上**，最多 3 张）：从零建存储链路——写入口（云开发前端直传，按方案 A）、`note_assets` 关系表与迁移、读回接口、详情页缩略图 + `wx.previewImage`、分享卡片带图、压缩 ≤500KB、删除笔记连带删图、注销连带清理、配额与超限提示。**约 2 周**，并且要新增 downloadFile 合法域名（模拟器永远看不出这条，只有真机能撞）。
出口：拍照与截图这两条入口在新版本上各真跑一遍（含权限被拒、HEIC 被拒、超 3 张被拦三种异常态）。

**阶段 4 · 2.0 提审与灰度（10-25 ~ 11-05）**
体验版先自扫，再提审（1–7 天）。提审描述里**不许出现"模板可热更新"这种对外说法**——对外只说"卡片样式会持续上新"，因为下发要登录且只回 live，审核环境读到的东西不稳定。

## 4. 负面清单（这一版明确不做）

- 不做 JS 解释器式的热更新（官方明令禁止，且配方体积/层数/节点已有上界：16KB / 24 层 / 2000 节点）。
- 不做服务端出图（`render: 'server'` 那枚门从没落地，见 §5⑤）。
- 不引入任何"篇数限制"（你 10-04 拍过笔记不限量，挂起分支里那条额度扩容按作废处理）。
- 不做语音录入、不支持 HEIC、不做海外、不做社交（MVP 那几条决策一条都不翻）。
- 不在 2.0 里重做 UI 风格——四套莫兰迪、左块右文、列表 D2 那套口径全部继承，2.0 只换交付方式与图片。
- 不碰微信 OCR 个人主体那条死路（101003），提炼仍只走混元。

## 5. 待拍（每条自带我的理解和代价）

**① "每篇笔记最多关联 3 张图片"——是选图上限，还是图要留下来？**
事实：今天图片 OCR 完就丢，库里一篇笔记没有任何图。
甲＝只把选图从 9 张改成 3 张（1~2 天，用户仍然看不到"笔记里有图"）。
乙＝笔记真存图、最多 3 张（约 2 周 + 云开发存储配额 + 一条新域名）。
**我建议乙**——因为你说的是"关联"，关联这个词意味着图要跟着笔记走；甲做完你下一句一定还是"图呢"。但这条差一个数量级，必须你点头。

**② 隔离走甲（同 AppID + 分支）还是乙（另开 AppID）？**
我建议甲。乙的唯一好处是"老用户不被打扰"，代价是两套判据两套域名两次审核，你一个人扛不住。

**③ 1.9.30 什么时候提审？**
2.0 的开工前提是阶段 0 收口。你扫过 1.9.30 没问题的话，我建议**今天就提**（版本描述我起草好，你扫一次登录码即可），否则阶段 0 整段往后压。

**④ 挂起分支里那四件（导出 Word / 一键存朋友分享 / 海报 AI 配图 / 小红书竖版）要不要捞回 2.0？**
都不在你这次说的四条里，所以默认不捞。哪件要，单独点一件——AI 配图那件还要额外配 downloadFile 域名，成本另算。

**⑤ `render: 'client' | 'server'` 那枚门撤不撤？**
它只出现在方案 §八，表里、迁移里都没有这一列，从没落地。建议**撤**（按 P1 收口），留着会误导下一个读文档的人以为有服务端出图这条路。

**⑥ 上一轮浅字那三条还挂着**：头部那两列白字压照片（抬到满白也只 2.86:1，要过线得压深头部那层罩）、二级字抬 .85 恢复三档深浅、新建页分类格那枚字。都不在 2.0 范围里，但 2.0 会重写这些页的样式，**开工前一并定掉最省**。

## 6. 风险与依赖

- **审核 1–7 天**，2.0 提审要排在大赛截止（10-17）之后还是之前，你自己权衡；这条会影响阶段 4 的日期。
- **云开发配额**：混元那条链路的 10 亿 Token 包 2027-03-18 到期；图片若走云开发存储，5GB 起步，超出是钱。
- **配方上界**：单套 16KB / 24 层 / 2000 节点，新模板画到复杂就会撞（P1 那两套是贴着界过的）。
- **个人主体**：虚拟支付、微信 OCR、部分类目权限拿不到——挂起分支里 xpay 那条即使捞回来也仍受这条限制。
- **仓库是公开的**（GitHub public），任何"下发配方"的细节写进仓库＝公开，配方里不许出现密钥或内部域名。
