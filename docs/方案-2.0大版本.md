## 0. 锚点

一句话：**把"卡片模板能不走发版就更新"做成一条真能跑、真有人管的通道；把截图和拍照来的图真正留在笔记上（9 张不动）；全程不许把线上 1.x 那条线弄坏。**

## 2. "与旧版隔离"怎么隔（先讲一件平台事实）

**微信小程序线上只有一个版本。** 不存在"1.x 用户和 2.0 用户同时在线各用各的"这种状态（除体验版/开发版那条灰度通道）。所以"隔离"只能发生在三个地方，不能发生在"两个线上版本并行"上：

- **甲 同 AppID + 分支隔离 + 数据向后兼容（建议）**
  拉 `release/2.0` 分支，master 冻结成"只修 P0 故障"；2.0 期间线上继续发 1.9.x 的补丁。
  兼容契约三条：① 接口字段**只增不改不删**，老包读新数据不许炸；② 配方读不懂就整套回退包内那十套——**这条今天已经是这个行为，但机制不叫 `schema_version`**（全仓没有这个字段，我之前凭印象写过一次，更正于此）：实际是三道闸，`min_app_version` 版本门槛、`poster.js` 那份 op/原语字段表加三条上界（16KB／24 层／2000 节点）、以及"配方自己的 id 必须等于这行的 template_id"，任何一道不过就**整行丢弃**，绝不"跳过不认识的那一层继续画"（半张图比不用更糟）；③ 数据库迁移只加表加列，2.0 期间不许改老列语义。
  代价：2.0 上线那一刻，所有用户一次性跳到 2.0，没有"想留在旧版"的出口。
  好处：一份 i18n、一套判据、一个域名配置、一次审核。你一个人维护，这条最省。

- **乙 另开 AppID，做一个全新的 2.0 小程序（真隔离）**
  代价：新 AppID 要重新配 request/uploadFile/downloadFile 合法域名、重新提审（1–7 天）、后端要按 AppID 分流用户与数据（现在 openid 是唯一键，等于要建"同一自然人两个身份"的映射）、老用户不主动迁移就看不到新版、i18n 与判据两套各自维护、云开发配额与混元 token 也要按两个主体算。
  适合的场景只有一个：你想让 2.0 换名字/换定位重新起盘。这次四条需求里没有这个意思。

- **丙 同一个包里做新旧双皮肤/开关**
  代码不隔离，两套 UI 长期共存，每条判据都要跑两遍。**不建议**，这是三种里最贵的，而且和"与旧版隔离"这句正好相反。
