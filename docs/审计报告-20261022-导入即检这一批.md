## ② 待拍：同一张图被压两遍

**现读**：检图那一路 `create.js:988` 调 `compressForBackup(p)`，提交那一路 `_backupShots` 在 `create.js:1061` **又调一次**同一个函数、同一个入参。
一次选九张＝九次离屏 canvas 重绘；滑到底再提交＝**同样九张再重绘九次**。
`imageCompress.js` 那一族是长边 1920、预算 500 KB、质量三档试（`:10-14`），每档都要 `wx.canvasToTempFilePath` 导一次＋`getFileInfo` 量一次。

**代价落在哪**：CPU 与内存，而且落在**手机上不是服务器上**——这条屏的既有纪律正是为此立的（`_backupShots` 注释写着"九张 4000×3000 一起重绘离屏 canvas 会把内存吃穿"）。串行没变，但**总功翻倍**了。

**为什么不顺手改**：修法要缓存"路径→压完那张"，而**仓里已经记过这条坑**：本机按路径缓存位图，同名换内容时界面／画布仍画第一张（旧图残留那类）。所以"按 path 做 key 的缓存"是已知会骗人的，得连"同一 path 被重写过"一起判（加 mtime 或尺寸），这不是三行的事。
**要改的话照抄这一条**：`_checkShots` 把压完的 `{path, bytes, width, height}` 存进一个与 `previewImages` 同下标的数组（**不用 path 当 key**，用下标；`removeShot` 那一刀跟着 splice），`_backupShots` 先查这一格、查不到再压。
**待拍点**：要不要在下一刀做。本批没做，**做了也不改变屏上任何一句话**。

## ③ 待拍（前提未证实）：两串都假设"路径唯一"

**现读**：`_setShotState` 按**路径**找下标（`create.js:962-969`，`previewImages.indexOf(path)`），而 `create.wxml:333` 那一排用的是 `wx:key="*this"`（列表值本身就是 key）。

**要说清的两点，免得这条被当成新 bug 夸大**：

**要证伪／证实的最便宜一条路**（写在这里，下次别重新想）：在 `pickImage` 的 `success` 里把 `fresh` 打一行 `console.log(fresh)`，模拟器里连着两趟选同一张图，看两串值是否相同。这一步不需要真机、不需要他扫码。
