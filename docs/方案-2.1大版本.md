## 〇、先把三条前提摆正（不摆正，后面每一步都会歪）

1. **那串"私密密码"不能当迁移凭证，也不能派生密钥。** 现网存的是 6 位数字的**无盐 sha256**（`backend/app/api/routes/user.py` 的 `_hash_pin`：`hashlib.sha256(pin.encode()).hexdigest()`）。6 位数字＝10⁶ 种，服务端一次能试几万发，**它连"锁自己笔记"都只靠接口限流挡着**，更不能当"把整个账号搬走"的凭据。它也没有加盐迭代，拿它派生加密密钥同样不成立。
2. **微信内换手机不需要迁移。** 身份是 openid，跟着微信号走；他在新手机上用微信打开小程序，`POST /api/auth/wechat` 拿到的还是同一个 `users.id`，笔记、分类、卡片、壁纸全在。**"跨端"这件事真正的难点从来不是搬数据，是"账号能不能脱离微信存在"。**
3. **"跨端"这个词得先定义，它可能是三件事**（我按代价从低到高排）：
   - 甲 **同账号多设备**（微信内换手机／iPad／桌面端小程序）——**今天已经成立**，只差没人验证过。
   - 乙 **同一个后端，多一个入口**（H5 落地页已经有了：扫码看分享那一层；再往上是"能登录能编辑的网页版"）。
   - 丙 **原生 App**（iOS/Android，用邮箱或手机号注册，与微信账号能合并成同一个人）。
   这三件事的架构差别很大，**不能一起开工**。下面 §二 的排法默认他要的是 甲＋乙，丙单独列成 2.2 的门槛。

## 一、三块的先后顺序（为什么是这个顺序）

**UI 改造 → 跨端账号 → 数据迁移。** 不是随便排的：

- UI 改造不碰数据模型，风险最低、体感最大，先做能立刻拿到反馈；而且**跨端（乙）一旦开工，网页版要重做一套皮**，所以皮必须先定下来，否则两套皮各改各的。
- 跨端账号是数据迁移的**前置**：迁移的前提是"两边都有账号"。没有第二种身份之前，"迁移"只可能是"同一个微信换手机"，那本来就不用迁。
- 数据迁移放最后，且**它真正的用处是"把微信里攒的东西搬进 App/网页账号"**，不是"救回丢掉的卡片"（那条已经查实：原图没上云就是找不回来，见 PRD §8.152，这条线不许再包装）。

## 二、跨端账号：最小改动的那条路

现网身份链是 `openid → users.id → JWT(gen 代数)`（见 `wtsj-jwt-auth-architecture`）。加第二种登录方式，**只加一张表，不动老表**：

```
identities(id, user_id, kind, value, verified_at, created_at)
  kind ∈ {'wechat_openid','email','phone'}
  UNIQUE (kind, value)
```

- 老用户一行都不用写：`users.openid` 继续当真相，`identities` 只给新登录方式用；等哪天真要合并再回填。
- 邮箱那一格**已经上线**（`contact_email`，10-04 那批），它就是现成的锚点：把"填邮箱"升级成"用邮箱登录"，用户已经会填了，不用再学一个新概念。
- 一个微信账号绑一个已验证邮箱 → 之后他可以用邮箱登录进**同一个 `user_id`**，看到的还是那批笔记。这就是"跨端"的全部机制，不需要新数据库、不需要同步协议。
- **JWT 里必须带上"这次是哪个身份登进来的"**，注销／改密／换绑的语义才说得清；`generation` 那一栏（现网已有）继续负责"改密就踢掉所有旧票"。

代价与风险，说在前面：
- 邮箱验证码要发信服务。现网**没有任何发信通道**（`backend/.env` 里没这项，服务器上也只有微信那两条凭据）。要么接腾讯云 SES（个人主体可开，按量计费，要备案域名过 SPF/DKIM），要么先只做"迁移码"这种**不对外发信**的通道。**这条不定，跨端就只能做到甲。**
- 一旦有第二种登录方式，"个人主体小程序能不能做账号体系"要重新过一遍微信的审核口径（虚拟支付那次已经踩过"平台枚举值不许凭印象造"这条，提审前得查现行规则）。

## 三、数据迁移：能落地的形态是"一次性迁移码"，不是那 6 位密码

体验上跟他说的"用密码实现"是一样的，只是凭证换成长相：

```
A 设备（旧）  「导出到我的另一台设备」 → POST /api/user/transfer/export
              服务端签发一个高熵一次性码：MIG-7KQ2-9FXT-3BWN（15 字符，去易混字母）
              有效期 10 分钟、一次一用、当场把要搬的东西打包成一份"迁移清单"（不落第二份数据，只记 id 集合）

B 设备（新）  输入这个码 → POST /api/user/transfer/import
              服务端校验 → 把清单里的行改挂到新 user_id（或合并进已有账号）→ 两边各自刷新
```

要点，四条都是"不写下来一定有人改错"的：

1. **码是服务端签发的，不是用户自己想的。** 用户自己想的口令＝弱口令，就是 §〇 第 1 条那个洞。UI 上可以叫"迁移口令"，字面上随他，但值必须由服务端生成。
2. **一次一用 + 短时效 + 失败计数。** 迁移是"钱袋子级别"的动作（搬走的是他全部笔记），必须比私密密码那道锁更严，不是更松。
3. **迁移的是归属，不是字节。** 笔记、分类、`shares`、`note_cards`、`assets` 五张表改 `user_id` 就行——云存储那些对象**没有按用户分桶**（fileID 里带 userId 那一段是路径不是权限），所以搬完之后**对象地址不变**，不需要复制、也不需要重传。这条省掉一整套异步搬运。
4. **私密那几篇默认不搬，要搬必须当场解锁。** 判据是分类名「私密」（`app/core/private_access.py`），锁本身在服务端。跨端之后"锁"这件事更容易出错：新设备根本没设过密码。定死一条——**迁移时私密分类的笔记整类跳过，并在结果里明说跳了几篇**，要搬让他在新设备上重设密码后单独做一次。

顺带必须承认的一件事：**改 `user_id` 是破坏性写入**，中途失败会留下"一半在一半在二"的脏数据。所以迁移要包在一个事务里，且**迁移前先跑一次 `backup.sh`**（现成脚本，含恢复演练）。

## 四、新 UI 改造：这一块的活不是"再画一版"，是把已拍的收干净

今天工作树里躺着**已拍板但没落地**的几件（都在 PRD/记忆里记着，不是新想法）：

- 四套莫兰迪配色 + 界面统一规范（10-04 五轮拍完、10-05 晚三级字并档）：**169 处写死色**，其中 106 处是旧墨黑族。不收这个，换一套皮就是再多 169 处硬编码。
- 淡雅两枚壁纸（象牙／天青）在分支 `feature-tinted-wallpapers-and-ui-font` 上，**从没合进 master**。
- 列表 D2、详情窗 v22、「我的」v7→v10、深色实心按钮＝底栏选中那格圆底（#304 甲）——**三条深色来源没在一处生效**。

所以 2.1 的 UI 这条我建议只做一件事：**把颜色与字号收成令牌（唯一来源 `utils/palette.js`），把上面那几条已拍的推平**，不再画新效果图。理由：跨端要复用同一套皮，皮还散在 169 个写死色里，网页版就得重抄一遍。

**这条有个硬约束**：小程序的皮和网页版的皮现在是两套技术（wxml/wxss vs CSS），**令牌可以共用，组件不能白拿**。真要乙，得先决定网页版走"H5 独立一套皮、共用设计令牌"还是"跨端框架一套代码"。我倾向前者（跨端框架为了小程序那套渲染层，坑的成本比省下的钱高），但这条要他拍。

## 六、负面清单（明确不做什么，防止下一个人自己长出来）

1. **不做"找回丢掉的卡片"。** 原图没上云就是找不回来。这条今天已经查实并被站长打回两次（PRD §8.152），以后不许再以任何形式（空框、待确认、自动重出）回到界面上。
2. **不把那 6 位私密密码当账号凭据、不当密钥派生源、不跨端复用。** 要真锁数据得换 KDF（加盐迭代）并让用户重设一次——那是独立一条需求，不塞进迁移里顺手做。
3. **不自己造平台枚举值。** 账号体系一旦上小程序，审核字段／类目／隐私声明项必须从后台现读，不许凭印象填（ITMS-91054 那次两版二进制被打回是同一条教训）。
4. **不做同步协议／离线冲突合并。** 现在的模型是"服务端唯一真相 + 本机缓存"，跨端是"同一个库两种入口"，不是多写合并。真要做多端并发编辑再单独立项。
5. **不给卡片或配图另起一套配额口径。** 卡片实测 204–239KB 已经把"每张 ≤200KB 入账"那个上界打穿了（今天量到的），2.1 里顺手改成"直接 SUM 真实 `file_size`"，别再拿估算值当账。

## 七、要他拍的（每条自带我的理解、事实、两条路、代价）

**① "跨端"到底指哪个？** 我的理解是"换个设备／换个入口还能看到同一批笔记"。事实：微信内换手机今天就已经成立，不需要任何开发。所以真需求要么是"网页版"，要么是"App"。
- 甲 只做网页版（H5 登录版）：代价＝要一套新皮 + 发信通道；好处＝不用提审、不用 App 上架。
- 乙 做 iOS App：代价＝多一条发版线＋审核＋隐私合规重做（TumarkNote 那条线的坑要重踩一遍）；好处＝商业化位置更好。
- 建议：**先甲**。理由：同一套后端同一套数据，甲做完乙就只是换个壳。

**② 邮箱验证码要发信服务，接不接？** 事实：现网零发信通道，个人主体能开腾讯云 SES，要备案域名 + SPF/DKIM。
- 甲 接 SES：代价＝一次配置 + 按量计费（几分钱一封）；好处＝邮箱登录、找回密码、迁移通知全都有路。
- 乙 先不接，只做"迁移码"（服务端生成、他自己在两台设备间抄，不发信）：代价＝没有"忘记密码"这条路；好处＝零外部依赖。
- 建议：**乙先跑通迁移码，SES 与邮箱登录放同一批但不挡迁移**。

**③ UI 这条 2.1.0 只做"令牌化 + 已拍推平"，不再出效果图，行不行？** 事实：手上压着 169 处写死色和一条从没合分支的壁纸。
- 甲 按我说的做：代价＝这一版看不到"新样子"，只是把已拍的落地。
- 乙 先出新一轮效果图再改：代价＝令牌不先收，新皮再叠一层写死色，以后每次换色改两遍。
- 建议：**甲**。

**④ 迁移时私密那几篇，跳过还是搬？** 建议**跳过并明说跳了几篇**；代价＝他要手动再做一次。搬的话必须在迁移流程里输一次密码，而那个密码只有 6 位、无盐——我不愿意在迁移这条高危链路上复用它。
