## 〇、先把三条前提摆正（不摆正，后面每一步都会歪）

1. **那串"私密密码"不能当迁移凭证，也不能派生密钥。** 现网存的是 6 位数字的**无盐 sha256**（`backend/app/api/routes/user.py` 的 `_hash_pin`：`hashlib.sha256(pin.encode()).hexdigest()`）。6 位数字＝10⁶ 种，服务端一次能试几万发，**它连"锁自己笔记"都只靠接口限流挡着**，更不能当"把整个账号搬走"的凭据。它也没有加盐迭代，拿它派生加密密钥同样不成立。
2. **微信内换手机不需要迁移。** 身份是 openid，跟着微信号走；他在新手机上用微信打开小程序，`POST /api/auth/wechat` 拿到的还是同一个 `users.id`，笔记、分类、卡片、壁纸全在。**"跨端"这件事真正的难点从来不是搬数据，是"账号能不能脱离微信存在"。**
3. **"跨端"这个词得先定义，它可能是三件事**（我按代价从低到高排）：
   - 甲 **同账号多设备**（微信内换手机／iPad／桌面端小程序）——**今天已经成立**，只差没人验证过。
   - 乙 **同一个后端，多一个入口**（H5 落地页已经有了：扫码看分享那一层；再往上是"能登录能编辑的网页版"）。
   - 丙 **原生 App**（iOS/Android，用邮箱或手机号注册，与微信账号能合并成同一个人）。
   这三件事的架构差别很大，**不能一起开工**。他 10-08 回的原话（"同一个微信号，换不同手机，或者重置本手机，下次再登录，依旧获取自己的笔记"）指的就是**甲**——所以 2.1 的范围是 甲 + 备份还原，乙／丙 留到 §八 第 ④ 条再拍。

## 一、三块的先后顺序（为什么是这个顺序）

**UI 改造 → 跨端账号 → 数据迁移。** 不是随便排的：

- UI 改造不碰数据模型，风险最低、体感最大，先做能立刻拿到反馈；而且**跨端（乙）一旦开工，网页版要重做一套皮**，所以皮必须先定下来，否则两套皮各改各的。
- 跨端那条今天**不要先写代码，要先实测**（同一个微信号换设备，理论上一直是通的，只是没人证明过）；它排在备份之前是因为它便宜，且红了才说明备份这条链子有对象。
- 备份／还原放最后，且**他 10-08 拍下来的形态是"加密备份文件 + 邮箱投递 + 登录后解析还原"**（§三），不是"救回丢掉的卡片"（那条已经查实：原图没上云就是找不回来，见 PRD §8.152，这条线不许再包装）。

## 二、跨端账号：最小改动的那条路

**这一整节是为"乙／丙"（网页版、App）备着的，他 10-08 拍的甲（同一个微信号换设备）用不上它，2.1 不建这张表。** 留着的理由：一旦要第二种登录方式，绕不开它，届时别再从零想一遍。

现网身份链是 `openid → users.id → JWT(gen 代数)`（见 `wtsj-jwt-auth-architecture`）。加第二种登录方式，**只加一张表，不动老表**：

```
identities(id, user_id, kind, value, verified_at, created_at)
  kind ∈ {'wechat_openid','email','phone'}
  UNIQUE (kind, value)
```

- 老用户一行都不用写：`users.openid` 继续当真相，`identities` 只给新登录方式用；等哪天真要合并再回填。
- 邮箱那一格**已经上线**（`contact_email`，10-04 那批），它就是现成的锚点：把"填邮箱"升级成"用邮箱登录"，用户已经会填了，不用再学一个新概念。
- 一个微信账号绑一个已验证邮箱 → 之后他可以用邮箱登录进**同一个 `user_id`**，看到的还是那批笔记。这就是"跨端"的全部机制，不需要新数据库、不需要同步协议。
- **JWT 里必须带上"这次是哪个身份登进来的"**，注销／改密／换绑的语义才说得清；`generation` 那一栏（现网已有）继续负责"改密就踢掉所有旧票"。

代价与风险，说在前面：
- 邮箱验证码要发信服务。现网**没有任何发信通道**（`backend/.env` 里没这项，服务器上也只有微信那两条凭据）。不过 §三 那条"把加密包发到邮箱"本来就要开一条发信，**跨端与备份可以共用同一条通道**：先把"寄附件"这条路打通，登录侧要不要再叠一层验证码是独立一议。
- 一旦有第二种登录方式，"个人主体小程序能不能做账号体系"要重新过一遍微信的审核口径（虚拟支付那次已经踩过"平台枚举值不许凭印象造"这条，提审前得查现行规则）。

## 三、"复原"这一条：最简路径是把只在本机的那几样搬上服务器（已做完代码）

站长 10-08 晚追加一句授权：**「如果复原，你设计最简单路径就行了，不一定按我的建议走。」** 所以这一节换了形态，他那三条口径仍然全部生效（界面上不出现密钥口令、邮箱不验证归属、减少使用门槛）——搬上云是这三条的最强形式：**用户一步都不用做**。

先说实测到的事实，因为它决定了整条路怎么走：他要的那句"同一个微信号换手机／重置手机后再登录，依旧获取自己的笔记"，**笔记这一路今天就已经成立**——笔记、分类、分享、卡片行（`note_cards`，2.0.1）、配图（`assets`）、私密锁、壁纸那一枚（`users.wallpaper`）全在库里。真正只写在这台手机上的只有四样：

| 只在本机的东西 | 存在哪 | 换手机后的表现 |
|---|---|---|
| 名片那四格形象图 | `poster_avatar_files` + `${USER_DATA_PATH}/*.img`，判据是 `exists(path)` | **四格全空**，且静默（与 2.0.1 之前卡片那一格同一个根） |
| 名片的名称与一句话 | `poster_profile` | 回到兜底那个"麦"字 |
| 背景亮度档 | `bgDim` | 回到默认那一档（小） |
| 卡片模板选的那一套 | `poster_profile.template` | 回到默认模板（**这一样还没搬**，见 §八 ⑤） |

所以做的是：新表 `user_profiles`（一人一份）+ 两个口 + 客户端 `utils/profileCloud.js`。**登录成功那一刻顺手对齐一次**：本机文件在就沿用（不重下、不花钱），不在就从 `cloud://` 拉回来落成本机一张新文件，画布那一路一个字都没改。老用户第一次升上来时服务器上还没有那一行，走的是反方向——先把本机这份推上去登记，**绝不许删本机任何一张**（这条写错就是数据丢失，尺子里钉着）。

三条没变的老规矩照样成立：换下来／撤掉的旧对象由回体 `file_ids` 交给客户端删（服务器删不掉）；这条链全程不抛，附属品失败不许把"本机已存好"报成失败；换身份时只清内存那一份。

**一处与他的建议不同、我按事实改口的取舍**：界面字体档**不上云**。`app.js` 顶上那段早就写着安卓上那三档字体基本命不中，跟着账号跑到别人设备上只会让人看到"没生效"——那不是"东西丢了"，是那台设备本来没这个能力。这条钉在尺子里（`ui_font` 不许出现在任何请求体）。

**邮件附件那条降级成可选的第二层**，不挡这条路，理由：它解决的是"想在自己手里留一份离线副本"，而不是"换手机后还是我的东西"。真要做，原来那两条硬话仍然算数：

1. **"用户把文件放到指定目录"这句话，在小程序这一侧唯一的落法是微信会话**（`wx.chooseMessageFile`；小程序读不到手机上任意目录）。移动文件由用户做、不是小程序做，所以与他的说法不矛盾——只是要翻译成小程序唯一开得了的那扇门。**这条还没实测，跑通之前不许写进规格。**
2. **不验证归属 ⇒ 邮箱能当"收件地址"，不能当"登录身份"**（邮件发错＝没收到，登录被人占用＝别人的笔记被看到，两种错的代价不同量级）。
3. 还原是往现有账号里写数据的破坏性动作：包在一个事务里，跑之前先照服务器现成的 `backup.sh` 存一份库。发信通道是实现选型（要开一条，SPF/DKIM + 已备案域名现成），附件上限、包体积、单价三样**做之前实测**，现在不写数。

## 六、负面清单（明确不做什么，防止下一个人自己长出来）

1. **不做"找回丢掉的卡片"。** 原图没上云就是找不回来。这条今天已经查实并被站长打回两次（PRD §8.152），以后不许再以任何形式（空框、待确认、自动重出）回到界面上。
2. **不把那 6 位私密密码当账号凭据、不当密钥派生源、不跨端复用。** 要真锁数据得换 KDF（加盐迭代）并让用户重设一次——那是独立一条需求，不塞进迁移里顺手做。
3. **不自己造平台枚举值。** 账号体系一旦上小程序，审核字段／类目／隐私声明项必须从后台现读，不许凭印象填（ITMS-91054 那次两版二进制被打回是同一条教训）。
4. **不做同步协议／离线冲突合并。** 现在的模型是"服务端唯一真相 + 本机缓存"，跨端是"同一个库两种入口"，不是多写合并。真要做多端并发编辑再单独立项。
5. **不给卡片或配图另起一套配额口径。** 卡片实测 204–239KB 已经把"每张 ≤200KB 入账"那个上界打穿了（今天量到的），2.1 里顺手改成"直接 SUM 真实 `file_size`"，别再拿估算值当账。
6. **备份邮箱不做归属验证、备份文件不做用户口令。** 这两条他 10-08 明确撤过（"邮箱不需要验证…加密方式按常规来做就行…减少用户使用门槛是关键"），谁也不许再以"更安全"的名义加回界面上——真要更严，走 §三 第 2 条那个"登录身份"的独立一议。

## 八、剩下要他拍的（每条自带我的理解、事实、两条路、代价）

**① 邮件备份包这一层还要不要做？** 我的理解：他要的是"换手机后还是我的东西"，这一条 §三 那条已经解决了（而且用户零操作）。邮件那一层多出来的只有一件事：**在自己手里留一份离线副本**，连服务器和云存储都被清掉时还在。
- 甲 不做：代价＝没有那份"第三方都不在我手上"的副本；好处＝零新依赖、零发信费、界面上不多一格。
- 乙 做：代价＝要先实测两件事（`wx.chooseMessageFile` 那扇门真能选到邮件附件、附件大小上限），还要开一条发信服务；做出来是 2.1.4 那一格。
- 建议：**先不做**，等 2.1.1/2.1.2 真机跑通、"换手机后一切还在"落地之后再谈。原来那两条子问题（包里含不含图片本体、私密那几篇进不进包）只在选乙时才成立，我先把它们留在这节里，不提前实现。

**② 后台《用户隐私保护指引》那项「邮箱」什么时候重交？** 事实：现网指引文本我没动过；`contact_email` 这一格界面上已经能填（「我的→设置→我的邮箱」），而指引里那一项是 10-07 那次随 2.0.0 提审落的。
