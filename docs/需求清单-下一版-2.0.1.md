## 一、先把"更新之后卡片没了"这件事讲清（这是他要求的"讲清原因"）

**结论一句话**：那张卡片的成品图**从来没上过服务器**，它只是这台手机里的一个文件；文件被清掉，界面上那一格就退回"没生成过"，而且不报错、不留痕。**2.0 这次更新没有删它**——但更新过程正是最容易让这个文件消失的那几种时刻之一。

四条实据：

1. **留档全在本机两处**：账在 `wx.setStorageSync('cardLog')`，图在 `${wx.env.USER_DATA_PATH}/cards/{noteId}-{tplId}-{时间戳}.jpg`（`miniprogram/utils/cardLog.js:20-21`、`:42`）。
2. **服务端零存放**：后端全仓与卡片成品图有关的只有一列 `shares.cover_asset_id`（`backend/app/models/share.py:34`），那是扫码落地页的封面，不是卡片图。`note_cards` 这类表在仓库里零命中。
3. **判据不是这次改严的**：`cardLog.aliveFor`（`:87-94`）那条"图文件不在就不算数"的规则，在 1.9.29 的首页里一模一样地写着（`git show master:miniprogram/pages/index/index.js` 第 318-326 行 `_cardsOf`，同一句 `fm.accessSync(p)`）。`git diff master...release/2.0 -- miniprogram/utils/cardLog.js` 总共只有 **+21 行**（就是把那段搬进函数），存储键 `cardLog`、目录 `.../cards`、文件名格式、`kind` 一个都没改。**所以"更新导致卡片消失"这条机关我在代码里没找到，不该写成结论。**
4. **另外两条我扫过、可以排除**：① 那两次"进页就清账"的一次性归一（`cardLog.js:100-127`）由 `cardLogKeepOnly` / `cardLogOnePerNote` 两个 flag 挡着，你手机上早就立过；② 2.0 的"与旧版隔离"是**分支隔离**（同一个 AppID、同一份本机 storage 与私有目录），不是数据隔离。

**那到底是什么把文件清掉的**（按可能性排，并标出没验过的）：

- 微信对小程序**本地私有目录**的清理：用户在微信「我→设置→通用→存储空间」里清缓存、或系统按配额回收，能只清掉图而清不掉 storage 里那份账（`cardLog.js:79-82` 记着 10-03 在模拟器上实测到过这一态：`src` 递到了、尺寸有、`accessSync` 说文件不在）。
- **删掉小程序再进**、或**换一台手机**：两处一起没了。走「我的→关于→…」重新进入新版并不会删包，但如果那一次是"删除后重装"，就必然空。
- **这条我没量，所以只当候选**：私有目录配额（约 10MB）被 2.0 新增的本机件（首页背景、两枚壁纸小样、模板缩略、随笔记保存的压缩图副本）挤紧，导致系统回收更早发生。**这条要靠量，不靠推理**，见下面 P0-4。

**还有一半是好的，要说清**：已经发出去的那张卡片本身没丢——现网库里 `shares` 20 行、15 行活动，你名下那 12 行仍活动，扫码落地页仍打得开。丢的是那一张图与"这篇生成过卡片"那一格。

## 二、P0（这一版的唯一主线）：卡片留档搬到服务端 + 存量救回的路径

### P0-1 服务端有一张能说话的表

新增 `note_cards`：`note_id / user_id / object_key / tpl / no_qr / file_size / created_at`。

- **为什么不复用 `assets` 表加个 `file_type='card'`**：`assets` 那张表有 `MAX_ASSETS_PER_NOTE = 9`（`backend/app/models/asset.py:7`）、详情页读图与公开页露图都按它取，卡片混进去的症状是"卡片被当成第一张配图露在公开页上"。新表便宜，串味贵。
- 一篇只留一张这条硬规则不变（10-03 你定的），换模板要先删旧的那张，服务端按 `note_id` 唯一约束挡。
- 卡片对象**算进全站配额**（它真占空间），但单独一项 SUM——不与那 5GB 配图那条混写成同一个数。

### P0-2 生成那一刻就上传（复用已经上线的直传链）

走 `utils/cloudUpload.js` 那条（10-07 已上现网、探针 41/41），不新建基础件。上传失败不阻断分享本身（与 B 链同一条纪律），失败的那一份落本机待传队列。

### P0-3 三处判据改吃服务端，本机文件降级成缓存

列表那一格、详情页右上那一格、笔记卡片页「一篇只留一张」那道闸（`pages/share/share.js:74`）——现在三处都问"这台手机上文件在不在"，改成问"服务端有没有那一行"；有就画（本机有缓存就读缓存，没有就从云取）。**这一条做完，"更新后卡片消失"整类问题才到此为止。**

### P0-4 开工第一件事是量两个数（不量完不许写代码）

① 一张卡片成品图实际多少字节（`wx.canvasToTempFilePath` 出的是 jpg）；② 本机私有目录现在被什么占着、离上限还剩多少（`wx.getFileSystemInfo`）。这两个数决定卡片要不要单设一档更小的尺寸，也决定 §一 最后那条候选能不能写成结论。

### P0-5 存量救回：三档，从高往低走（这条就是他要求"必须补的那一条"）

**关键事实**：卡片是**按数据确定性渲染出来的**，不是拍照得来的——所以"救回"不等于找回那个文件，而是**重渲染出同一张**（`pages/share/share.js:139-154`：`poster.posterProfile()` + 那篇笔记 + 模板 id + `showQr` → `poster.planPoster(...)`）。

- **补传档（图还在，只是没上云）**：本机台账里 `aliveFor` 还列得出的那些 → 一次性补传，服务端记下 `tpl/no_qr`，立 flag 不重复跑。**这一档做完你就不会再丢。**
- **重渲档（台账里 `tpl`/`no_qr` 还在，图被清了）**：用**同一套模板、同一份笔记内容**重渲染一张再上传。要说清一句代价：渲染要吃「分享形象」那三样（名字、一句话、四槽图，现在只在本机 `poster_profile` / `poster_avatar_files`），如果那张图也被清掉了，重渲染出来的**不是原来那一张**（少头像或换成占位）——所以界面上要写"这是重新生成的那一张"，不能悄悄顶替。
- **待确认档（连台账都没了，只有 `shares` 那行还在）**：服务端只能证明"这篇曾经公开过"，不知道用的是哪套模板。这一档**不猜**：那一格显示"这篇公开过，卡片需要重新出一张"，点一下走现在的生成流程。宁可多一句实话，不要画一张他没见过第二次的图当"原图"。

三档都要在同一趟里跑完，跑完给一份数：补传多少张、重渲染多少张、多少张只能重出。**这份数是给验收看的，也是唯一能证明"救回"真发生了的东西**。

## 四、开工顺序与验收（怎么测，不看代码看结果）

1. P0-4 先量那两个数（半天）→ 2. P0-1 建表与接口 + 用例（本机）→ 3. P0-2 生成即上传 → 4. P0-3 三处判据改服务端（**要连带改那三处依赖本机文件的尺子口径**）→ 5. P0-5 存量三档跑一遍 + 出那份数 → 6. ②③④。

**验收口径（这一条过了才叫解决）**：给一篇笔记生成卡片 → 把小程序从后台划掉、在微信「我→设置→通用→存储空间」里清一次这个小程序的缓存（或直接换另一台手机登录同一个微信）→ 再进那篇，**那一格还是同一张卡片**。

**不这么验收的后果**：只看"我这侧模拟器画得出来"永远测不到这个 bug，因为它的全部触发条件就是"本机文件没了而数据还在"。

## 五、2.1 的边界（一句话，不在这一版做）

新 UI 改造、跨端与数据迁移那条另出一份技术方案。今晚查实的一条硬约束要写在最前面：私密密码在库里是**6 位数字的无盐 sha256**（`backend/app/api/routes/user.py` 的 `_hash_pin`，`sha256(pin.encode()).hexdigest()`，没盐没迭代次数），**它既不能当账号凭据、也不能拿来派生加密密钥**。所以"用密码功能来实现数据迁移"这句话需要先解决"迁移密钥从哪来"，不是把现有那一列改改就能用。

## 六、需要他拍的（每条写了我建议哪个）

**一、P0 这一版做多少？** 我建议：**P0-1～P0-5 全做，P1 三件里只做 ②**。理由：③ 要他看图、④ 是地基但工作量能单独算，把它们挤一批会让"卡片不再丢"这件救火的事跟着延期。
- 好处：这一版就是一条主线，验收只看那一个动作（清缓存再进，卡片还在）。
- 我建议不要的第三条路：只做 P0-3（改判据）不做 P0-1/P0-2（真存上去）——那会让界面显示"有卡片"而点开是白板，比现在更难看。

**二、重渲档"重渲染同一张"要不要做？** 我建议：**做，但界面上必须写"这是重新生成的那一张"**。
- 好处：台账里 `tpl` 还在的那些（也就是绝大多数）能真的回到眼前。
- 不做的最坏情况：只补传图上得到的那些，其余仍显示"没生成过"，在他眼里就是"我生成的卡片被版本更新吃掉了"——他今天已经这样看了第二次。

**三、2.0.0（已过审）先发还是压住、把 P0 并进去一次过？** 我建议：**先发**。
- 好处：已过审的包不浪费（重新排队 1-7 天），2.0 那条主功能（图片存得下来）当天就能被真用户用到。
- 关键一句：**2.0.0 不会让卡片更容易丢**（§一 第 3 条：判据、键名、目录、文件名全没改），风险面与线上 1.9.29 一致。
- 不发的最坏情况：这一版排队重来一次，而救火那条（P0）本来就要另出一版——等于两件事都没提前。
